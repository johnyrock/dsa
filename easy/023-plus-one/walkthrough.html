Easy · Two Pointers · LeetCode #66

Plus One, narrated

Scroll through the string-conversion shortcut, the carry that only disturbs trailing nines, and a right-to-left trace of the two-line loop, with the digit array shown alongside.

Pattern used Two Pointers Addition starts at the least significant digit. A non-nine absorbs the carry; a nine becomes zero and passes the carry left.

STEP 1

The problem

You are given a non-empty array digits holding the decimal digits of a non-negative integer, most significant digit first. Add one to that integer and return the result in the same form. The array has no leading zeros unless the number itself is 0.

Running example: digits = [1,2,9], which is the number 129. Adding one gives 130, so the answer is [1,3,0].

The output is an array, not an integer. That matters: the array can hold up to 100 digits, far more than a 64-bit integer can represent, so "convert to an int and add" is not a general solution even if it works in Python.

STEP 2

First instinct: rebuild the integer

The obvious shortcut is to glue the digits into a string, parse it, add one, and split the result back apart:

value = int("".join(str(d) for d in digits))return [int(c) for c in str(value + 1)]

For the running example this computes int("129") + 1 = 130 and then splits 130 into [1,3,0]. It is correct in Python, where integers grow without bound, and it is O(n) time. But it walks every digit twice (once to join, once to split), allocates two strings and a new list, and in Java, C++ or Go a 100-digit input overflows the integer before the addition ever happens.

The deeper objection is that it ignores the structure of the problem. Adding one to 129 only changes the last two digits. Building the whole number from scratch to change two positions is wasted motion.

STEP 3

The key insight: only the trailing nines move

Do the addition the way you would on paper. The carry enters at the least significant digit, digits[2] in the example. If that digit is below 9, it absorbs the carry (it goes up by one) and nothing to its left changes. If it is a 9, it becomes 0 and the carry moves one position left, where the same question is asked again.

The only digits that change are the trailing run of 9s (each becomes 0) and the first non-9 to their left (it goes up by one). Everything further left is untouched.

That is why the code starts with for index in range(len(digits) - 1, -1, -1) and checks if digits[index] < 9. The panel dims digits[0] and digits[1] because, until the carry reaches them, they are not part of the computation at all.

STEP 4

The approach: scan right to left, stop early

Walk index over 2, 1, 0. At each position there are exactly two cases:

  • digits[index] < 9: do digits[index] += 1 and return digits immediately. The carry has been absorbed and the answer is complete.
  • Otherwise the digit is a 9: set digits[index] = 0 and let the loop continue leftward, carrying the one.

If the loop finishes without returning, every digit was a 9 and the carry fell off the left edge. The last line, return [1] + digits, prepends it. The array is modified in place, so the common case needs no allocation at all.

STEP 5

Trace it: index 2, a nine becomes zero

The loop starts at index = 2, where digits[2] = 9. The test digits[2] < 9 is false, so the branch that increments and returns is skipped. Instead digits[index] = 0 runs, and the array is now [1,2,0].

The carry has not been absorbed. The loop continues to index = 1, still carrying the one. Notice that this is the only line in the loop body that runs for a 9: there is no explicit carry variable, because "the loop is still running" is the carry.

STEP 6

Trace it: index 1 absorbs the carry

Now index = 1 and digits[1] = 2. This time 2 < 9 is true, so digits[1] += 1 makes it 3 and return digits fires at once. The array is [1,3,0].

digits[0] is never visited. The panel keeps it dimmed for exactly that reason: the loop never reached index = 0, and the leading 1 is returned unchanged because it was never in danger of changing.

The early return inside the loop is the whole point of scanning from the right. For a typical input, the function does one comparison, one increment, and stops.
STEP 7

Trace it: the answer

The function returned [1,3,0], which reads as 130, and 129 + 1 = 130. Only two of the three digits were examined, and only two were modified: digits[2] went 9 → 0 and digits[1] went 2 → 3.

Compare with the string approach, which would have touched all three digits twice. The difference is small at n = 3 and large at n = 100 when only the last digit needs to change.

STEP 8

Where this goes wrong: the carry that nobody absorbs

The panel shows the case that breaks most first drafts: digits = [9,9]. Both iterations hit the 9 branch, so after the loop digits is [0,0] and the function has not returned. The correct answer is [1,0,0].

Forgetting the fallback. If the function ends with return digits after the loop instead of return [1] + digits, it returns [0,0] for [9,9]. Every all-nines input ([9], [9,9], [9,9,9]) comes back as all zeros, which is the number 0, not 10, 100, 1000. The [1] + is the only place the array ever grows.

Dropping the early return. Write the increment branch as just digits[index] += 1 with no return, thinking the loop will "finish naturally". It does not stop: for [1,2,9] it turns the 9 into 0, then increments the 2 to 3, then keeps going and increments the 1 to 2, and finally hits the fallback and returns [1,2,3,0]. Every digit to the left of the first non-9 gets an unwanted +1 and a spurious leading 1 appears.

Test three inputs before calling this done: a plain case like [1,2,3], one trailing nine like [1,2,9], and the all-nines case [9,9]. Each exercises a different line.
STEP 9

Time and space

In the worst case (every digit is a 9) the loop visits all n digits and then builds a list of n + 1 entries, so O(n) time. In the typical case it stops after the first digit. The extra space is O(1): the array is updated in place, and the only allocation is the [1] + digits list for the all-nines output, which is the answer itself and unavoidable.

ApproachTimeSpace
Join, parse, add, splitO(n), always touches every digit twiceO(n) for the strings and the new list
Right-to-left carry, in placeO(n) worst, O(1) typicalO(1) extra (n + 1 output only when all nines)

The string version also fails outright on fixed-width integers for long inputs. The carry version never forms the integer, so it has no width limit.

STEP 10

The final solution

Six lines of body. Each one is a step above.

  • for index in range(len(digits) - 1, -1, -1): walks from the last digit to the first, because that is the direction a carry travels.
  • if digits[index] < 9: asks whether this digit can absorb the carry without overflowing.
  • digits[index] += 1 absorbs it; the digit goes up by one and no carry remains.
  • return digits stops at once. Nothing to the left can change, so there is nothing left to do.
  • digits[index] = 0 is the only line reached for a 9: the digit wraps to zero and the loop continuing is the carry moving left.
  • return [1] + digits runs only if every digit was a 9. The carry fell off the left end, so the number gains a new leading 1.
One-line summary to remember: scan from the right; the first digit below 9 absorbs the carry and you return, every 9 before it becomes 0, and if there was no such digit, prepend a 1.
