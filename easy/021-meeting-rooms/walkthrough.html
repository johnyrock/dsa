Easy · Intervals · LeetCode #252

Meeting Rooms, narrated

Scroll from checking every pair to a sort and one linear scan, with the meetings drawn on a timeline alongside.

Pattern used Intervals Once meetings are sorted by start time, a meeting can only newly conflict with its immediate predecessor.

STEP 1

The problem

You are given a list of meetings, each as [start, end]. Decide whether a single person could attend all of them, which is another way of asking: do any two meetings overlap in time? Return True if none overlap, False if any pair does.

Running example: intervals = [[0, 30], [5, 10], [15, 20]]. The meeting [5, 10] sits entirely inside [0, 30], so one person cannot be at both. Answer false.

Two things to pin down before writing code. First, the answer is a single boolean; you never need to say which meetings collide. Second, what counts as overlap: [1, 2] and [2, 3] share only the instant 2, and the convention here is that meetings that merely touch do not conflict.

STEP 2

First instinct: check every pair

Two meetings a and b overlap when each starts before the other ends. Test that for every pair:

for i in range(len(intervals)):    for j in range(i + 1, len(intervals)):        a, b = intervals[i], intervals[j]        if a[0] < b[1] and b[0] < a[1]:            return Falsereturn True

Correct, and for three meetings it is three comparisons: (0,1), (0,2), (1,2). But the pair count is n(n − 1) / 2, so 1,000 meetings need about 500,000 checks and the constraint allows 10^4 meetings, which is 50 million. That is O(n²), and almost all of those comparisons are between meetings that are nowhere near each other in time.

STEP 3

The key insight: sorted by start, only neighbours can collide

Sort the meetings by start time. Now take any meeting and ask which earlier meetings it could overlap with. If it starts after the meeting immediately before it has ended, does it need to be checked against anything further back?

No. The panel shows [15, 20] against [5, 10] only. If [15, 20] clears [5, 10], and [5, 10] had already cleared [0, 30], the chain of adjacent checks already covers [15, 20] versus [0, 30]. And if [5, 10] did not clear [0, 30], we would have returned False at that step and never got here.

So after sorting, each meeting is compared with exactly one predecessor. That turns the quadratic pair scan into a single linear pass, at the price of an O(n log n) sort. The test itself simplifies too: once starts are ascending, a[0] < b[1] is automatically true for the earlier meeting, so the only condition left is intervals[index][0] < intervals[index - 1][1], line 5 of the solution.

STEP 4

The approach: sort, then scan adjacent pairs

  • intervals.sort(key=lambda interval: interval[0]) orders the meetings by start time, in place.
  • for index in range(1, len(intervals)) visits every meeting except the first, since the first has no predecessor.
  • if intervals[index][0] < intervals[index - 1][1]: return False: this meeting begins before the previous one has finished, which is a conflict. Stop immediately.
  • return True after the loop: every adjacent pair was clear, so no pair overlaps.

The panel summarises the test as start[i] < end[i-1]. Note the early return: the first conflict is proof enough, and nothing later can undo it. Also note that with zero or one meeting the loop body never runs and the function returns True, which is what the tests expect for [].

STEP 5

Trace it: the sort

Line 3 sorts by interval[0]. The starts are 0, 5 and 15, already ascending, so the sort leaves the running example in the order it was given: [0, 30], [5, 10], [15, 20].

That is a coincidence of this input, not something you can rely on. For [[7, 10], [2, 4]] the sort would swap them, and the adjacent-pair argument from step 3 only holds once the starts really are in order. The sort is the step that makes the rest of the algorithm correct, even when it looks like it did nothing.

STEP 6

Trace it: index = 1

The loop starts at index = 1, so the current meeting is intervals[1] = [5, 10] and its predecessor is intervals[0] = [0, 30].

Evaluate line 5: intervals[1][0] is 5 and intervals[0][1] is 30. 5 < 30 is True: the second meeting begins while the first is still running. The panel draws a dashed line at time 5, the start of [5, 10], and it falls inside the bar for [0, 30].

Overlap found on the very first comparison. One person would have to be in two rooms at once from 5 to 10.
STEP 7

Trace it: return at once

Line 6 executes: return False. The function is done. [15, 20] is never examined, and the panel dims it to show that.

This is safe because the question is existential: "does any pair overlap?" One overlapping pair settles it, and no later comparison could make the conflict go away. The brute force in step 2 would also have stopped here, but only because pair (0, 1) happened to be first; on other inputs it might grind through many clear pairs before finding a conflicting one that the sorted scan would have hit immediately.

STEP 8

Where this goes wrong: touching meetings and the missing sort

Using <= instead of <. The panel switches to intervals = [[1, 2], [2, 3]]. At index = 1, intervals[1][0] is 2 and intervals[0][1] is 2. With the correct test, 2 < 2 is False, the loop finishes, and the function returns true: one meeting ends exactly when the next begins, which is fine. Write if intervals[index][0] <= intervals[index - 1][1] instead and 2 <= 2 is True, so it returns False for meetings that merely touch.

Forgetting to sort. Drop line 3 and run [[7, 10], [2, 4]]: at index = 1 the test is 2 < 10, True, so it returns False even though the meetings are disjoint. The neighbour argument from step 3 is only valid once the starts are ascending; without the sort, "adjacent in the list" means nothing about "adjacent in time".

Overlap means strictly before the previous end. Equal endpoints are back-to-back, not double-booked.
STEP 9

Time and space

The sort is O(n log n). The scan visits each meeting once with O(1) work: O(n). The sort dominates, so the total is O(n log n) time. list.sort works in place, so beyond the sort's own internal buffer the algorithm allocates only a few indices: O(1) extra space.

ApproachTimeSpace
Check every pairO(n²)O(1)
Sort by start, scan neighboursO(n log n)O(1) extra

For 10,000 meetings that is roughly 130,000 comparison steps in the sort versus 50 million pair checks.

STEP 10

The final solution

Five lines, each one a step above.

  • intervals.sort(key=lambda interval: interval[0]) puts meetings in start order, which is what makes "check only the predecessor" valid.
  • for index in range(1, len(intervals)) starts at 1 because meeting 0 has nothing before it; an empty or one-element list skips the loop.
  • if intervals[index][0] < intervals[index - 1][1] asks whether this meeting starts strictly before the previous one ends.
  • return False the moment that is true; one conflict is enough.
  • return True if the loop finishes, since every adjacent pair, and therefore every pair, is clear.
One-line summary to remember: sort by start, then a meeting can only conflict with the one right before it, and only if it starts strictly before that one ends.
