Reverse Bits, narrated

Scroll through the string-reverse shortcut, the shift-and-append loop that must run exactly 32 times, and a byte-by-byte trace of the running example, with the low bits of input and output shown alongside.

Pattern used Bit Manipulation The first bit read from the input belongs at the far end of the output. Shift the output left, append the current low bit, and shift the input right.

STEP 1

The problem

You are given a 32-bit unsigned integer n. Reverse the order of its bits, so bit 0 becomes bit 31, bit 1 becomes bit 30, and so on, and return the resulting integer.

Running example: n = 0000 0010 1001 0100 0001 1110 1001 1100 (decimal 43261596). Read the bits back to front and you get 0011 1001 0111 1000 0010 1001 0100 0000, which is 964176192.

The width is fixed at 32 even when the number has leading zeros. That single fact drives the whole solution, and it is the thing the pitfall step comes back to. The panel tracks only the lowest 8 bits of n, 10011100, and the lowest 8 bits of result, because 32 columns do not fit; the reasoning is identical for the other three bytes.

STEP 2

First instinct: reverse a string

Python makes this a one-liner: render the number as a zero-padded 32-character binary string, reverse it, and parse it back.

return int(format(n, "032b")[::-1], 2)

It is correct, and the 032b padding even handles leading zeros. The panel shows the low byte 10011100 becoming 00111001 in the reversed string, which is what will end up as the top byte of the answer.

The cost is allocation: a 32-character string, a second reversed copy, and a parse. In a language without a slice-reverse idiom the same approach is a loop over characters, which is just the bit loop with extra steps. Interviewers ask this question to see the bit loop, and the string version does not demonstrate that you understand how the shifts move data.

STEP 3

The key insight: read low, write high

The first bit you read from the input, its bit 0, has to end up at bit 31 of the output. You do not have to place it there directly. Put it at bit 0 of result and then, on each of the 31 later rounds, shift result left by one. After 31 shifts it is sitting at bit 31.

So each round is three moves: shift result left to make room, drop n's current low bit into the empty slot, then shift n right so its next bit is in position 0. In code that is result = (result << 1) | (n & 1) followed by n >>= 1.

The bits leave n from the low end in order 0, 1, 2 … and enter result at its low end in that same order. Because every earlier bit gets pushed one place left on every later round, the order comes out reversed for free.
STEP 4

The approach: exactly 32 rounds

Start with result = 0. Then for _ in range(32): do the shift-append-shift from the previous step. After the loop, return result.

The loop bound is a fixed 32, not while n. The example input has five leading zeros (bits 31 down to 27 are 0), and those must become five trailing zeros in the output. Once n has been shifted down to 0 there are no more 1s to read, but result still needs to be shifted left for each remaining position. A loop that stops when n is empty would leave the answer too small by exactly that many shifts.

STEP 5

Trace it: rounds 1 to 3, the first 1 arrives

The low byte of n is 10011100, so reading from bit 0 upward the first bits are 0, 0, 1. Rounds 1 and 2 each compute (result << 1) | 0, which leaves result at 0, and shift n right; after them the low byte of n >> 2 is 10100111, as the panel shows.

Round 3 reads n & 1 = 1. result = (0 << 1) | 1 = 1, or 00000001. That single bit is the original bit 2 of the input, and it now has 29 more left-shifts ahead of it, which will carry it to bit 29 of the answer.

STEP 6

Trace it: rounds 4 to 8, the prefix grows

After round 3, n >>= 1 exposes the next bit; the panel shows the low byte of n >> 3 as 11010011, with result = 1 holding the reversed prefix so far.

Rounds 4 and 5 read 1, 1: result goes to 11 then 111. Rounds 6 and 7 read 0, 0: 1110 then 11100. Round 8 reads 1: 111001, which written as a byte is 00111001.

Read the original low byte 10011100 from its low end: 0, 0, 1, 1, 1, 0, 0, 1. Read the accumulated result 00111001 from its low end: 1, 0, 0, 1, 1, 1, 0, 0. Each is the other backwards, which is what eight rounds of shift-append should produce.

STEP 7

Trace it: the remaining 24 rounds and the answer

After 8 rounds the input's low byte is used up. The panel now shows the low byte of n >> 8, 00011110, which is the input's second byte, and result holding 00111001 (decimal 57).

Rounds 9 to 32 process the three remaining bytes of n the same way. Each of those 24 rounds shifts the existing 8 bits of result one place further left, so by the end they occupy bits 24 to 31 of the answer: the input's low byte, reversed, has become the output's top byte.

The final value is 0011 1001 0111 1000 0010 1001 0100 0000, and return result gives 964176192. The input's five leading zeros are the answer's five trailing zeros.

STEP 8

Where this goes wrong: stopping early, or shifting the wrong way

Looping while n: instead of 32 times. The panel shows n = 1. A while-n loop reads the single 1, appends it, shifts n to 0 and stops after one round, returning 1. The correct answer moves that bit to position 31, giving 2147483648 (10000000 in the top byte). Only a fixed 32-round loop keeps shifting result after n has run out of bits. Leading zeros of the input are real data.

Placing each bit at its own index. A tempting rewrite is result |= (n >> i & 1) << i for i in range(32). That reads bit i and writes it back to bit i, which reconstructs n exactly: the running example returns 43261596, its own input. If you want the direct-placement form, the target is << (31 - i); the shift-append form avoids having to get that subtraction right.

Test with n = 1 (expect 2147483648) and n = 0 (expect 0). The first catches any loop that stops early; the second confirms the loop is harmless on an empty input.
STEP 9

Time and space

The loop runs exactly 32 times regardless of the input, and each round is two shifts, one AND and one OR. That is O(1) time. The state is two integers, result and n, so O(1) space.

ApproachTimeSpace
Format, reverse string, parseO(32), three passesO(32) for two strings
Shift-append loopO(32), one pass, no allocationO(1)

Both are constant because the width is fixed. If the function is called millions of times, the follow-up in the original problem, the loop's lack of allocation matters, and a byte-wise lookup table (reverse each of the four bytes via a 256-entry table and swap their order) cuts the 32 rounds to 4.

STEP 10

The final solution

Five lines of body.

  • result = 0 — an empty output with room for 32 bits.
  • for _ in range(32): runs a fixed number of rounds, one per output bit, and does not care whether n still has 1s.
  • result << 1 pushes everything already collected one place left, making room at bit 0.
  • | (n & 1) drops the input's current lowest bit into that room.
  • n >>= 1 discards the bit just consumed so the next one is in position 0.
  • return result — after 32 rounds the first bit read has been shifted 31 times and sits at the top.
One-line summary to remember: 32 times, shift the result left, append the input's low bit, shift the input right.
