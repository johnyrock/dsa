Easy · Binary Search · LeetCode #704

Binary Search, narrated

Scroll through the thinking, from the linear scan to the loop that throws away half the array per comparison, with the state of the algorithm shown alongside.

STEP 1

The problem

You get an array of integers nums, already sorted in ascending order, and an integer target. Return the index where target sits, or -1 if it is not in the array.

Two details matter: the values are distinct, so there is at most one right answer, and the array is sorted, which is the only reason this problem is interesting.

Running example: nums = [-1, 0, 3, 5, 9, 12], target = 9. The answer is 4 because nums[4] == 9.

The question asks for the index, not whether the value is present. So whatever we do, we have to keep track of where we are looking.

STEP 2

First instinct: walk the array

The most direct idea is to look at every element from left to right and stop when one equals the target.

for i, n in enumerate(nums):    if n == target:        return ireturn -1

This is correct and takes about ten seconds to write. But it looks at every element in the worst case, so the running time is O(n). At n = 10,000 that is up to ten thousand comparisons, and the problem explicitly asks for better.

Notice what this loop ignores: it never uses the fact that the array is sorted. It treats [-1, 0, 3, 5, 9, 12] exactly the same as a shuffled bag of the same numbers. That is the waste.

STEP 3

Reframe: what does one comparison buy?

In an unsorted array, comparing one element with the target tells you about that element and nothing else. One comparison, one element ruled out.

In a sorted array the same comparison says much more. Look at the middle element, nums[2] = 3. It is smaller than 9. Because the array ascends, everything to the left of it is also smaller than 9.

One comparison in the middle rules out three cells at once: indices 0, 1 and 2 are all too small to be 9.

So the reframed question is not "is this the target?" but "which half is the target in?". Sorted means one comparison throws away half the array.

STEP 4

The key idea: shrink a window

Keep two indices, lo and hi, marking the slice of the array that could still contain the target. Start with the whole thing: lo = 0, hi = len(nums) - 1. Then repeat:

  • mid = (lo + hi) // 2 is the middle of the current window.
  • If nums[mid] == target, return mid. Done.
  • If nums[mid] < target, the target is to the right, so lo = mid + 1.
  • Otherwise the target is to the left, so hi = mid - 1.

Two pieces of that are worth saying out loud. First, the loop condition is while lo <= hi, not <. Since hi is a real index rather than one past the end, lo == hi means the window still holds exactly one unchecked candidate, and it deserves a look.

Second, the moves are mid + 1 and mid - 1, never plain mid. We already compared nums[mid] and it was not the answer, so excluding it is safe — and it is what guarantees the window gets strictly smaller every pass, which is why the loop terminates.

STEP 5

Trace it: first probe

The window starts as the whole array: lo = 0, hi = 5. The middle is mid = (0 + 5) // 2 = 2. Integer division floors, so with six cells mid leans left.

nums[2] = 3. That is not 9, and it is less than 9, so 9 must live to the right of index 2 if it exists at all.

We move lo = mid + 1 = 3. Indices 0, 1 and 2 are gone for good — three cells eliminated by one comparison.

STEP 6

Trace it: the window has halved

The live window is now nums[3 .. 5], which is [5, 9, 12]. Three candidates left out of six.

The condition lo <= hi holds (3 ≤ 5), so we go round again and recompute the middle of the new window: mid = (3 + 5) // 2 = 4.

mid is always recomputed from the current lo and hi. It is not a pointer that walks; it is derived state.
STEP 7

Trace it: found

nums[4] = 9, which equals the target. We return mid, so the answer is 4.

Two comparisons on a six-element array. The linear scan would have taken five. The gap widens fast: at a thousand elements it is about ten comparisons instead of a thousand.

We never looked at indices 0, 1, 3 or 5. They were eliminated in bulk, not one at a time.
STEP 8

When the target is not there

Now run the same array with target = 2, which is missing. The window shrinks the same way, it just never lands on a match:

  • lo = 0, hi = 5, mid = 2: nums[2] = 3 > 2, so hi = 1.
  • lo = 0, hi = 1, mid = 0: nums[0] = -1 < 2, so lo = 1.
  • lo = 1, hi = 1, mid = 1: nums[1] = 0 < 2, so lo = 2.

Now lo = 2 is greater than hi = 1. The window is empty, the loop condition fails, and we fall out to return -1. lo crossing hi is the proof of absence.

This is where while lo < hi bites. Look at the third bullet: the window was one cell wide, lo == hi == 1. With < the loop would have exited right there and never checked index 1. Search that same array for target = 0 and the buggy version returns -1 even though nums[1] is 0.

The rule: hi is an inclusive index, so the comparison must be inclusive too.

STEP 9

Time and space

Every iteration does a constant amount of work and cuts the window roughly in half: 6 → 3 → 1 → 0. The number of halvings it takes to get from n down to nothing is log₂ n, so the total is O(log n) time.

Nothing is allocated. Three integers, lo, hi and mid, hold all the state, so it is O(1) extra space.

ApproachTimeSpace
Linear scanO(n)O(1)
Binary search, iterativeO(log n)O(1)
Binary search, recursiveO(log n)O(log n) call stack

Unlike the usual trade of memory for speed, this one is free: the sorted input was already paid for, and reading it cleverly costs nothing extra.

STEP 10

The final solution

Eleven lines. Every one of them maps to a step above.

  • lo, hi = 0, len(nums) - 1 opens the window on the whole array, with hi an index that exists.
  • while lo <= hi keeps going while at least one candidate is unchecked.
  • mid = (lo + hi) // 2 is the probe, recomputed from the current window each pass.
  • return mid is the only early exit, checked before either move.
  • lo = mid + 1 and hi = mid - 1 discard the impossible half, excluding mid so the window always shrinks.
  • return -1 is what falling out of the loop means: lo crossed hi, the window is empty.
One-line summary to remember: sorted means one comparison throws away half the array, so keep halving the window until it is empty.
