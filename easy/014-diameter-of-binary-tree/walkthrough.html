Easy · Tree · LeetCode #543

Diameter of Binary Tree, narrated

Scroll from recomputing heights at every node to a single post-order pass that tracks the best left-plus-right sum, with each node's height shown alongside.

Pattern used Tree The longest path may turn at any node. Child heights tell us the length of the path that turns through that node.

STEP 1

The problem

Given the root of a binary tree, return the length of its diameter: the longest path between any two nodes, measured in edges. The path may or may not pass through the root, and it never reuses a node.

Running example: root = [1,2,3,4,5] in level order. Node 1 has children 2 and 3; node 2 has children 4 and 5. The answer is 3: the path 4 → 2 → 1 → 3 has 3 edges (and 4 nodes).

Two things to fix in your head before writing code. First, the unit is edges, so a single node has diameter 0 and a two-node tree has diameter 1. Second, the longest path here happens to go through the root, but it does not have to: in a tree whose left subtree is huge and right subtree is a single node, the longest path may live entirely inside the left subtree.

STEP 2

First instinct: at every node, measure both arms from scratch

Any path has a topmost node where it turns. At that node the path goes down some distance on the left and some distance on the right, so its length is height(node.left) + height(node.right), where height counts the nodes on the longest downward chain. So: for every node, compute both child heights with a plain height helper, add them, and keep the maximum.

def height(node):    if node is None:        return 0    return 1 + max(height(node.left), height(node.right))

This is correct, and the "turn at some node" idea in it is the real insight. The cost is that height is recomputed for every ancestor. On the running example node 1 walks its entire left subtree to learn its height, and then node 2 walks the very same nodes again; the panel's h? badges on 4 and 5 are those repeated visits. On a chain the node at depth k re-walks everything below it, and the total is O(n²).

STEP 3

The key insight: the height walk already knows both arms

Look at what the height helper does at node 2. It calls itself on 4 and on 5, gets h=1 from each, and returns 1 + max(1, 1). At that exact moment it holds both child heights in its hands, and the path that turns at 2 is 1 + 1 = 2 edges, from 4 up to 2 and down to 5.

So do not throw those two numbers away. While computing the height, also compute left_height + right_height at every node and remember the largest one seen. That is the highlighted line: diameter = max(diameter, left_height + right_height).

Two different quantities move through the recursion and it helps to name them. The height flows upward as the return value and counts nodes on the longest downward chain. The through-path is a side effect, counted in edges, and never goes up; it only updates a shared best.

STEP 4

The approach: one post-order pass with a shared best

Set diameter = 0 in the outer function, then define a nested height that declares nonlocal diameter so it can update it. At every node:

  • left_height = height(node.left) — the left arm, computed once.
  • right_height = height(node.right) — the right arm, computed once.
  • diameter = max(diameter, left_height + right_height) — the path that turns here, kept if it beats the best so far.
  • return 1 + max(left_height, right_height) — this node's height, for its parent.

The panel shows the walk about to begin: diameter = 0, the root at node = 1, and its two children still marked ? because post-order means the root answers last. Each node computes its height exactly once and its through-path exactly once.

STEP 5

Trace it: leaf 4

The recursion goes left first, down to node 4. Its two children are None, so left_height = 0 and right_height = 0.

The through-path at 4 is 0 + 0 = 0 edges, a path consisting of just node 4, and diameter = max(0, 0 + 0) = 0 leaves the best unchanged. Node 4 then returns its height, 1 + max(0, 0) = 1, shown as the badge h=1.

Leaf 5 goes through exactly the same computation next: height 1, diameter still 0. Leaves never change the diameter, because a leaf has no arms.

STEP 6

Trace it: node 2

Node 2 now has both answers: left = 1 from node 4 and right = 1 from node 5. The path that turns at 2 goes down one edge to 4 and one edge to 5, so it is 1 + 1 = 2 edges long.

diameter = max(0, 1 + 1) = 2. The best path so far is 4 → 2 → 5, and the panel highlights those three nodes.

Then node 2 returns its height for its parent: 1 + max(1, 1) = 2. Note the two numbers are different things that happen to be equal here: 2 edges through, 2 nodes down.

STEP 7

Trace it: the root, and the answer

Node 3 is a leaf on the right, so it returns height 1 and leaves the diameter alone. The root now has left = 2 from node 2 and right = 1 from node 3.

The path turning at the root is 2 + 1 = 3 edges: 4 → 2 → 1 → 3. diameter = max(2, 2 + 1) = 3, a new best. The root returns its own height, 1 + max(2, 1) = 3, but that return value is discarded: height(root) is called for its side effect, and the outer function returns diameter.

The answer is 3. Root height also happens to be 3 in this example, which is a coincidence. Keep the two apart: the answer is the best through-path, not the height.
STEP 8

Where this goes wrong: nodes versus edges

Adding one to the through-path. The height line is 1 + max(...), and it is tempting to mirror it: diameter = max(diameter, left_height + right_height + 1). That counts the turning node as well, which gives the number of nodes on the path. At the root it computes 2 + 1 + 1 = 4, the panel's 2+1+1 badge, and the function returns 4 instead of 3. Four nodes, three edges; the problem asks for edges.

Returning the height instead of the diameter. Ending with return height(root) returns 3 on this example, which is correct by accident, since the root's height and the diameter coincide here. On a tree whose longest path does not pass through the root, or on any lopsided tree, the height is a different number. The last line must be height(root) followed by return diameter.

Forgetting nonlocal diameter. Without it, the assignment diameter = max(...) inside height creates a new local variable, and Python raises UnboundLocalError on the read side of that same line, because diameter is now local but not yet assigned. The outer variable would never be updated.

Sanity-check with two nodes: [1,2] must give 1. If you get 2, you are counting nodes.
STEP 9

Time and space

Each node is entered by height exactly once and does constant work of its own: one addition, two max calls. So the time is O(n). The five h= badges in the panel are the five heights, each computed once and reused by the parent.

The extra memory is the recursion stack, which is as deep as the tree is tall: O(h). That is about log n for a balanced tree and n for a chain.

ApproachTimeSpace
Height helper called at every nodeO(n²) on a chain, O(n log n) when balancedO(h) call stack
One post-order pass, shared bestO(n)O(h) call stack

The improvement is purely from not recomputing: the brute force and the final solution do the same additions at each node; the final solution just gets the child heights from the recursion instead of from a fresh walk.

STEP 10

The final solution

A nested height function with one side effect. Line by line:

  • diameter = 0 — the best through-path seen so far; a single node has diameter 0.
  • def height(node): with nonlocal diameter — the helper returns heights and is allowed to update the outer best.
  • if node is None: return 0 — an empty subtree has no nodes on its longest chain.
  • left_height = height(node.left) and right_height = height(node.right) — post-order: both arms first, each computed once.
  • diameter = max(diameter, left_height + right_height) — the path that turns at this node, in edges; keep it if it is the longest yet.
  • return 1 + max(left_height, right_height) — this node's height, in nodes, for its parent.
  • height(root) then return diameter — run the walk for its side effect and return the best, not the height.
One-line summary to remember: the longest path turns at some node, and there its length is left height plus right height, so track that sum while computing heights.
