Merge Two Sorted Lists, narrated

Scroll through the thinking, from dumping the values into a Python list and sorting to the one-pass merge with a dummy head, with the state of both lists shown alongside.

STEP 1

The problem

You get the heads of two singly linked lists, list1 and list2. Each one is already sorted in non-decreasing order. Return the head of one sorted list containing all the nodes.

The nodes already exist. The job is to relink them into a single chain, not to build a new one.

Running example: list1 = 1 → 2 → 4 and list2 = 1 → 3 → 4. The answer is 1 → 1 → 2 → 3 → 4 → 4.

A linked list gives you only one move: from a node, follow .next. There is no indexing and no looking backwards, so any solution has to work by walking forwards.

STEP 2

First instinct: collect, sort, rebuild

The direct idea is to walk both lists, push every value into a Python list, sort it, then build a fresh chain of nodes from the sorted values.

values = []for head in (list1, list2):    while head:        values.append(head.val)        head = head.nextvalues.sort()# then rebuild a node for every value

This works, and it is a fine thing to say out loud. But the sort costs O((n + m) log(n + m)), and the values list plus the new nodes cost O(n + m) extra space.

Something is being thrown away here. The sort treats the input as an unordered pile of numbers. What did we already know about it?

STEP 3

Reframe: the inputs are already sorted

Both lists arrive sorted. Inside list1, nothing after the head is smaller than the head. The same holds for list2.

So the smallest value in the whole merge is not hiding somewhere in the middle. It is either list1's head or list2's head, and one comparison tells you which.

The next smallest node is always at one of the two heads. Take it, advance that list, and the same statement is true again.

That is the whole algorithm. No sort, and no need to look at a node more than once.

STEP 4

The key idea: a dummy head and a tail pointer

Repeatedly taking the smaller head means appending to the end of a growing result. To append in O(1) we keep tail, a pointer to the last node attached so far.

But the very first append has no last node to attach to, so a naive version needs a special case: "if the result is empty, set head, otherwise set tail.next." That branch is where off-by-one bugs live.

  • The trick: start with a throwaway node, dummy, and set tail = dummy.
  • Now the result is never empty, so every append is the same line: tail.next = node.
  • At the end the real head is dummy.next, and the dummy is discarded.
The dummy buys uniformity: one code path instead of a first-node case and an every-other-node case.
STEP 5

Trace it: first comparison

Both heads are 1. The test is list1.val <= list2.val, so 1 ≤ 1 is true and we take from list1.

tail.next = list1 hangs that node off the dummy, list1 = list1.next steps past it, and tail = tail.next moves the tail onto it.

Using <= rather than < means ties go to list1, which keeps equal values in their original relative order. The merge is stable.
STEP 6

Trace it: second comparison

Now the heads are 2 from list1 and 1 from list2. This time 2 ≤ 1 is false, so the else branch runs and we take from list2.

The merged chain is 1 → 1, and list2 has advanced to 3.

Nothing about the loop body changed. Only which of the two pointers moved.

STEP 7

Trace it: third comparison

Heads are 2 and 3. 2 ≤ 3, so list1 gives up its node again and the merged chain becomes 1 → 1 → 2.

Carry on the same way: 4 versus 3 takes the 3, then 4 versus 4 takes list1's 4 and empties list1. The loop condition while list1 and list2 is now false and the loop stops.

At that moment list2 still points at a 4. Which is exactly the case the next step is about.

STEP 8

The pitfall: the leftover tail

The loop exits as soon as either list runs out, so it almost always leaves nodes behind in the other one. On the running example that is a lone 4 in list2.

Stopping there returns 1 → 1 → 2 → 3 → 4 and silently drops the last node. The fix is one line after the loop:

tail.next = list1 or list2
The leftover is already sorted and every value in it is at least as large as everything merged so far, so one link attaches the whole remainder. No loop needed.

The same line handles the empty-input cases for free. If list1 is None the loop never runs, tail is still the dummy, and tail.next = list2 makes the answer just list2. If both are None it sets None and dummy.next is None.

STEP 9

Time and space

Every iteration of the loop consumes exactly one node and never revisits it, so the loop runs at most n + m times with O(1) work inside. The final attachment is a single assignment. That is O(n + m) time.

The only new object is the dummy node, and the nodes themselves are spliced in place rather than copied, so the extra space is O(1).

ApproachTimeSpace
Collect values, sort, rebuildO((n + m) log(n + m))O(n + m)
Two pointers with a dummy headO(n + m)O(1)

Sorting cannot beat this, because the sorted order was information we were handed for free.

STEP 10

The final solution

Thirteen lines, and every one of them maps to a step above.

  • dummy = ListNode() and tail = dummy set up the append-without-a-special-case trick.
  • while list1 and list2 runs only while there is an actual comparison to make.
  • if list1.val <= list2.val is the reframed question: which head is the next smallest?
  • tail.next = … then list1 = list1.next splices one node out and onto the result.
  • tail = tail.next keeps the tail pointing at the real end. Forget it and the next append overwrites this one.
  • tail.next = list1 or list2 attaches the leftover, and covers both empty-input cases.
  • return dummy.next skips the placeholder and returns the real head.
One-line summary to remember: both lists are sorted, so the next node is always the smaller head; a dummy makes every append look the same.
