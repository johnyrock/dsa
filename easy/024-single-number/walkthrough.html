Easy · Bit Manipulation · LeetCode #136

Single Number, narrated

I’ll start by searching for each value’s partner, then use XOR to cancel every pair in one pass.

Pattern used Bit Manipulation XOR is associative, and x ^ x is zero. Every duplicated value cancels regardless of order, leaving the sole unpaired number.

STEP 1

The problem

You are given a non-empty array nums in which every value appears exactly twice, except for one value that appears once. Find that value. The problem asks for linear time and, crucially, constant extra space.

Running example: nums = [4,1,2,1,2]. The two 1s are a pair, the two 2s are a pair, and 4 is alone. The answer is 4.

The panel shows each value as an 8-bit pattern: 4 is 00000100, 1 is 00000001, 2 is 00000010. Keep the bit view in mind, because the trick that satisfies the space constraint lives at the bit level.

STEP 2

First instinct: look for each value's partner

My first instinct is to take each value in turn and scan the rest of the array for a second copy. If I find none, that value is the answer.

for i, candidate in enumerate(nums):    if all(nums[j] != candidate for j in range(len(nums)) if j != i):        return candidate

This baseline scans the array for each candidate, so it takes O(n²) time and uses O(1) extra space.

I only need pairs to cancel, not to be located. XOR removes equal pairs without storing a set or sorting the array.

STEP 3

The key insight: XOR cancels pairs

Bitwise XOR (^) has three properties that together solve this problem:

  • x ^ x == 0 — XORing a value with itself gives zero.
  • x ^ 0 == x — zero is the identity.
  • XOR is associative and commutative, so the order of operands does not matter.

I look at the panel. Starting from 4 (00000100), XORing in a 1 turns bit 0 on: 4 ^ 1 = 5 (00000101). XORing in the second 1 turns bit 0 back off: 5 ^ 1 = 4. The pair of 1s has vanished, and it did not matter that 4 was sitting in between.

XOR every element of the array together. Because order does not matter, every pair cancels to 0 no matter how far apart the two copies sit, and the lone value is the only thing that survives.
STEP 4

The approach: one accumulator

Initialise unique = 0, the XOR identity, so the first value folds in unchanged. Then for number in nums: do unique ^= number. That is the whole loop. When it finishes, unique holds whatever failed to cancel.

There is no set, no sort, no second pass. The only state is a single integer, shown in the panel as unique = 0 (00000000) before the loop starts.

STEP 5

Trace it: 4, then 1

The first value is 4. 0 ^ 4 = 4, which sets bit 2 in the accumulator: unique = 4 (00000100).

The second value is number = 1. 4 ^ 1 = 5: bit 0 turns on and bit 2 stays. unique = 5 (00000101).

Two values have been folded in and neither has met its partner yet, so both are visible in the accumulator. That is what the state of unique means at any moment: the XOR of every value seen so far, which is the same as the XOR of every value seen an odd number of times so far.

STEP 6

Trace it: the first pair cancels

Index 2 folds in the first 2: 5 ^ 2 = 7, or 00000111 — three unpaired values, three bits set.

Index 3 brings the second 1. 7 ^ 1 = 6, or 00000110. Bit 0 flipped back off; the two 1s have cancelled even though a 2 arrived between them. I can verify that 6 == 4 ^ 2, exactly the XOR of the values still unpaired: the 4 and the first 2.

The panel's current pointer is on index 3 and the accumulator shows unique = 6 (00000110).

STEP 7

Trace it: the last pair cancels, 4 remains

Index 4 brings the second 2. 6 ^ 2 = 4, or 00000100. Bit 1 flips off and only bit 2 is left, which is the 4 from the very first step.

The loop is over and return unique gives 4. Every duplicated value flipped its bits twice, which is the same as not flipping them at all; 4 flipped its bit once and survives.

Whole computation: 4 ^ 1 ^ 2 ^ 1 ^ 2 = 4. Five XORs, one integer of state.
STEP 8

Where this goes wrong: the wrong operator or the wrong seed

Using addition instead of XOR. The panel makes the difference concrete: 1 + 1 = 2, but 1 ^ 1 = 0. Addition doubles a pair and carries the result into the next bit; it never cancels anything. With unique += number the running example returns 10, the sum of all five values, not 4. The cancellation identity belongs specifically to XOR.

Seeding with the first element and then looping over everything. Writing unique = nums[0] and then for number in nums: folds nums[0] in twice. For [4,1,2,1,2] that computes 4 ^ 4 ^ 1 ^ 2 ^ 1 ^ 2 = 0: the 4 cancels itself and the function returns 0. Either seed with 0 and loop over all of nums, or seed with nums[0] and loop over nums[1:]. Never both.

A one-element array like [7] is the quickest check for both bugs: the correct code returns 7 immediately, the add version returns 7 too (so it is not sufficient), but the double-seed version returns 0.
STEP 9

Time and space

Each number is XORed into the accumulator exactly once, so O(n) time. No structure grows with the input; the only state is one integer, so O(1) space.

ApproachTimeSpace
Scan for each value's partnerO(n²)O(1)
Sort, then find the unpaired valueO(n log n)O(1) to O(n) depending on the sort
Hash set, add on first sight, remove on secondO(n)O(n)
XOR accumulatorO(n)O(1)

The set already reaches linear time. XOR is the only option that also meets the constant-space requirement, and it does it with less code than any of the others.

STEP 10

The final solution

Four lines of body.

  • unique = 0 seeds the accumulator with the XOR identity, so the first value folds in unchanged.
  • for number in nums: visits every value once, in whatever order the array has; order does not matter to XOR.
  • unique ^= number flips the bits of number in the accumulator. A value seen twice flips them twice and leaves no trace.
  • return unique — after the last iteration, the only bits still set belong to the value that appeared once.
One-line summary to remember: XOR everything together; pairs cancel to zero regardless of order, and the single number is what is left.
