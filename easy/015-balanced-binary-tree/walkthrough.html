Balanced Binary Tree, narrated

Scroll from the O(n²) height-at-every-node check to a single post-order pass that returns -1 as an imbalance sentinel, with each node's returned height shown alongside.

Pattern used Tree A tree is balanced only when every node's child heights differ by at most one. Return a height, but use -1 to carry an unbalanced result upward.

STEP 1

The problem

Given the root of a binary tree, decide whether it is height-balanced: at every node, the height of the left subtree and the height of the right subtree differ by at most 1. The height of an empty subtree is 0, and a leaf has height 1.

Running example: root = [3,9,20,null,null,15,7] in level order. Node 3 has children 9 and 20; node 20 has children 15 and 7. The answer is true.

The word "every" is what makes this problem interesting. It is not enough to compare the two subtrees under the root; a tree can look balanced at the top and still hide a lopsided subtree three levels down. The answer is a single boolean, but earning it means checking the gap at each of the n nodes.

The README's second example, [1,2,2,3,3,null,null,4,4], is the counterexample: its left arm is two levels deeper than its right arm, so the answer there is false. We will come back to it in the pitfalls step.

STEP 2

First instinct: a height function plus a check at every node

Write the definition straight into code. First a helper that computes the height of a subtree:

def height(node):    if node is None:        return 0    return 1 + max(height(node.left), height(node.right))

Then a second recursive function that, at each node, computes abs(height(node.left) - height(node.right)), rejects if it is greater than 1, and otherwise recurses into both children to check them too.

This is correct, and it is the version most people write first. The problem is that height is called from scratch at every node. On the running example the root calls height on the whole 20-subtree, and then when the check moves down to node 20, it walks that same subtree again. The panel's h? badges on 9 and 20 mark those two full height walks the root alone triggers.

On a bushy tree the repeated work is tolerable, but on a chain (every node has only one child) the node at depth k re-walks the n - k nodes below it, and the total is 1 + 2 + … + n, which is O(n²). With up to 5000 nodes, that is around 12 million visits for a job that needs 5000.

STEP 3

The key insight: one return value can carry two facts

The waste in the brute force comes from separating two questions that are answered by the same walk. Computing a node's height already visits both children; the balance check at that node needs exactly the two numbers that walk produces. So compute them once, and let the height function report imbalance as well.

Heights are never negative, so -1 is free to mean "something below here is unbalanced". height returns a real height (0 or more) when the subtree is balanced, and the sentinel -1 the moment it is not.

The panel shows the two possible outcomes for the root: a normal height, or -1. The highlighted lines are the decision: if right_height == -1 or abs(left_height - right_height) > 1: return -1, and otherwise return 1 + max(left_height, right_height).

Once a -1 appears anywhere, every ancestor sees it and passes it up without doing any more work, so the final answer at the top is just height(root) != -1.

STEP 4

The approach: post-order, bail out early

The recursion is post-order: a node's own result is computed after both children have reported. At node 3 the panel shows left = ? and right = ?, because nothing is known until the calls return.

  • left_height = height(node.left) — recurse into the left child first.
  • if left_height == -1: return -1 — if the left subtree is already unbalanced, do not bother walking the right one.
  • right_height = height(node.right) — otherwise recurse into the right child.
  • if right_height == -1 or abs(left_height - right_height) > 1: return -1 — reject if the right side is unbalanced, or if this node's own gap is 2 or more.
  • return 1 + max(left_height, right_height) — this node is fine; report its height like any ordinary height function.

Every parent receives each child's height exactly once, so every node is visited exactly once. The early return after the left call is what turns an unbalanced left subtree into a genuine short-circuit rather than just a flag.

STEP 5

Trace it: the leaves

Start at the root, node 3. It calls height(node.left), which is node 9. Node 9 in turn calls height on its left child, which is None, and gets 0 back from the base case; the same happens on the right. So at node 9, left = 0, right = 0, the gap abs(0 - 0) is 0, and it returns 1 + max(0, 0) = 1.

The panel marks that with →1 next to node 9, and draws the ghost 0 below it to show where the base-case value came from. Leaves 15 and 7 go through exactly the same steps later in the walk and each return height 1, which is why they carry →1 badges too.

Back at the root, left_height is now 1. It is not -1, so the root proceeds to right_height = height(node.right) and the walk moves to node 20.

STEP 6

Trace it: node 20

Node 20 calls height on 15, gets 1, checks that it is not -1, then calls height on 7 and gets 1. So left = 1, right = 1, and abs(1 - 1) = 0.

Neither child returned the sentinel and the gap is within 1, so the rejection line does not fire. Node 20 returns 1 + max(1, 1) = 2: the badge →2 in the panel.

This is the normal case. A balanced node behaves exactly like a plain height function; the sentinel logic only costs two comparisons and never changes the value flowing upward.

STEP 7

Trace it: the root, and the answer

The root now has both numbers: left = 1 from node 9 and right = 2 from node 20. The gap is abs(1 - 2) = 1. The check is > 1, and 1 is not greater than 1, so a gap of exactly one is allowed.

The root returns 1 + max(1, 2) = 3, which is the height of the whole tree. The outer function then evaluates height(root) != -1: 3 != -1 is true, and that is the answer.

Five nodes, five calls to height (plus the trivial None base cases). The brute force would have called its height helper on the 20-subtree twice, visiting leaves 15 and 7 once from the root and again from node 20.
STEP 8

Where this goes wrong

The panel switches to the README's second example, [1,2,2,3,3,null,null,4,4]. The two 4s hang below the left-hand 3s and are not drawn, but they are why the left 2 has height 3 while the right 2 has height 1. Only the root has a gap of 2; every other node in that tree is individually balanced.

Checking the gap only at the root. Writing abs(height(root.left) - height(root.right)) <= 1 and returning happens to give the right answer here (3 − 1 = 2, so false), which is what makes it dangerous: it passes this test and fails any tree whose imbalance sits below a root with two equally tall arms. The check must run at every node, which is why it lives inside the recursive height rather than in is_balanced.

Dropping the gap test from the sentinel version. If the rejection line is shortened to if right_height == -1: return -1, no node ever produces a -1 in the first place. The root computes 1 + max(3, 1) = 4, 4 != -1 is true, and the function returns true for a tree that is plainly unbalanced. Both halves of that or are needed: one forwards a child's verdict, the other makes this node's own verdict.

Forgetting to forward the sentinel. Skip the if left_height == -1: return -1 guard and a -1 from below gets fed into abs(-1 - 0) = 1, which passes, and then into 1 + max(-1, 0) = 1, which looks like a perfectly healthy leaf. The imbalance is laundered into a valid height and the final answer is wrongly true.

And the brute force from step 2 is not wrong, only slow: recomputing heights at every node still returns false here, but on a 5000-node chain it does roughly 12 million node visits where the sentinel version does 5000.
STEP 9

Time and space

Each node is entered by height exactly once and does constant work of its own (two comparisons, an abs, a max), so the time is O(n). The badges in the panel are the five heights computed for the five nodes, each computed once.

The only extra memory is the recursion stack, which is as deep as the tree is tall: O(h). For a balanced tree that is about log n; for a chain it degrades to n, and Python's default recursion limit of 1000 is worth remembering for chains near the 5000-node constraint.

ApproachTimeSpace
Height helper + check at every nodeO(n²) on a chain, O(n log n) when balancedO(h) call stack
Height with -1 sentinelO(n)O(h) call stack

The sentinel also short-circuits: once a -1 is found, every remaining ancestor returns immediately and any unvisited right subtrees on the path are never walked at all.

STEP 10

The final solution

One nested helper and one comparison. Line by line:

  • def height(node): — a height function that doubles as the balance checker, via its return value.
  • if node is None: return 0 — an empty subtree has height 0 and is trivially balanced.
  • left_height = height(node.left) — post-order: ask the left child first.
  • if left_height == -1: return -1 — forward an unbalanced verdict immediately, without touching the right side.
  • right_height = height(node.right) — now ask the right child.
  • if right_height == -1 or abs(left_height - right_height) > 1: return -1 — reject if the right side is unbalanced, or if this node's own gap is 2 or more.
  • return 1 + max(left_height, right_height) — otherwise this node is balanced; report its real height.
  • return height(root) != -1 — the tree is balanced exactly when the root's result is a real height.
One-line summary to remember: compute heights bottom-up, and return −1 instead of a height the moment any node's children differ by more than one.
