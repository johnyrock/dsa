Easy · Dynamic Programming · LeetCode #70

Climbing Stairs, narrated

Scroll through the thinking, from the exponential recursion to a loop with two variables, with the state of the algorithm shown alongside.

Pattern used Dynamic Programming f(n) = f(n-1) + f(n-2), Fibonacci with two variables

STEP 1

The problem

A staircase has n steps. Every move takes you up either 1 step or 2 steps. Count the distinct sequences of moves that land exactly on the top.

Order matters: climbing 1 then 2 is a different climb from 2 then 1, even though both cover 3 stairs.

Running example: n = 5. The answer is 8. Listing them by hand is possible but tedious, which is a hint that we want a formula rather than an enumeration.

Notice we are asked for a count, not for the sequences themselves. We never have to build a climb — only add up how many exist.

STEP 2

First instinct: recursion

Think about the very last move you make. It was either a 1-step or a 2-step. If it was a 1-step, you were standing on step n - 1 before it; if it was a 2-step, you were on step n - 2. There is no third option.

So the number of climbs splits cleanly in two, and we can write it down directly:

def climb_stairs(n):    if n <= 2:        return n    return climb_stairs(n - 1) + climb_stairs(n - 2)

This is correct, and it is a good thing to say out loud in an interview. It is also unusably slow. Each call spawns two more calls, so the call tree roughly doubles at every level: O(2ⁿ).

The waste is easy to name. climb_stairs(5) calls climb_stairs(4) and climb_stairs(3) — and climb_stairs(4) calls climb_stairs(3) all over again, from scratch. The same subproblems are recomputed thousands of times. At n = 45 this never finishes.

STEP 3

Reframe: how much does step n actually depend on?

The recurrence f(n) = f(n-1) + f(n-2) is right. The recursion is just a bad way to evaluate it, because it walks down from n and rediscovers the bottom of the staircase over and over.

So ask the narrower question: "To compute the answer for step n, what do I actually need in hand?"

Exactly two numbers: the count for step n - 1 and the count for step n - 2. Nothing below them ever matters again.

One fix is memoization: keep the same recursion but cache each f(k) in a dict the first time it is computed. Every subproblem is then solved once, which drops the time to O(n) — but it still holds n cached values and an n-deep call stack.

If we only ever need the last two counts, though, we do not need the cache at all. We can start at the bottom and walk up.

STEP 4

The key idea: build upward with two variables

Start from what we can count on our fingers. Step 1 has 1 way (a single 1-step). Step 2 has 2 ways (1+1, or one 2-step). Those are the base cases, and they are the seed of everything above.

Hold them in two variables:

  • two_back — the count for the step two below the one we are computing.
  • one_back — the count for the step directly below it.

Then for each step from 3 up to n, the new count is two_back + one_back, and both variables shift up one: the old one_back becomes the new two_back.

Look at the counts as they appear: 1, 2, 3, 5, 8, 13 … This is the Fibonacci sequence, shifted by one position. ways(n) = Fib(n + 1). Recognising that is a nice sanity check, but the reasoning above is what you should be able to rebuild.
STEP 5

Trace it: step 3

We enter the loop with two_back = 1 (step 1) and one_back = 2 (step 2).

The count for step 3 is 2 + 1 = 3. Check it by hand: 1+1+1, 1+2, 2+1. Three climbs, as promised.

Now slide the window. two_back becomes 2 (step 2) and one_back becomes 3 (step 3). The value for step 1 is dropped, and we will never want it again.

STEP 6

Trace it: step 4

Same move, one stair higher. The count for step 4 is 3 + 2 = 5.

Slide again: two_back = 3, one_back = 5.

Notice what the panel is not doing. The dimmed cells are drawn so you can see the shape of the table, but the code never allocated an array. Only two integers exist at any moment.

STEP 7

Trace it: step 5, the answer

The count for step 5 is 5 + 3 = 8. That was the last iteration, because the loop runs up to and including n.

When the loop exits, one_back holds the count for step n. That is what we return.

The exponential recursion made thousands of calls to reach this number. The loop made three additions.
STEP 8

Where this goes wrong: base cases and the loop bounds

Two specific bugs live here, and both pass a casual eyeball.

Dropping the base-case guard. Without if n <= 2: return n, call it with n = 1. The loop range(3, 2) is empty, so nothing runs, and the function returns the seeded one_back = 2. But there is only 1 way to climb a single stair. The seed values are answers for steps 1 and 2, so those two inputs must be handled before the loop, not by it.

Starting the loop at the wrong index. Write range(2, n + 1) instead of range(3, n + 1) and the loop runs one extra time. For n = 5 it computes step 6 and returns 13 instead of 8 — a plausible-looking number from the same sequence, which is what makes it nasty.

The seeds already cover steps 1 and 2, so the loop's job starts at step 3. Count the iterations for n = 3: it should run exactly once.
STEP 9

Time and space

The loop runs from 3 to n, doing one addition and one rebinding each time. That is O(n) time. It keeps two integers regardless of how large n gets, so O(1) space.

ApproachTimeSpace
Plain recursionO(2ⁿ)O(n) call stack
Recursion + memoizationO(n)O(n) cache + stack
Bottom-up, two variablesO(n)O(1)

Memoization already fixes the disastrous part — the repeated subproblems. Going bottom-up buys the last improvement, the space, by noticing that a full dp table stores n values when only two are ever read.

STEP 10

The final solution

Six lines. Every one of them maps to a step above.

  • if n <= 2: return n handles the two base cases the loop cannot produce.
  • two_back, one_back = 1, 2 seeds the window with steps 1 and 2.
  • range(3, n + 1) is the loop bound: start above the seeds, finish on n.
  • two_back, one_back = one_back, two_back + one_back is the recurrence and the slide, in one statement. The right-hand side is evaluated before either name is rebound, so no temporary is needed.
  • return one_back — after the last iteration, that is the count for step n.
One-line summary to remember: the ways to reach step n are the ways to reach n−1 plus the ways to reach n−2, so keep only the last two counts.
