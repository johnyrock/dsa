Binary Search, Explained

Halving the search space every step, and the "search on the answer" trick that makes it show up far outside sorted arrays.

The core idea

Think of a paper phone book. You are looking for "Nakamura". You do not start at page one and read every name. You flop the book open near the middle, land on "Lawson", and think: N comes after L, so the whole first half is dead. You throw it away, open the middle of what is left, and repeat. A book with a million names is done in about twenty flips.

That is binary search. You keep a range of positions that could still hold the answer, look at the middle one, and use what you see to throw away half the range. You repeat until the range is empty or you have landed on the answer.

Why it's fast: every step deletes half the remaining candidates. Halving 1,000,000 down to 1 takes only about 20 steps, because 2²⁰ is roughly a million. That "number of halvings" is exactly what O(log n) means.

The one thing binary search demands is order. You have to be able to look at the middle element and know, with certainty, which side the answer is on. A sorted array gives you that for free. Later on you will see that other things give it to you too.

How to recognise it

Binary search is on the table when a problem has one of these smells:

  • The input is sorted, and the problem says "find" or "where would this go".
  • The expected complexity is O(log n), or the constraints are enormous (n up to 10⁹) so even a single pass over every value is too slow.
  • The question is "the smallest x that works" or "the largest x that works" — minimum speed, minimum capacity, maximum size. This is the "search on the answer" flavour below.
  • You can write a yes/no test that is monotonic: once the answer flips from no to yes as x grows, it never flips back. Monotonic just means "goes one way and stays there".
  • The array is sorted but rotated, or sorted in a wobbly way. Even then, one of the two halves is always properly sorted, which is enough.

The naive way first

Find the index of target in a sorted array. The obvious version walks the whole thing:

def search_slow(nums, target):
    for i in range(len(nums)):
        if nums[i] == target:
            return i
    return -1

This is O(n): for a million numbers it does up to a million comparisons. And every one of them past the first is wasted information. When search_slow checks index 0 and sees 2 < 23, it has just learned that the array is sorted so index 1 is also less than 23, and index 2, and so on up until things get bigger. It learns that and immediately throws it away, then checks index 1 anyway. Binary search is what you get when you refuse to throw that away.

The pattern

Keep two indices, lo and hi, marking the range that could still contain the answer. Here that range includes both ends, so an empty range is lo > hi. 

def binary_search(nums, target):
    lo, hi = 0, len(nums) - 1        # the range [lo, hi], both ends included

    while lo <= hi:                  # while the range still has something in it
        mid = (lo + hi) // 2         # // is integer division: round down
        if nums[mid] == target:
            return mid               # landed on it
        elif nums[mid] < target:
            lo = mid + 1             # mid is too small, so is everything left of it
        else:
            hi = mid - 1             # mid is too big, so is everything right of it

    return -1                        # range went empty, target is not here

The lines that matter are lo = mid + 1 and hi = mid - 1. Read them as promises: "I have personally checked mid, it is not the answer, and everything on that side of it cannot be the answer either." The + 1 and - 1 are what make the range shrink every single time. If you ever write lo = mid in this template, the range can stop shrinking and the loop runs forever.

Notice what happened at step 1. One comparison against 12 eliminated four of the seven positions — index 3 because we checked it, and indices 0, 1, 2 because sortedness guarantees they are all smaller still. You are not paying for information about one element; you are paying for information about half the array.

Notice also step 3. lo and hi are both 4, so the range holds exactly one element, and mid is that element. This is why the loop condition is lo <= hi and not lo < hi: with < the loop would have quit one step early and missed the answer sitting right there.

Variations

Leftmost position (the insertion point)

Far more useful than plain "find it" is "where does this value start, or where would I insert it to keep the array sorted?" That handles duplicates and missing values in one shot. The trick is to never return early: keep shrinking until the range is empty, and let lo be the answer. 

def lower_bound(nums, target):
    """Index of the first element >= target (== len(nums) if there is none)."""
    lo, hi = 0, len(nums)            # note: hi is one PAST the end this time
    while lo < hi:                   # range is [lo, hi), right end excluded
        mid = (lo + hi) // 2
        if nums[mid] < target:
            lo = mid + 1             # mid is too small, answer is strictly right
        else:
            hi = mid                 # mid might BE the answer, so keep it
    return lo

Two things changed. hi now sits one past the last index, so the range is "lo up to but not including hi", and the loop stops when they meet. And hi = mid has no - 1, because mid is still a candidate. Python ships this exact function as bisect.bisect_left, and bisect_right for the first element strictly greater. In an interview, writing it yourself once is worth it; in real code, use the library.

Search on the answer

This is the variation that surprises people, because there is no array to search. Suppose you must pick a speed, or a capacity, or a size, and you can test a candidate value cheaply. If "does speed x work?" is monotonic — too slow is no, and everything at or above some threshold is yes — then you can binary search the range of possible answers instead of an array. 

def min_workable(lo, hi, works):
    """Smallest x in [lo, hi] with works(x) True, assuming False...False,True...True."""
    while lo < hi:
        mid = (lo + hi) // 2
        if works(mid):
            hi = mid                 # mid works, but something smaller might too
        else:
            lo = mid + 1             # mid fails, so does everything below it
    return lo

To use it you write the works function first — usually a simple O(n) simulation — then wrap this around it. "Ship all packages within D days" and "Koko eating bananas" are both exactly this shape: guess a capacity, simulate, adjust.

Rotated sorted arrays

An array like [12, 16, 23, 38, 2, 5, 8] is sorted and then rotated: someone cut it and swapped the two pieces. You cannot compare nums[mid] to the target directly and know which side to keep. But you can first compare nums[lo] to nums[mid] to find out which half is the properly sorted one, then check whether the target falls inside that half's range. If it does, search there; if it does not, search the other half. Still O(log n), just with one extra question per step.

Common mistakes

The infinite loop from lo = mid. With mid = (lo + hi) // 2 and lo and hi one apart, mid equals lo. Writing lo = mid then changes nothing and the loop spins forever. Rule of thumb: if a branch assigns lo = mid, you must round mid up with (lo + hi + 1) // 2. Easier: stick to the two templates above, where lo always gets mid + 1.
Mixing up the two range styles. hi = len(nums) - 1 pairs with while lo <= hi and hi = mid - 1. hi = len(nums) pairs with while lo < hi and hi = mid. Take one pair from each style and you get an off-by-one or an index error. Pick one and always write it the same way.
Forgetting the input must be sorted. Binary search on unsorted data does not error, it silently returns nonsense. If you have to sort first, that costs O(n log n), so a single search is not worth it — but many searches over the same array very much are.
Overflow in (lo + hi) // 2. Python integers are unbounded so this is safe here. In C++, Java, or Go, lo + hi can overflow a 32-bit int; there you write lo + (hi - lo) // 2. Worth knowing because interviewers ask about it.

Complexity

  • Time: O(log n). The range halves every iteration, so it takes log₂(n) halvings to get from n candidates down to one. For "search on the answer", it is O(log(range) × cost of one test).
  • Space: O(1) for the loop version — just lo, hi, and mid. A recursive version is O(log n) because of the call stack.
