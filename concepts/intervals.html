Merge Intervals, Explained

Sort by start, then sweep: merging, inserting, and finding overlaps.

The core idea

Picture a stack of sticky notes on your desk, each one a booking for the same meeting room: "9:00 to 10:00", "2:00 to 6:00", "8:00 to 10:00". They came in whatever order people happened to ask, so the pile is a mess. You want to know the real answer: which blocks of time is the room actually busy?

Nobody solves that by comparing every note with every other note. You lay them out in order of start time, then read left to right with one finger, gluing a note onto the one before it whenever they touch. That is the entire pattern.

An interval is just a pair of numbers, [start, end], standing for a stretch of a line: a range of times, a range of positions, a range of anything ordered. Two intervals overlap when they share at least one point. The pattern is: sort by start, then sweep once, keeping a single "currently open" interval that you either stretch or close off.

Why it's fast: once the list is sorted by start, any interval that could overlap the one you are holding must be the very next one you read. Everything further right starts even later. So you never need to look backwards, and one pass is enough.

How to recognise it

You are almost certainly looking at an interval problem when:

  • The input is a list of pairs like [[1,3],[2,6],[8,10]], and the two numbers in each pair mean "from" and "to".
  • The words are calendar words: meetings, bookings, schedules, conflicts, rooms, flights, shifts, "busy", "free".
  • The question asks about overlap: merge the overlapping ones, count how many overlap at once, remove the fewest so that none overlap, insert a new one.
  • The ranges are unsorted and the answer must be sorted. That is a strong hint that sorting is step one and the real work is the single pass after it.
  • The pairs are ranges on a line even if they are not times: memory blocks, ranges of IP addresses, chapters in a book, x-coordinates of buildings.

The naive way first

Here is the honest first attempt. Take every pair of intervals, and if two of them overlap, replace them with one combined interval. Repeat the whole thing until a full pass changes nothing, because gluing two together can create a new overlap with a third. 

def merge_slow(intervals):
    merged = [list(iv) for iv in intervals]
    changed = True
    while changed:
        changed = False
        for i in range(len(merged)):
            for j in range(i + 1, len(merged)):
                a, b = merged[i], merged[j]
                if a[0] <= b[1] and b[0] <= a[1]:      # they overlap
                    a[0] = min(a[0], b[0])
                    a[1] = max(a[1], b[1])
                    merged.pop(j)
                    changed = True
                    break
            if changed:
                break
    return sorted(merged)     # and now sort, because the answer must be in order

This works. It is also slow, and worse, it is fiddly: the breaks exist only to restart the scan after a merge, and the while changed loop can run many times. Each full scan is O(n²) and there can be O(n) scans, so the worst case is O(n³).

The wasted work is the backtracking. Interval [15,18] gets compared against [1,3] over and over, even though a human glancing at the desk can see they are nowhere near each other. All that checking exists purely because the notes are in random order. Put them in order once and the question "could these two overlap?" is answered by adjacency instead of by a comparison.

The pattern

Sort by start. Hold one interval open. For each next interval, either stretch the open one or close it and open a new one. 

def merge(intervals):
    if not intervals:
        return []

    intervals = sorted(intervals, key=lambda iv: iv[0])   # 1. sort by start
    out = [list(intervals[0])]                            # 2. seed with the first

    for start, end in intervals[1:]:
        last = out[-1]
        if start <= last[1]:            # THE line: does this one start before the last one ended?
            last[1] = max(last[1], end) # overlap -> stretch the open interval
        else:
            out.append([start, end])    # gap -> close it off and start a new one

    return out

The line that matters is if start <= last[1]. Read it out loud as a question about the current note and the one you already glued down: "does this one begin before that one finished?" If yes they touch, so there is really only one busy block, and you widen it. If no, there is a genuine gap, and the block you were holding is final.

Two details are worth staring at. First, out[-1] is the interval you are still holding open; the rest of out is already finished and never touched again. Second, you must write max(last[1], end), not just end — the new interval can be entirely swallowed by the open one, as [2,3] is by [1,10], and plain assignment would shrink your answer.

The answer: three genuinely separate busy blocks. Five intervals in, one pass, three out.

Notice what happened at step 3. The open interval was [8,10] and the new one was [9,12], so the end moved from 10 to 12 — and that changed the question asked at step 4. Against the original [8,10] you would ask "is 15 <= 10?"; against the stretched [8,12] you ask "is 15 <= 12?". Both happen to be "no" here, but that is luck. This is why the open interval has to be a live, mutable thing rather than a copy of whatever you last read: each merge can widen the target that the next interval is tested against.

Also notice the last row. The loop ends with an interval still open, and it never goes through the else branch that appends. It is already in out because you appended it when you opened it, and you have been mutating it in place ever since. Beginners who build the answer with a separate current variable instead of out[-1] almost always forget to append that final one.

Variations

Insert one interval into an already-sorted list

If the list is already sorted and non-overlapping, and you are handed one new interval, you do not need to sort again. Walk the list in three phases: everything that ends before the new one starts goes through untouched; everything that overlaps gets absorbed into the new one; everything after goes through untouched. That is O(n) with no sort at all. 

def insert(intervals, new):
    out = []
    i, n = 0, len(intervals)

    while i < n and intervals[i][1] < new[0]:   # ends before new starts
        out.append(intervals[i])
        i += 1

    start, end = new
    while i < n and intervals[i][0] <= end:     # overlaps new
        start = min(start, intervals[i][0])
        end = max(end, intervals[i][1])
        i += 1
    out.append([start, end])

    out.extend(intervals[i:])                   # everything after
    return out

The subtle bit is intervals[i][0] <= end in the second loop, where end is growing as you go. Absorbing an interval can extend the reach far enough to swallow the next one too.

Sort by end instead: fewest removals

"Remove the fewest intervals so that none of the survivors overlap" is not a merge problem, and sorting by start gives the wrong answer. Sort by end and keep greedily: whenever two conflict, throw away the one that ends later, because it blocks more of the future. This is a greedy argument, not a sweep. 

def erase_overlap_intervals(intervals):
    if not intervals:
        return 0
    intervals = sorted(intervals, key=lambda iv: iv[1])   # sort by END
    kept_end = intervals[0][1]
    removed = 0
    for start, end in intervals[1:]:
        if start < kept_end:      # conflicts with the one we kept
            removed += 1          # drop this one; it ends later
        else:
            kept_end = end
    return removed

The sweep line: how many overlap at once

"How many meeting rooms do I need?" is not asking you to merge anything — it is asking for the biggest pile-up. Forget the intervals and keep only the events: a start is +1 person in the building, an end is -1. Sort all the events by time and run a counter. The peak is your answer. 

def max_overlap(intervals):
    events = []
    for start, end in intervals:
        events.append((start, 1))    # a meeting begins
        events.append((end, -1))     # a meeting ends
    events.sort()                    # ends (-1) sort before starts (+1) at the same time

    live = best = 0
    for _time, delta in events:
        live += delta
        best = max(best, live)
    return best

The tuple sort is doing real work here. At the same timestamp, (5, -1) sorts before (5, 1), so a meeting that ends at 5 frees its room before a meeting starting at 5 claims one. If your problem counts [1,5] and [5,9] as a conflict, starts must win the tie instead: keep the deltas as they are but sort with key=lambda e: (e[0], -e[1]). The same job can be done with a min-heap of end times, which some people find easier to picture.

Two sorted lists at once: intersections

Given two separate sorted lists of intervals, the overlap of a and b is [max(a.start, b.start), min(a.end, b.end)], which is a real interval only when that start is <= that end. Walk both lists with an index each and always advance the one that ends first — a two-pointer merge rather than a sweep.

Common mistakes

Assigning the new end instead of taking the max. Writing last[1] = end looks fine until a short interval hides inside a long one: merging [1,10] with [2,3] would silently shrink your answer to [1,3]. Always last[1] = max(last[1], end).
Guessing whether touching counts as overlapping. Do [1,4] and [4,5] merge into [1,5], or stay apart? It depends entirely on the problem, and it is the difference between <= and < on one line. LeetCode's Merge Intervals says they merge. A "meeting rooms" problem usually says they don't, because you can leave at 4 and someone else can arrive at 4. Decide this before you write the comparison, not after the test fails.
Sorting by the wrong end of the pair. Merging needs sort-by-start. Greedy "keep the most non-overlapping intervals" needs sort-by-end. They are different problems that both look like "sort the intervals", and using the wrong key gives an answer that is right on your small test and wrong on the real one.
Mutating the caller's list. intervals.sort() reorders the list you were handed, and out = [intervals[0]] puts the caller's own inner list into your result, so last[1] = ... then edits their data. Use sorted(...), which returns a new list, and list(intervals[0]), which copies the pair. Interview graders rarely check this; real code and confusing test failures both do.

Complexity

  • Time: O(n log n). The sort dominates. The sweep itself touches each interval exactly once, so it is only O(n) — if the input arrives already sorted, as in the insert variation, the whole thing drops to O(n).
  • Space: O(n) for the output, O(1) extra. Beyond the list you are building you keep nothing but a couple of variables. (Python's sort itself needs O(n) working space, and the usual convention is to count the output separately from the extra space.)
