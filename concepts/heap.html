Heaps & Top-K, Explained

A structure that always hands you the smallest or largest item, for top-K, k-th largest, and merging sorted streams.

The core idea

A hospital emergency room does not treat people in the order they arrived. It treats the most urgent person next. New patients keep arriving, urgencies keep shifting, and yet the question "who is next?" must always be answerable instantly. Nobody re-sorts the whole waiting room every time the door opens — that would be absurd. They just keep the most urgent case at the front.

A heap is that waiting room. It is a structure that gives you the smallest item instantly, and lets you add or remove items cheaply, while making no promises at all about the order of everything else. That last part is the deal you are striking: you give up full sorting, and in exchange every operation gets cheap.

Concretely, a min-heap is a binary tree with one rule: every parent is smaller than or equal to its children. That rule alone forces the smallest value to sit at the root. The tree is stored as a flat list, where the children of index i live at 2i+1 and 2i+2, so there are no node objects and no pointers.

note that the list is NOT sorted — 8 sits before 5. Only the root is promised.
Why it's fast: the tree is always kept balanced and complete, so its height is log₂(n) — about 20 levels for a million items. Adding or removing an item only has to fix one path from root to leaf, so both cost O(log n), while peeking at the smallest is O(1) because it is just index 0. Sorting everything, by contrast, costs O(n log n) and gives you far more order than you asked for.

How to recognise it

Reach for a heap when:

  • The problem says "top k", "k largest", "k closest", or "kth smallest". The word k next to a big n is the loudest signal there is.
  • You repeatedly need the smallest or largest thing, and the collection keeps changing. If it never changes, just sort once — a heap earns its keep when items come and go.
  • Data arrives as a stream and you cannot hold it all, or "find the running median".
  • You are merging several sorted sequences and need the overall smallest next item.
  • "Always process the cheapest/nearest/earliest option next" — task scheduling, Dijkstra's shortest path. That is a priority queue, which is what a heap is usually called when it is doing that job.

The naive way first

Find the k largest numbers in a list. The first idea is to sort and slice: 

def k_largest_sorted(nums, k):
    return sorted(nums)[-k:]         # O(n log n), then take the last k

That is honestly fine for most inputs, and you should say so in an interview. But it does more work than the question asked for. Sorting puts all n items in order when you only ever look at k of them; if n is 10 million and k is 10, you have ordered 10 million things to answer a question about 10. Worse, it needs every item in memory at once, so it cannot handle a stream that never ends.

The other naive idea — scan for the max, remove it, repeat k times — is O(n × k), which is even slower once k grows past log n.

The pattern

Keep a heap holding only k items: the best k you have seen so far. For the k largest, use a min-heap, so the weakest survivor is the one sitting at the top, ready to be evicted the moment something better shows up. 

import heapq

def k_largest(nums, k):
    if k <= 0:
        return []
    heap = []                                # a min-heap of the best k so far

    for x in nums:
        if len(heap) < k:
            heapq.heappush(heap, x)          # still filling up
        elif x > heap[0]:                    # heap[0] is the WEAKEST of the k
            heapq.heappushpop(heap, x)       # evict it, insert x

    return sorted(heap)

The line that matters is elif x > heap[0]. Read it as a bouncer at a club with k places: "is this newcomer better than the worst person currently inside?" If not, the newcomer is rejected in O(1) and you never touch the heap. If yes, one swap keeps the club at exactly k people.

Note that heap[0] is the only element you are allowed to trust. The rest of the list is in heap order, not sorted order, which is why the function ends with sorted(heap) — over k items, which is cheap.

heapq is min-only. Python's heapq module gives you a min-heap and nothing else: heap[0] is always the smallest. To get max behaviour, push -x instead of x and negate again when you pop. Because negation flips the order, the largest original value becomes the smallest negated one, so it lands on top. There is no heapq.heapmax — the minus sign is the API.

Notice what happened at step 6. The value 2 was compared against a single number, heap[0], and thrown away — no insertion, no restructuring, no comparison against 5, 8 or 9 individually. Most elements in a real top-k problem take exactly this path, which is why the pattern is so much faster than its worst case suggests.

Notice also the heap list at step 5: [5, 9, 8]. That is not sorted, and it is not a bug. The heap only promises that each parent is at most its children: 5 is at most 9, and 5 is at most 8. Nothing was ever promised about 9 versus 8. Print a heap and it will look shuffled; that is the point.

Variations

Max-heap by negation

When you need the largest item on top, negate on the way in and on the way out. The two minus signs cancel and the values you get back are the real ones. 

import heapq

def three_biggest_in_order(nums):
    heap = [-x for x in nums]        # flip: biggest value becomes smallest
    heapq.heapify(heap)              # rearrange in place, O(n)
    out = []
    for _ in range(min(3, len(heap))):
        out.append(-heapq.heappop(heap))   # flip back on the way out
    return out

heapq.heapify(lst) turns an existing list into a heap in place in O(n) — cheaper than n separate pushes, and the right move when you already have all the data.

Priorities with tuples

To order items by something other than the item itself, push a tuple. Python compares tuples element by element, so the first slot acts as the priority. 

import heapq

def most_frequent(words, k):
    counts = {}
    for w in words:
        counts[w] = counts.get(w, 0) + 1
    heap = []
    for word, c in counts.items():
        heapq.heappush(heap, (c, word))  # ordered by count, then alphabetically
        if len(heap) > k:
            heapq.heappop(heap)          # drop the least frequent survivor
    return [w for c, w in sorted(heap, reverse=True)]

A warning that bites people: if two tuples tie on the first slot, Python compares the second slot. That is fine for strings and numbers, but if the second slot is a custom object with no ordering defined, you get TypeError. The fix is a tiebreaker in the middle — a counter that increases with every push — so the comparison never reaches the object itself.

Merging sorted sequences

To merge k sorted lists, put the first item of each into a heap along with the list it came from. Pop the smallest, output it, and push that list's next item. The heap holds at most k items, so the whole merge is O(total items × log k). This is the general form of Merge Two Sorted Lists, where k is just 2 and a heap is overkill. 

import heapq

def merge_sorted(lists):
    heap = []
    for li, lst in enumerate(lists):
        if lst:
            heapq.heappush(heap, (lst[0], li, 0))   # (value, which list, which index)
    out = []
    while heap:
        val, li, idx = heapq.heappop(heap)
        out.append(val)
        if idx + 1 < len(lists[li]):
            heapq.heappush(heap, (lists[li][idx + 1], li, idx + 1))
    return out

Python also ships heapq.merge, plus heapq.nlargest(k, xs) and heapq.nsmallest(k, xs), which do the whole top-k pattern in one call. Know the manual version for interviews; use the library everywhere else.

Two heaps, for a running median

Keep a max-heap of the smaller half of the numbers and a min-heap of the larger half, and keep their sizes within one of each other. The median is then the top of one heap, or the average of both tops — both O(1) reads, with O(log n) insertion. This "two heaps facing each other" trick is the standard answer to Find Median from Data Stream.

Common mistakes

Expecting a max-heap. heapq only does minimums. If you push raw values and read heap[0] expecting the biggest, you get the smallest and no error. Negate on push and on pop — forgetting the second negation returns correct-looking numbers with the wrong sign, which is a genuinely hard bug to spot.
Treating the heap list as sorted. Only heap[0] is guaranteed. Slicing heap[:3] does not give you the three smallest, and iterating the list gives no useful order. To get sorted output, either pop repeatedly or call sorted(heap) at the end.
Letting the heap grow to n for a top-k question. Pushing everything and popping k times is O(n log n) and O(n) memory — no better than sorting. The whole win comes from capping the heap at k, which makes it O(n log k) time and O(k) memory.
Mutating an item after pushing it, or forgetting a tiebreaker. A heap only re-checks order when you push or pop, so changing a stored item's priority in place silently corrupts it — push a new entry and skip stale ones instead. And in tuples, add a unique counter before any unorderable object so equal priorities never force Python to compare the objects.

Complexity

  • Time: O(n log k) for the top-k pattern — each of the n elements does at most one O(log k) push or push-pop on a heap capped at k items. A single push or pop is O(log n) because it fixes one root-to-leaf path; heapify on an existing list is O(n); peeking is O(1).
  • Space: O(k), since the heap never holds more than k items. That is what lets the pattern run over a stream too large to store.
