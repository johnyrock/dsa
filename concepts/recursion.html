Recursion, Explained

A function that calls itself, the call stack that makes it work, and how to trust the recursive leap.

The core idea

You are standing in a queue and you want to know your position, but you cannot see the front. So you tap the person ahead of you on the shoulder and ask: "what number are you?" They do not know either, so they ask the person ahead of them. This keeps going until it reaches the person at the very front, who can answer without asking anybody: "I'm number 1." That answer comes back down the queue, and each person adds one before passing it on. You get your answer without ever seeing the front of the line.

That is recursion. A recursive function is a function that solves a problem by calling itself on a smaller version of the same problem. It needs exactly two things: a base case (the person at the front, who answers directly and asks nobody) and a recursive case (everyone else, who asks a smaller question and builds their answer on top of the reply).

Why it's useful: recursion is usually not about speed — it is about not having to write down the bookkeeping. Python already keeps a call stack: a pile of paused function calls, each remembering its own variables and where to resume. When you recurse you get that pile for free, so you never have to invent your own "list of places I still have to visit". For anything with a nested or branching shape — folders inside folders, nodes with children, choices leading to more choices — that saves you most of the code.

How to recognise it

Recursion is the natural fit when a problem statement has one of these smells:

  • The thing is made of smaller copies of itself. A folder contains folders. A tree node's children are trees. A linked list's next is another linked list.
  • The depth is not known in advance. If you cannot say how many for loops you would need, you need recursion.
  • You can describe the answer in terms of a slightly smaller answer. "The sum of this list is the first element plus the sum of the rest." If you can say a sentence like that, you have already written the function.
  • The problem branches. "At each step you either take this item or you don't" — two recursive calls per step. That is the shape behind backtracking and dynamic programming.
  • The words "all", "every path", "explore" appear. Exhaustive search is recursion wearing a hat.

The naive way first

Say you have a list that may contain other lists, like [1, [2, 3], [[4, 5]]], and you want the total of every number in there. Without recursion, a beginner writes loops for each level of nesting: 

def total_depth_3(data):
    t = 0
    for a in data:
        if isinstance(a, list):
            for b in a:
                if isinstance(b, list):
                    for c in b:
                        t += c            # and what if there is a list *here*?
                else:
                    t += b
        else:
            t += a
    return t

This returns 15 for the example, so it looks fine. Then somebody hands you [[[[1]]]] — four levels deep — and it crashes with a TypeError, because c is a list and you cannot add a list to a number.

The waste here is not wasted time, it is wasted code. Every level of nesting costs you another for loop and another isinstance check, and there is no depth at which you are finally done. The three loops are the same eight lines repeated with different variable names. Recursion writes those eight lines once and lets the call stack repeat them as many times as the data needs.

The pattern

Every recursive function has the same skeleton: stop, shrink, combine. Here it is on the simplest possible problem — adding up a flat list of numbers. 

def total(nums, i=0):
    if i == len(nums):                     # 1. BASE CASE: nothing left to add
        return 0                           #    the sum of no numbers is 0

    rest = total(nums, i + 1)              # 2. SHRINK: ask for the answer to a smaller problem
    return nums[i] + rest                  # 3. COMBINE: my element plus their answer

The line that matters is total(nums, i + 1). Read it out loud as "the sum of everything after position i", and then — this is the hard part — believe that it works without tracing it. That act of faith is called the recursive leap. You only have to check two things, and if both hold, the function is correct:

  1. The base case returns the right answer without recursing. Sum of an empty run of numbers is 0. True.
  2. Every recursive call moves strictly closer to the base case, and the combine step is right assuming the smaller answer is right. i + 1 always gets closer to len(nums). True.

Nothing else needs to be checked. If you find yourself trying to hold six levels of calls in your head at once, you have stopped taking the leap and started doing the computer's job.

End. Under each cell is what the call starting there returned. Each one is its own element plus the number to its right.

Notice what happened at step 6, and how little happened before it. Steps 1 to 5 computed nothing. They only stacked up five paused functions, each holding one number, waiting. All the arithmetic happened on the way back up. This is the thing beginners find spooky, and it is worth saying plainly: a recursive function has a "going down" phase and a "coming back up" phase, and where you put your code decides which phase it runs in. Work before the recursive call happens top-down; work after it happens bottom-up.

Variations

Recursion over nested structures

This is the version that fixes the broken loops from earlier. One function, any depth. The recursive call is inside a loop because a list can hold many sub-lists, not just one. 

def total_nested(data):
    t = 0
    for item in data:
        if isinstance(item, list):
            t += total_nested(item)   # same function, smaller box
        else:
            t += item
    return t

total_nested([1, [2, 3], [[4, 5]]])   # 15
total_nested([[[[1]]]])               # 1, no matter how deep it goes

Recursion over a linked list

A linked list is recursive by construction: a node, plus another linked list hanging off next. Here prev carries the already-reversed part downward, which is why nothing happens on the way back up — this is a tail call, the flavour where the recursive call is the very last thing. (See linked lists for what these nodes are.) 

def reverse_list(head, prev=None):
    if head is None:       # base case: ran off the end, prev is the new head
        return prev
    nxt = head.next        # remember the rest before we overwrite the link
    head.next = prev       # flip this one arrow
    return reverse_list(nxt, head)

Two recursive calls: branching

When each step has more than one option, call yourself once per option and add or compare the results. Counting the paths from the top-left to the bottom-right of a grid, moving only down or right: 

def count_paths(rows, cols):
    if rows == 1 or cols == 1:   # base case: only one straight line left
        return 1
    return count_paths(rows - 1, cols) + count_paths(rows, cols - 1)

count_paths(3, 3)   # 6

Branching recursion is where the interesting patterns live — and where it gets slow, because the same subproblem gets recomputed on different branches. Storing those answers is dynamic programming; undoing a choice before trying the next one is backtracking.

Recursion vs. a loop

Anything recursive can be rewritten with a loop and an explicit stack (a list you append to and pop from), and anything with one straight recursive call — like total above — is usually clearer as a plain for loop. Use recursion when the data branches, not to look clever.

Reach for recursion

  • Trees, nested lists, folders
  • Unknown or unbounded depth
  • "Try every option" searches
  • Divide and conquer (merge sort, binary search)

Reach for a loop

  • Walking an array once
  • Depth could be 100,000 (Python will stop you)
  • The recursion is one call, at the end
  • You need every scrap of speed

Common mistakes

No base case, or one that never gets hit. def broken(n): return n + broken(n - 1) never stops, and Python eventually raises RecursionError: maximum recursion depth exceeded. A base case that exists but is unreachable is the same bug wearing a disguise: if you test if i == len(nums) but step by i + 2, you can jump straight over it.
Forgetting to return the recursive call. Writing total(nums, i + 1) on its own line instead of return nums[i] + total(nums, i + 1) computes the whole answer and throws it away. Python does not warn you; the function just returns something wrong, or None. If a recursive function returns None for no obvious reason, this is almost always why.
Slicing instead of indexing. total(nums[1:]) looks tidier than total(nums, i + 1), but nums[1:] copies the rest of the list every call. That turns an O(n) function into O(n²) and quietly uses O(n²) memory. Pass an index, not a slice.
Forgetting Python's depth limit. The default limit is 1000 nested calls, so a recursion that is one-call-per-element dies on a list of 20,000. Interview inputs rarely go that deep, but if yours does, rewrite it as a loop rather than raising the limit — raising it can crash the interpreter outright.

Complexity

  • Time: (number of calls) × (work inside one call, ignoring the recursive calls). total makes n + 1 calls doing O(1) work each, so O(n). count_paths branches in two every call, so it is exponential — about O(2rows+cols).
  • Space: O(depth of the recursion) even when you allocate nothing, because every paused call sits on the call stack holding its variables. total on n elements is O(n) space — a real cost that the loop version does not pay. See time & space complexity.
