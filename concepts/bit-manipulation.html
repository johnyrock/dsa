Bit Manipulation, Explained

AND, OR, XOR, and shifts, and the handful of tricks that turn up in interviews.

The core idea

Imagine a row of light switches on a wall. Each switch is either on or off — no in-between. Now agree on a rule: the rightmost switch is worth 1, the next one left is worth 2, the next 4, then 8, 16, and so on, doubling every time you move left. Flip some switches on, add up what they are worth, and you have a number. Flip a different set and you get a different number. Every whole number is exactly one pattern of switches.

That is binary. Each switch is called a bit (short for "binary digit"), written as 0 for off and 1 for on. The number 13 is: 

worth:    8   4   2   1
bits:     1   1   0   1
          8 + 4 + 0 + 1  =  13

13 in binary is 1101. Python agrees: 0b1101 == 13, and bin(13) gives '0b1101'.

Your computer stores every integer this way already. Bit manipulation just means operating on those switches directly, all of them at once, instead of doing arithmetic on the number they add up to. Python gives you five tools for it:

  • a & b — AND. A bit is 1 only if it is 1 in both. 12 & 10 == 8, because 1100 & 1010 = 1000.
  • a | b — OR. A bit is 1 if it is 1 in either. 12 | 10 == 14 (1110).
  • a ^ b — XOR, "exclusive or". A bit is 1 if the two bits differ. 12 ^ 10 == 6 (0110).
  • a << k — left shift. Slide every bit k places left, filling with 0s. Same as multiplying by 2k: 1 << 3 == 8.
  • a >> k — right shift. Slide right, dropping what falls off the end. Same as integer-dividing by 2k: 13 >> 1 == 6.

XOR is the one that earns its keep in interviews, because of three small facts that turn out to be a superpower: 

x ^ 0 == x          # XOR with nothing changes nothing
x ^ x == 0          # anything XOR'd with itself vanishes
(a ^ b) ^ c == a ^ (b ^ c)   # order does not matter at all
Why it's useful: put those three facts together and XOR becomes a machine that cancels pairs regardless of where they sit. Fold a whole list together with ^ and every value that appears twice annihilates itself, no matter how far apart the two copies were. What is left is the value that had no partner — found in one pass, using a single integer of memory.

How to recognise it

Bit tricks are narrow. These are the tells:

  • "Every element appears twice except one." That sentence is XOR, essentially always.
  • The problem forbids extra memory — "solve it in O(1) space", "without using extra space" — while the obvious solution wants a set or a dictionary.
  • The problem is literally about bits: count the 1s, reverse the bits, check for a power of two, add two numbers without +.
  • You need every subset of a small set (n up to roughly 20). Each subset is a yes/no choice per item, which is exactly a row of switches, so the numbers 0 to 2ⁿ - 1 enumerate all of them.
  • You want a compact flag set. "Which of these 26 letters have I seen?" fits in one integer instead of a set, which matters inside a hot loop.

Equally important: bit manipulation is not a general problem-solving pattern. If a problem does not fall into one of the shapes above, reaching for bits usually makes your code harder to read for no speed gain. A hash map is almost always the better default.

The naive way first

The problem: every number in the list appears exactly twice, except one that appears once. Find it. Given [4, 1, 2, 1, 2] the answer is 4.

The natural solution is to count:

def single_number_slow(nums):
    seen = {}
    for x in nums:
        seen[x] = seen.get(x, 0) + 1
    for x, count in seen.items():
        if count == 1:
            return x

There is nothing wrong with this. It is O(n) time, it is clear, and in real code you should probably write it. But look at what it keeps: a dictionary entry for every distinct value, which is O(n) memory — and you throw almost all of it away. You build up counts for hundreds of numbers just to answer one yes/no question about each: did it appear an odd number of times?

That is the wasted work. You are storing "how many" when you only need "odd or even", and you are storing it per value when the values cancel each other out anyway.

The pattern

XOR everything together. That is the whole algorithm.

def single_number(nums):
    result = 0
    for x in nums:
        result ^= x     # THE line: pairs cancel, the loner survives
    return result

The line that matters is result ^= x, which is shorthand for result = result ^ x. Read it not as "combine these numbers" but as "toggle every switch that x has on". When the same value comes past a second time it toggles exactly the same switches back off. Because order does not matter to XOR, the two copies cancel even though they are nowhere near each other in the list.

Starting at result = 0 is not arbitrary either: 0 is XOR's do-nothing value, the way 0 is for + and 1 is for *. Start anywhere else and your answer is off by that amount.

Run it on [4, 1, 2, 1, 2]. Only three bits are needed, worth 4, 2 and 1:

          worth 4   worth 2   worth 1

XOR down a column is just "is the number of 1s odd?". Paired values contribute two 1s to every column they touch, so they always land on even.

One switch left standing, the one worth 4. Answer: 4. One pass, one integer of memory, no dictionary.

Notice what happened at step 4. The running result was 111 — a state that means nothing on its own; 7 is not in the input and is not the answer. Then the second 1 arrived and pushed it back to 110. This is the thing that makes XOR feel like magic and also the thing that makes it hard to trust: the intermediate values are meaningless. You cannot look at result halfway through and sanity-check it. All you can rely on is the invariant — at every step, result holds the XOR of everything seen so far, so any value seen an even number of times has already cancelled out. Trust the invariant, not the numbers.

One more thing worth seeing: the answer never depended on the order. Shuffle that list any way you like and every step changes, but the final 100 does not.

Variations

Reading and writing one bit

Everything else is built out of one idea: 1 << i is a number with a single 1 in position i and 0s everywhere else. That is called a mask — a stencil you lay over a number to touch one slot and leave the rest alone. 

def get_bit(n, i):
    return (n >> i) & 1          # slide bit i down to the end, keep only it

def set_bit(n, i):
    return n | (1 << i)          # OR with a 1 in that slot

def clear_bit(n, i):
    return n & ~(1 << i)         # AND with 1s everywhere except that slot

def flip_bit(n, i):
    return n ^ (1 << i)          # XOR with a 1 in that slot

~ flips every bit, so ~(1 << i) is "1s everywhere except slot i" — exactly the stencil you need to knock out one bit with AND. Positions are counted from the right starting at 0, so bit 0 is the one worth 1.

Counting the 1 bits

The obvious loop checks each of 32 positions. The trick version does one iteration per 1 bit, which is faster on sparse numbers: 

def count_bits(n):
    count = 0
    while n:
        n &= n - 1      # erases the lowest 1 bit
        count += 1
    return count

Why does n & (n - 1) erase the lowest 1? Subtracting 1 flips that lowest 1 to a 0 and turns every 0 to its right into a 1: 1011 0000 minus 1 is 1010 1111. ANDing the two keeps only the bits above that point. (Python has bin(n).count('1') and int.bit_count(), but interviewers usually want to see this.)

Power of two

A power of two is a number with exactly one 1 bit — 1, 10, 100, 1000. So knocking out its lowest 1 bit must leave nothing: 

def is_power_of_two(n):
    return n > 0 and (n & (n - 1)) == 0

Every subset, from a counter

With n items, each subset is n yes/no choices, so it is a row of n switches, so it is a number from 0 to 2ⁿ - 1. Counting up through those numbers enumerates every subset with no recursion at all: 

def subsets(items):
    out = []
    for mask in range(1 << len(items)):          # 2**len(items) masks
        picked = [items[i] for i in range(len(items)) if (mask >> i) & 1]
        out.append(picked)
    return out

This is the flat version of what backtracking does with recursion, and the same "state as an integer" idea powers bitmask dynamic programming. It only works while n is small — 2²⁰ is a million, 2³⁰ is a billion.

Missing number

Given 0..n with one number removed, XOR the values together with the indices. Every number that is present cancels against its own index, and the missing one is left over. This is the same problem cyclic sort solves a different way. 

def missing_number(nums):
    result = len(nums)                 # start with n, the index that has no slot
    for i, x in enumerate(nums):
        result ^= i ^ x
    return result

Common mistakes

^ is XOR, not "to the power of". Coming from maths or from a spreadsheet, 2 ^ 3 looks like 8. In Python it is 1, because 010 ^ 011 = 001. The power operator is **. This one bites silently: your code runs, it just returns nonsense.
Python integers have no fixed width. There is no 32-bit box. ~5 is -6, not some big positive number, and -1 >> 100 is still -1 because negatives behave as if they have infinitely many 1s off to the left. Any problem that talks about "a 32-bit integer" needs you to mask the result yourself with & 0xFFFFFFFF, then convert back if the sign bit is set. This is the single most common reason a bit solution that is correct in C loops forever or returns a huge number in Python.
Forgetting that 0 passes the power-of-two test. 0 & (0 - 1) is 0, so is_power_of_two(0) would say True without the n > 0 guard. Zero and negative numbers are the edge cases in almost every bit trick; check them before you check anything else.
Assuming XOR cancels any repeat. It cancels pairs. If the duplicates appear three times each, 5 ^ 5 ^ 5 is 5, not 0, and the whole approach collapses. Read the problem statement carefully: "appears twice" is XOR, "appears three times" needs a different technique (counting the 1s in each bit position modulo 3).

Complexity

  • Time: O(n) for the XOR fold — one pass, and each ^ is a single machine instruction on fixed-width integers, so it is O(1) per element. The bit-twiddling helpers are O(1), or O(number of 1 bits) for the n & (n-1) loop, which is at most 32 or 64.
  • Space: O(1). One integer, whatever the input size. That is the entire reason to prefer XOR over the counting dictionary, which needs O(n) — see time and space complexity for why that trade matters.
