Greedy Algorithms, Explained

Taking the locally best choice at every step, when that works, and how to tell when it doesn't.

The core idea

You are a cashier handing back 63p in change, and you want to use as few coins as possible. You do not sit down and enumerate every combination of coins. You grab the biggest coin that still fits — 25p — then the biggest that fits in what is left, and so on, until you have handed over nothing. It takes about four seconds and you have never once regretted a coin.

A greedy algorithm is exactly that: at each step take the choice that looks best right now, commit to it, and never reconsider. No backtracking, no table of alternatives, no second guesses.

Why it's fast: you look at each option once and make one decision about it, so the whole thing is a single pass — usually O(n), or O(n log n) if you have to sort first. Compare that with backtracking, which walks every combination, or dynamic programming, which fills a whole table. Greedy does neither. It keeps no history at all.
And why it is dangerous: keeping no history means that if the locally best choice is ever the globally wrong one, you will never find out. Greedy is the one pattern where writing the code is easy and knowing whether you are allowed to write it is the hard part. There is a worked counterexample below; read it before you trust a greedy solution.

How to recognise it

Greedy is worth trying when:

  • There is an obvious "best" ordering — biggest first, earliest deadline first, earliest finishing time first — and the problem practically hands it to you.
  • The problem asks for a maximum count or a minimum count of things chosen under a simple constraint: most meetings that fit, fewest coins, fewest jumps.
  • A choice does not badly constrain later choices. Taking the meeting that ends soonest leaves the most room for everything after it; nothing you might want later becomes impossible.
  • You can argue an exchange: "take any optimal answer that does not include my greedy choice; I can swap my choice in without making it worse." If you can say that sentence honestly, greedy is correct. If you cannot, it probably is not.
  • Sorting the input makes the problem look trivial. Half of all greedy solutions are a sort followed by one loop.

Negative signal: if choices interact — taking this item changes what the best next item even is, as with a weight limit or a budget — greedy usually fails and you want dynamic programming.

The naive way first

The running example is fewest coins to make an amount. The complete, obviously-correct approach is to try every coin as the next one and keep the best result: 

def min_coins_slow(coins, amount):
    if amount == 0:
        return 0
    best = float("inf")
    for c in coins:
        if c <= amount:
            best = min(best, min_coins_slow(coins, amount - c) + 1)
    return best

min_coins_slow([25, 10, 5, 1], 12)   # 3  (10 + 1 + 1)

This is always right, and it is exponential: every call branches once per coin, so the number of calls grows exponentially — about 390 million calls for an amount of 63, which is hopeless. Even asking it for an amount of 100 will outlast your patience.

The wasted work is that it explores orderings. It tries 25-then-10 and 10-then-25 as if they were different answers, and it re-solves "make 38p" once for every different route that arrives at 38p. Caching those repeats is dynamic programming and gets you to O(amount × coins). The greedy claim is bolder: that you never needed to explore at all.

The pattern

Sort into the order that makes "best" mean something, then take everything you can, in that order.

def min_coins_greedy(coins, amount):
    coins = sorted(coins, reverse=True)   # biggest first: the ordering IS the algorithm
    used = []
    for c in coins:
        while amount >= c:                # take as many of this coin as fit
            amount -= c
            used.append(c)
    return used

min_coins_greedy([1, 5, 10, 25], 63)   # [25, 25, 10, 1, 1, 1] — six coins

The line that matters is sorted(coins, reverse=True). In a greedy algorithm the sort key is the algorithm — everything after it is bookkeeping. When a greedy solution is wrong, the bug is almost never in the loop; it is that you sorted by the wrong thing, or that no sort key exists for this problem at all.

The general shape, for any greedy problem, is the same three lines: sort by the key, walk the sorted items once, take each one if it is still compatible with what you have already taken.

Notice what happened at step 1 — or rather, what didn't. Taking that first 25p was never revisited. No later step could say "actually, two 10s and a 5 would have been better", because the algorithm keeps no record of the choice and has no mechanism for changing it. It worked here, for a reason specific to these coins: with 1, 5, 10 and 25, no pile of smaller coins can ever replace a bigger coin using fewer pieces. Change the coin set and that reason evaporates.

What is actually optimal: 3 + 3, two coins. Greedy is 50% worse, on an input with three coins and an amount of six.

Look at where it went wrong: step 1. Taking the 4 left a remainder of 2, and 2 is an awkward number to make from 1s, 3s and 4s. The 3 was the better first move even though it is smaller — because of what it leaves behind, which is information greedy never looks at. And this is not a one-off: the same coins give the wrong answer for 6, 10, 14, 18, 22, 26, 30, and so on forever.

How to check, in two minutes. Before trusting a greedy rule, do this: write the honest brute force (or a small DP), generate every input up to some small size, and compare the two answers. If they never disagree, you probably have something. If they disagree once, you are done — you have your counterexample, and the answer is dynamic programming. Sweeping amounts 1 to 200 for the coins [1, 5, 10, 25] finds no disagreement; the same sweep for [1, 3, 4] finds one at 6 almost immediately.

This is why Coin Change is a DP problem on LeetCode and not a greedy one: the coins are given to you, so you cannot assume they behave like real money.

Variations

Sort by end time: fit the most items

The classic correct greedy. Given meetings with start and end times, book as many non-overlapping ones as possible. Sort by end time and take every meeting that starts after the last one you took finished. 

def max_meetings(meetings):
    meetings = sorted(meetings, key=lambda m: m[1])   # earliest FINISHING first
    count = 0
    last_end = float("-inf")
    for start, end in meetings:
        if start >= last_end:        # does not clash with what we already took
            count += 1
            last_end = end
    return count

max_meetings([(1, 3), (2, 4), (3, 5), (0, 6), (5, 7), (8, 9)])   # 4

The exchange argument works here: the meeting that finishes earliest leaves at least as much room as any other first choice, so swapping it into any optimal schedule never makes things worse. Sort the same list by start time instead and you get 2 — the long (0, 6) meeting gets picked first and blocks four others.

Sort by start: merging intervals

A different key for a different question. To merge overlapping ranges, sort by start and extend the last range whenever the next one begins before it ends. 

def merge(intervals):
    intervals = sorted(intervals, key=lambda x: x[0])   # earliest STARTING first
    merged = []
    for start, end in intervals:
        if merged and start <= merged[-1][1]:           # overlaps the last one
            merged[-1][1] = max(merged[-1][1], end)
        else:
            merged.append([start, end])
    return merged

merge([[1, 3], [2, 6], [8, 10], [15, 18]])   # [[1, 6], [8, 10], [15, 18]]

Running best, no sort at all

Some greedy algorithms need no ordering because the input order already is the ordering. Buying and selling a stock once: at every day, greedily assume you bought at the cheapest price seen so far. 

def max_profit(prices):
    cheapest = float("inf")
    best = 0
    for p in prices:
        cheapest = min(cheapest, p)     # greedy: always buy at the cheapest so far
        best = max(best, p - cheapest)
    return best

max_profit([7, 1, 5, 3, 6, 4])   # 5

This one is correct because a cheaper buying day is never worse for any future selling day — the exchange argument again, in one line.

Greedy with a heap

When "best right now" changes as you go, you cannot pre-sort — you need a structure that hands you the current best on demand. That is a heap (a priority queue), and the pattern is: push everything you have unlocked, pop the best, repeat. Task scheduling and "merge k sorted lists" both look like this.

Common mistakes

Assuming greedy works because it feels obvious. The coin example above is the whole lesson: a rule that is correct for real money is wrong for [1, 3, 4], and nothing in the code hints at it. "It felt right" is not an argument. Either state the exchange argument in a sentence, or test against brute force on small inputs.
Passing the sample tests and calling it proved. Greedy failures are usually rare and structured — they need a specific relationship between the values, so the first few examples in a problem statement typically miss them entirely. A greedy solution that passes three hand-written examples has shown nothing.
Sorting by the wrong key. "Sort the intervals" is not an instruction; by start and by end are different algorithms answering different questions. Before typing the sort, say what the key is for: earliest finish leaves the most room, earliest start makes overlaps adjacent.
Using greedy when choices compete for a shared budget. In 0/1 knapsack, taking items by best value-per-kilogram is the natural greedy rule, and it is wrong: with items (3kg, £6), (4kg, £7), (5kg, £8) and a 9kg limit, greedy takes the 3kg and 4kg items for £13, while the 4kg and 5kg pair fills the bag exactly for £15. A shared, exhaustible resource is the standard signal that you need DP instead.

Complexity

  • Time: O(n log n) when the sort is what makes it work, since the sort dominates the single pass afterwards. O(n) when no sort is needed, as in the running-best variants. This is the payoff: DP on the same problem is often O(n × something).
  • Space: O(1) beyond the input if you sort in place and keep only a running answer, O(n) if you build an output list or sort a copy. See time & space complexity.
