Cyclic Sort, Explained

When the numbers are 1 to n, put each one in its own slot and the missing or duplicate one falls out.

The core idea

A cloakroom has five numbered hooks and five numbered coats. Someone has hung them up in a mess. You do not need a clever sorting method to fix it: pick up whatever is on hook 1, walk it to its own numbered hook, and pick up whatever was hanging there. Keep doing that. Every coat you carry goes straight home, and when you are done, hook k holds coat k. If a hook ends up empty, you know instantly which coat is missing — the hook's number tells you.

That is cyclic sort. When an array holds the numbers 1 to n (or 0 to n) in some scrambled order, the value is the address. Value v belongs at index v - 1. So you walk the array putting each number where it belongs by swapping, and afterwards any index whose value does not match is your answer.

Why it's fast: every swap puts at least one number in its final resting place forever, so there can be at most n swaps in total. That makes it O(n) — faster than the O(n log n) of a general sort — and it uses no extra memory, unlike a hash set of what you have seen.

How to recognise it

This pattern has an unusually loud tell. Look for:

  • "An array containing n numbers taken from the range 1 to n", or 0 to n, stated in the problem. That sentence is the pattern announcing itself.
  • "Find the missing / duplicate / corrupt number" in such an array.
  • "Do it in O(n) time and O(1) extra space" alongside the range constraint. Those two constraints together rule out sorting and rule out a set, which leaves this.
  • The array may be modified. Cyclic sort rearranges the input; if the problem forbids that, you need a different trick.
  • Smallest missing positive, even when the values are junk. The array can still act as its own lookup table for whatever does fall in 1..n.

If the numbers are not bounded by the array's length, this does not apply — the addressing scheme has nothing to stand on. Reach for a hash map or binary search instead.

The naive way first

Take: an array holds n distinct numbers from 1 to n + 1, with exactly one missing. Find it. The first thing most people write is a scan per candidate: 

def find_missing_slow(nums):
    n = len(nums) + 1
    for candidate in range(1, n + 1):
        if candidate not in nums:      # a fresh scan of the whole list, every time
            return candidate
    return -1

The in on a list is not free: it walks the list. So this is O(n²) — for 10,000 numbers, about 50 million comparisons on average.

The wasted work is that each candidate's scan learns a great deal and then throws it away. Searching for the number 1 walks past 7, 4 and 2 and forgets that it saw them; searching for 2 walks past them all again. The array already knows where everything is — the code just refuses to use it.

A sensible middle step is set(nums), which gets you to O(n) time. But it costs O(n) extra memory, and problems that specify this pattern usually forbid exactly that.

The pattern

Walk an index i from left to right. Look at nums[i], work out where it belongs, and swap it there. Crucially, do not advance i after a swap — you now have a new, unexamined value sitting at i, and it needs the same treatment. 

def cyclic_sort(nums):
    i = 0
    while i < len(nums):
        home = nums[i] - 1                 # value v belongs at index v - 1
        if nums[i] != nums[home]:          # someone else is sitting in its seat
            nums[i], nums[home] = nums[home], nums[i]
        else:
            i += 1                         # this seat is settled, move on
    return nums

The line that matters is if nums[i] != nums[home]:. Read it as "is the value that belongs at home already there?" You might expect if i != home:, and for a clean 1..n permutation the two are identical. They differ when the array contains duplicates: with [2, 2], the value 2 at index 1 is already home, and i != home would keep swapping it with an identical 2 forever. Comparing values never loops.

Why the loop terminates even though i sometimes does not move. Each iteration either advances i (at most n times) or performs a swap that places a value at its correct index, where it will never be moved again (at most n times). So the loop body runs at most 2n times. The nested-looking structure is still O(n).

Notice what happened at steps 1 to 3. i stayed at 0 the whole time. Each swap dropped a new value into index 0, and each one got handled in turn: 3 went home, then 5 went home, then 2 went home, and only then did 1 land at index 0 where it belonged. That is the "cycle" the pattern is named after — the values 3 → 5 → 2 → 1 formed a loop of displacements, and one pass around it resolved all of them.

And notice step 3. The swap put 2 at index 1 and brought 1 back to index 0. One swap, two numbers placed. That is why the swap count is at most n and usually well under it.

Variations

The range is 0 to n, not 1 to n

Then value v belongs at index v, with no minus one. One value in 0..n is missing, so one index will hold the wrong thing — and if every index matches, the missing number is n itself, which has no slot. 

def missing_number(nums):
    i, n = 0, len(nums)
    while i < n:
        home = nums[i]                            # value v belongs at index v
        if nums[i] < n and nums[i] != nums[home]: # n has no slot, so skip it
            nums[i], nums[home] = nums[home], nums[i]
        else:
            i += 1
    for i in range(n):
        if nums[i] != i:
            return i
    return n

All the missing numbers at once

Same sort, then one scan. Every index whose value is wrong hands you a missing number directly — the index plus one. Duplicates in the input are what create the empty slots. 

def find_disappeared(nums):
    i = 0
    while i < len(nums):
        home = nums[i] - 1
        if nums[i] != nums[home]:
            nums[i], nums[home] = nums[home], nums[i]
        else:
            i += 1
    return [i + 1 for i, v in enumerate(nums) if v != i + 1]

The duplicate

Mirror image: after sorting, the first index whose value is wrong is holding the extra copy, so you return the value rather than the index. 

def find_duplicate(nums):
    i = 0
    while i < len(nums):
        home = nums[i] - 1
        if nums[i] != nums[home]:
            nums[i], nums[home] = nums[home], nums[i]
        else:
            i += 1
    for i, v in enumerate(nums):
        if v != i + 1:
            return v
    return -1

If the problem forbids modifying the array, the same question can be answered with fast and slow pointers, treating i → nums[i] as a linked list and finding where the cycle starts.

Junk values mixed in (first missing positive)

The array may hold negatives, zeros, and huge numbers. Those have no home in 1..n, so leave them where they fall and just skip past them. Everything that does belong still gets placed, and the first wrong index is still the answer. 

def first_missing_positive(nums):
    n = len(nums)
    i = 0
    while i < n:
        home = nums[i] - 1
        if 0 <= home < n and nums[i] != nums[home]:   # ignore anything outside 1..n
            nums[i], nums[home] = nums[home], nums[i]
        else:
            i += 1
    for i in range(n):
        if nums[i] != i + 1:
            return i + 1
    return n + 1

Common mistakes

Advancing i after a swap. Writing this as a for i in range(n) loop with a swap inside quietly abandons the value that just landed at i. Use a while and only increment in the else branch.
Comparing indices instead of values. if i != home: looks equivalent and passes on inputs with no duplicates. On [1, 1] it spins forever, swapping a 1 with an identical 1. Always compare nums[i] != nums[home].
Mixing up the two index maps. For values 1..n the home of v is v - 1; for values 0..n it is v. Using the wrong one gives an IndexError or a silently wrong answer. Read the problem's range before writing the line.
Swapping without bounds-checking on messy input. If values can fall outside the range — as in First Missing Positive — nums[i] - 1 may be negative or past the end. An index past the end raises IndexError, which at least tells you; a negative one silently wraps around to the other end of the array and corrupts it, which does not. Guard with 0 <= home < n.

Complexity

  • Time: O(n). Each loop iteration either advances i or fixes one value permanently, and each of those can happen at most n times, so the body runs at most 2n times.
  • Space: O(1). The swaps happen inside the input array; nothing is allocated. (The "all missing numbers" variant returns a list, but that is the output, not working memory.)
