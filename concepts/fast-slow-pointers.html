Fast & Slow Pointers, Explained

Two pointers moving at different speeds through a linked list: cycle detection, midpoints, and the nth node from the end.

The core idea

Two runners set off together. One jogs, one sprints at exactly double the pace. If the road is straight, the sprinter reaches the end and that is that — they never meet again. But if the road is a circular track, the sprinter eventually laps the jogger and they end up standing on the same spot. You did not need a map of the track, and you did not need to remember every step you took. You just needed two different speeds.

That is the whole pattern. Fast and slow pointers means walking one pointer through a linked list one node at a time while a second pointer goes two at a time. Where they end up — the same node, or off the end — tells you something you would otherwise have to store a lot of memory to learn. It is also called Floyd's tortoise and hare.

Why it's useful: it answers "is there a loop?" and "where is the middle?" in O(1) extra memory. The obvious alternatives — remembering every node you have visited, or walking the list twice to measure it — cost O(n) memory or an extra pass. Two variables cost nothing.

New to linked lists? The linked list page covers what a node is and why you cannot just index into one.

How to recognise it

Look for these signals:

  • A linked list, plus "cycle", "loop", or "does it end?" This is the signature use.
  • "The middle node", or "the first half and the second half", when you are not allowed a second pass to count the length.
  • "The nth node from the end". You cannot count backwards in a singly linked list, so you open a gap of n between two pointers and walk them together.
  • "O(1) extra space" spelled out in the constraints on a linked-list problem. That is the interviewer ruling out a set of visited nodes.
  • Any process that repeats a function forever — x = f(x) on integers, say. If the values must eventually repeat, they form a cycle, and the same two-speed trick finds it without storing every value.

The naive way first

To detect a cycle, the instinctive answer is to write down every node you visit and check whether you have been there before: 

def has_cycle_slow(head):
    seen = set()
    node = head
    while node:
        if id(node) in seen:     # we have stood on this exact node already
            return True
        seen.add(id(node))
        node = node.next
    return False

id(node) is Python's unique number for an object. We store that rather than the node itself, because two different nodes can hold equal values and we care about identity, not value.

This is correct, and it is O(n) time. The waste is not time — it is space. The set grows to O(n), one entry for every node, in a list that might have a million of them. Then it is all thrown away, when the only fact we wanted out of it was a single yes or no.

The pattern

Send both pointers from the head, move one by one and the other by two, and watch for a collision. 

def has_cycle(head):
    slow = head
    fast = head
    while fast and fast.next:      # fast needs two nodes ahead of it to move
        slow = slow.next           # one step
        fast = fast.next.next      # two steps
        if slow is fast:           # they landed on the same node
            return True
    return False                   # fast ran off the end, so the list is straight

The line that matters is while fast and fast.next:. Read it as the guard that lets you write fast.next.next on the following line without crashing. fast must exist, and fast.next must exist, or the two-step move would run off the end of the list. It is also your exit condition: reaching the end is the proof that there is no cycle, because a cycle has no end.

Note slow is fast, not slow == fast. is asks "the same object?" while == asks "equal contents?" Two separate nodes both holding the value 3 are == but not is, and here you mean identity.

Why a collision is guaranteed. Once both pointers are inside the loop, look at the gap between them going forward. Every step, slow gains 1 and fast gains 2, so the gap shrinks by exactly 1 each time. A quantity that shrinks by 1 every step and wraps around a finite loop must eventually hit 0. It cannot step over the target, because it moves by exactly one.

Notice what happened at step 3. fast was on node 5, the last node — but "last" is a lie here, because node 5 points back to node 3. So fast went 5 → 3 → 4 and landed on the node slow had just reached. The wrap-around is invisible to the code; fast.next.next simply follows whatever pointers exist.

Also notice that the meeting node, 4, is not where the cycle starts. The cycle starts at node 3. The two are different, and the next section shows the two-line trick that gets from one to the other.

Variations

Where does the cycle begin?

Once the pointers meet, put one of them back at the head and move both one step at a time. The node where they meet again is the entrance to the loop. In our example: node 1 vs node 4, then node 2 vs node 5, then node 3 vs node 3 — the entrance, correctly. 

def cycle_start(head):
    slow = fast = head
    while fast and fast.next:
        slow = slow.next
        fast = fast.next.next
        if slow is fast:
            slow = head                 # restart one pointer at the head
            while slow is not fast:     # now both move ONE step at a time
                slow = slow.next
                fast = fast.next
            return slow                 # they meet at the entrance
    return None

The reason, briefly: let a be the distance from the head to the entrance and b the distance from the entrance to the meeting point. Because fast travelled exactly twice as far as slow, the distance from the meeting point onward to the entrance turns out to equal a. So two pointers, one at the head and one at the meeting point, moving at the same speed, arrive at the entrance together.

The middle of the list

When fast reaches the end, it has covered twice as much ground, so slow is halfway. One pass, no length counting. 

def middle_node(head):
    slow = fast = head
    while fast and fast.next:
        slow = slow.next
        fast = fast.next.next
    return slow

With an even number of nodes this returns the second of the two middles. If you need the first one, start fast at head.next instead.

The nth node from the end (a fixed gap, same speed)

Here the pointers move at the same speed, but you open a gap of n nodes first. When the leading pointer hits the last node, the trailing one is sitting exactly n nodes back. 

def remove_nth_from_end(head, n):
    dummy = ListNode(0, head)   # a fake node in front, so deleting the head is not special
    slow = fast = dummy
    for _ in range(n):          # open a gap of n nodes
        fast = fast.next
    while fast.next:            # walk both until fast is on the last node
        slow = slow.next
        fast = fast.next
    slow.next = slow.next.next  # slow is now just before the target: unlink it
    return dummy.next

Cycles without a linked list

Any repeated function x = f(x) over a finite set of values must eventually repeat, which means it has a cycle. Happy Number replaces "sum of the squares of the digits" until it hits 1 or loops forever — the same two speeds decide which. 

def next_number(n):
    return sum(int(d) ** 2 for d in str(n))

def is_happy(n):
    slow, fast = n, next_number(n)
    while fast != 1 and slow != fast:
        slow = next_number(slow)
        fast = next_number(next_number(fast))
    return fast == 1

Find the Duplicate Number (#287) is the same idea in disguise: treat i → nums[i] as the "next" pointer and the duplicate value is the entrance to the cycle.

Common mistakes

Checking only while fast:. That crashes with an AttributeError the moment fast is the last node, because fast.next.next dereferences None. You need both halves: while fast and fast.next:.
Comparing with == instead of is. On a list like 1 → 2 → 2 → 3, the two nodes holding 2 compare equal, and an == check reports a cycle that does not exist. Compare identity.
Assuming the meeting point is the cycle's start. It usually is not — in the trace above they met at node 4 while the cycle begins at node 3. Returning the meeting node passes the "is there a cycle?" problem and fails the "where does it start?" one.
Checking for a collision before the first move. Both pointers start on the head, so a check at the top of the loop reports a cycle immediately for every list. Move first, compare second — or start fast at head.next and adjust the rest to match.

Complexity

  • Time: O(n). slow visits each node at most once before the collision, and fast moves at twice that rate, so the total work is proportional to the list length.
  • Space: O(1). Two pointer variables, no matter how long the list is. That is the entire point — the set-based version is O(n).
