Tree Traversal (DFS & BFS), Explained

Preorder, inorder, postorder, and level order, and which one to reach for.

The core idea

Picture the org chart of a small company. The CEO is at the top. Two people report to the CEO, a few people report to each of them, and so on down to the people with nobody under them. Now you have to say hello to everybody exactly once. There are only two sensible plans.

Plan one: pick one person, then their first report, then that person's first report, all the way to the bottom of that branch, then back up one step and take the next branch. You go deep before you go wide. That is depth-first search, or DFS.

Plan two: say hello to the CEO, then to everyone one level down, then everyone two levels down. You finish a whole floor before touching the next one. That is breadth-first search, or BFS, also called level order.

First, the vocabulary. A tree is a set of boxes called nodes, each holding a value and pointing at some nodes below it. The one at the top is the root. The nodes a node points at are its children; a node with no children is a leaf. A node plus everything hanging beneath it is a subtree. In a binary tree each node has at most two children, called left and right. Nothing ever points back upward, so there are no loops: from the root there is exactly one path down to any node. 

class TreeNode:
    def __init__(self, val, left=None, right=None):
        self.val = val
        self.left = left      # another TreeNode, or None
        self.right = right    # another TreeNode, or None
Why traversal is the whole game: almost every tree question is "visit every node and do a little bit of bookkeeping". Depth, sum, search, invert, validate, serialise — all of them are a traversal with three or four extra lines. Once you can write the traversal from memory, the problem shrinks to "what do I record at each node, and when?"

How to recognise it

You are looking at a traversal problem when:

  • The input is a tree and the answer is a single number about all of it: depth, sum, node count, "is it balanced".
  • The question mentions levels or rows: "level order", "right side view", "the widest level", "zigzag". That word level is BFS shouting at you.
  • The question mentions sorted order on a binary search tree: "the k-th smallest", "validate this BST". Inorder DFS is the move.
  • You need information from the children before you can answer for the parent: height, "does this subtree contain X", subtree sums. That is postorder DFS.
  • The shortest path from the root to a node matching some condition. BFS finds it first, so you can stop early.

The naive way first

Before you know traversal, the instinct is to reach down the tree by hand, one dotted attribute at a time. Here is someone trying to find whether a value is anywhere in the tree: 

def contains_slow(root, target):
    if root is None:
        return False
    if root.val == target:
        return True
    if root.left is not None:
        if root.left.val == target:
            return True
        if root.left.left is not None and root.left.left.val == target:
            return True
        # ...and on and on, one level at a time, forever
    return False

This cannot work, and the reason is worth naming. You do not know how deep the tree is when you write the code, so there is no number of if blocks that is enough. You also wrote root.left and root.left.left as separate cases when they are the same job applied to a smaller tree. The wasted work here is not CPU time, it is you: you are hand-unrolling a loop whose length you will never know. The fix is to let a function call itself, which is recursion.

The pattern

Every depth-first traversal of a binary tree is this shape. Memorise it and the rest is decoration.

def dfs(node):
    if node is None:          # base case: fell off the bottom, nothing to do
        return
    # (A) preorder position: you are here, children not visited yet
    dfs(node.left)            # go all the way down the left side
    # (B) inorder position: left side done, right side not started
    dfs(node.right)           # then all the way down the right side
    # (C) postorder position: both children are fully done

The line that matters is if node is None: return. Everything else in the function assumes node is real, so this single guard is what stops the recursion falling off the edge of the tree. Write it first, every time, before you write anything else.

The three comment positions are the only choice you actually make. Put your work at (A) and you get preorder: a node is handled before its children. Put it at (B) and you get inorder: the whole left subtree, then the node, then the right subtree. Put it at (C) and you get postorder: the node is handled only after everything below it is finished, which means the children can hand results up to it. 

def preorder(node, out):
    if node is None:
        return out
    out.append(node.val)      # visit BEFORE the children
    preorder(node.left, out)
    preorder(node.right, out)
    return out

def inorder(node, out):
    if node is None:
        return out
    inorder(node.left, out)
    out.append(node.val)      # visit BETWEEN the children
    inorder(node.right, out)
    return out

def postorder(node, out):
    if node is None:
        return out
    postorder(node.left, out)
    postorder(node.right, out)
    out.append(node.val)      # visit AFTER the children
    return out

BFS is a different shape entirely, because it does not use recursion. It uses a queue: a list you add to at one end and remove from the other, so the node that has been waiting longest comes out next. Python's collections.deque gives you that with append and popleft. 

from collections import deque

def level_order(root):
    if root is None:
        return []
    levels = []
    queue = deque([root])
    while queue:
        level = []
        for _ in range(len(queue)):   # exactly the nodes sitting on this level
            node = queue.popleft()
            level.append(node.val)
            if node.left:
                queue.append(node.left)
            if node.right:
                queue.append(node.right)
        levels.append(level)
    return levels

Here the line that matters is for _ in range(len(queue)). You measure the queue length once, before the inner loop starts. Everything in the queue at that instant is exactly one level, and everything you push during the loop belongs to the next one. That one snapshot is what separates "a flat list of nodes" from "a list of levels".

One example, traced by hand

Here is a six-node tree. We will run inorder on it and write down every step.

             4
           /   \
          2     6
         / \     \
        1   3     7

Start. The root is 4. The leaves are 1, 3 and 7.

Each row below is one moment in the recursion. "Call" is the function invocation we are inside; "returns to" means that call finished and we popped back up to the caller.

End. The number in brackets above each node is when it was recorded. Reading them in order gives 1, 2, 3, 4, 6, 7 — sorted.

Notice what happened at step 6. Node 4 is the root, the very first call we made, and it was the fourth value recorded. It had to sit and wait while its whole left subtree finished. That waiting is the entire difference between the three orders: preorder would have recorded 4 at step 1, postorder would have recorded it last. Nothing else about the code changes.

This tree is also a binary search tree (BST): every value in a node's left subtree is smaller than the node, every value in its right subtree is larger. That is exactly why inorder came out sorted. "Inorder on a BST gives sorted order" is worth memorising — it is the trick behind a whole family of problems.

Variations

Postorder for anything that flows upward

When the parent's answer is built out of the children's answers, do the work at position (C) and let the return value carry it up. Depth is the cleanest example: a tree's depth is one more than the deeper of its two subtrees. 

def max_depth(node):
    if node is None:
        return 0
    return 1 + max(max_depth(node.left), max_depth(node.right))

Read it as a promise: "assume the two recursive calls already give me the correct depths." You never trace it in your head. Subtree sums, "is this balanced", and "count the good nodes" are all this shape.

DFS without recursion, using an explicit stack

Recursion uses the call stack behind your back. You can carry your own stack instead, which matters when the tree is deep enough to blow Python's recursion limit (about 1000 frames by default). 

def preorder_iterative(root):
    if root is None:
        return []
    out, stack = [], [root]
    while stack:
        node = stack.pop()             # a stack: last in, first out
        out.append(node.val)
        if node.right:
            stack.append(node.right)   # push right FIRST
        if node.left:
            stack.append(node.left)    # so left comes off the stack first
    return out

Compare this with level_order above. Same loop, same pushes. The only difference is stack.pop() versus queue.popleft() — last-in-first-out gives you DFS, first-in-first-out gives you BFS. That one swap is the whole distinction.

BFS when you want the shallowest answer

BFS reaches every node at depth 1 before any node at depth 2. So if you are looking for the closest node matching a condition, BFS finds it first and you can return immediately. DFS would have to search the entire tree and keep a running minimum. Same idea powers shortest paths in graph traversal.

Binary search trees: skip half the tree

In a BST you do not need to visit everything. Comparing the target with the current value tells you which side it must be on, so you throw the other side away — the same halving idea as binary search. 

def bst_search(root, target):
    node = root
    while node is not None:
        if node.val == target:
            return True
        node = node.left if target < node.val else node.right
    return False

That is O(h) where h is the height, not O(n). On a balanced tree of a million nodes, about twenty steps.

Common mistakes

Forgetting the None base case. Leaves have left and right set to None, and you will recurse into them. Without if node is None: return at the very top you get AttributeError: 'NoneType' object has no attribute 'val'. Write the guard before you write the body.
Reading the queue length inside the loop. In level order, if you write while queue: and pop one at a time without the for _ in range(len(queue)) snapshot, you get every node in BFS order but no idea where one level ends and the next begins. Measure the length before you start popping.
Mixing up "inorder gives sorted" and "any tree". Inorder produces sorted output only on a binary search tree. On an arbitrary binary tree it produces a perfectly valid traversal that means nothing in particular.
Pushing left before right in the iterative DFS. A stack reverses what you put in, so pushing left then right makes you visit the right child first. If your preorder comes out mirrored, this is why.

Complexity

  • Time: O(n) for any full traversal — every node is visited exactly once, and the work per node is constant. Searching a balanced BST is O(log n) because each comparison discards half the remaining tree.
  • Space: O(h) for DFS, where h is the height, because that is how many calls are stacked up at the deepest moment: O(log n) if the tree is balanced, O(n) if it is a single long chain. BFS is O(w) where w is the widest level, which for a full tree is about n/2, so O(n).
