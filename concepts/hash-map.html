Hash Maps & Sets, Explained

Trading a little memory for instant lookups, the single most common trick for turning O(n²) into O(n).

The core idea

Picture a coat check at a theatre. Without one, finding your coat means walking down a rail of four hundred coats looking at each one. With one, you hand over ticket 137, and the attendant walks straight to hook 137. The ticket number does not describe the coat — it tells you exactly where to stand. Getting your coat takes the same amount of time whether there are ten coats or ten thousand.

A hash map is that coat check. You give it a key, it runs the key through a hash function — a small calculation that turns the key into a number — and that number is the shelf it stores the value on. Looking a key up runs the same calculation and goes straight to the shelf. In Python this is the humble dict. 

key "cat"  ──hash──>  3   ┌───┬───┬───┬─────────┬───┬───┐
key "dog"  ──hash──>  0   │dog│   │   │cat, fish│   │   │
key "fish" ──hash──>  3   └───┴───┴───┴─────────┴───┴───┘
                            0   1   2      3      4   5
                        (cat and fish "collide" on shelf 3;
                         the map just keeps both there and
                         checks the actual keys when asked)

A set is the same machine with the values thrown away. It only remembers which keys it has seen. Use a dict when you need to look something up, and a set when you only need to ask "have I seen this?".

Why it's fast: the position is computed from the key, not searched for. So d[k], k in d, and d[k] = v all take roughly constant time — O(1) — no matter how many keys are already in there. That is what lets you replace "scan the whole list to see if x is here" with a single question.

How to recognise it

Almost any time you catch yourself scanning a list inside another loop, a hash map is the fix. Concretely:

  • "Have I seen this before?" — duplicates, first repeated character, cycle detection by value.
  • "How many times does each thing appear?" — anagrams, majority element, character counts.
  • "Find the partner" — you have x and you need whether target - x exists. Store what you have seen and ask the map.
  • "Group these together" — bucket items by some computed signature, like sorted letters.
  • You need a lookup by something that isn't an index — by name, by word, by coordinate pair.
  • The brute force is O(n²) and the two loops are only there to pair things up. That is the giveaway. Hash maps turn "search for it" into "ask for it".

The naive way first

Two Sum: given a list of numbers and a target, return the indices of the two numbers that add to the target. The instinct is to try every pair. 

def two_sum_slow(nums, target):
    for i in range(len(nums)):
        for j in range(i + 1, len(nums)):
            if nums[i] + nums[j] == target:
                return [i, j]
    return []

That is O(n²) — for 10,000 numbers, about 50 million additions. Look at what the inner loop is actually doing, though. Once you have fixed nums[i] = 5 and the target is 12, you are not really comparing pairs. You are searching the rest of the list for the number 7, one element at a time, and then doing it all again for the next i. Searching a list is exactly the job a hash map does in one step.

The pattern

Walk the list once. At each element, ask the map whether the partner you need has already gone by. Then add the current element to the map so it can be someone else's partner later. 

def two_sum(nums, target):
    seen = {}                        # value -> the index we saw it at

    for i, x in enumerate(nums):     # enumerate gives (index, value) pairs
        need = target - x            # the partner that would complete the pair
        if need in seen:             # O(1) question, not an O(n) scan
            return [seen[need], i]
        seen[x] = i                  # remember x for whoever comes later

    return []

The line that matters is if need in seen. That single question replaces the entire inner loop of the naive version. Read the whole loop as: "is my partner already behind me? if not, take a seat and wait for them."

The ordering matters too. You check before you insert. If you inserted first, then for target = 10 and x = 5, the number 5 would find itself in the map and report a pair made of one element used twice.

Every element gets stored once and asked about once. That is the whole trade: a bit of memory (the seen dict) bought us a whole loop's worth of time.

Variations

A set, for pure membership

When you do not care where you saw something, only whether, use a set. It is the same O(1) lookup with no values stored. 

def contains_duplicate(nums):
    seen = set()
    for x in nums:
        if x in seen:
            return True
        seen.add(x)
    return False

This matters more than it looks: x in some_list is O(n) because Python walks the list, but x in some_set is O(1). Swapping a list for a set in a membership check is often the entire optimisation.

Counting

To count occurrences, use the key as the thing and the value as the tally. dict.get(k, 0) returns 0 instead of crashing when the key is new. 

def is_anagram(s, t):
    if len(s) != len(t):
        return False
    counts = {}
    for ch in s:
        counts[ch] = counts.get(ch, 0) + 1
    for ch in t:
        if counts.get(ch, 0) == 0:
            return False             # t has a letter s doesn't have enough of
        counts[ch] -= 1
    return True

Python's collections.Counter does this for you: Counter(s) == Counter(t) is the one-liner. Write the loop once so you understand it, then use Counter.

Grouping by a computed key

Bucket items by a signature you compute from them. All anagrams of each other share the same sorted letters, so sorted letters is the key and the bucket is a list. 

from collections import defaultdict

def group_anagrams(words):
    groups = defaultdict(list)       # a missing key auto-creates an empty list
    for w in words:
        key = "".join(sorted(w))     # "eat" and "tea" both become "aet"
        groups[key].append(w)
    return list(groups.values())

Hash map plus another structure

The map is often half of a solution. An LRU cache is a dict for O(1) lookup plus a doubly linked list for O(1) reordering. Sliding window problems use a dict of counts inside the window. Prefix sum problems use a dict of "running total seen at index". When one structure gets you halfway, ask what a hash map could bolt on.

Common mistakes

Unhashable keys. Keys must be immutable, so lists and dicts cannot be keys — d[[1, 2]] = 3 raises TypeError: unhashable type: 'list'. Convert to a tuple first: d[(1, 2)] = 3. Same for sets: use frozenset, or a sorted tuple, when you need a set-like key.
Storing the value when you needed the index. Two Sum asks for indices, so the dict must be value -> index. Getting this backwards is the single most common Two Sum bug, and it only shows up on inputs where the values are not conveniently equal to their positions.
Inserting before you check. Add the current element to the map after asking about its partner, or an element will match itself. If a problem genuinely allows the same value twice at two different indices, the check-then-insert order handles that correctly on its own.
Assuming hash maps are always O(1). The constant time is an average. If many keys hash to the same shelf they pile up and lookups degrade toward O(n). For ordinary interview inputs this never bites, but it is why the honest answer is "O(1) on average, O(n) worst case".

Complexity

  • Time: O(n) for one pass, because each of the n elements costs one O(1) lookup and one O(1) insert. Worst case O(n²) if every key collides, which essentially never happens in practice.
  • Space: O(n) — in the worst case you store every element before finding the answer. This is the trade: you spend memory to stop re-scanning.
