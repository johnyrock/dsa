Prefix Sums, Explained

Precompute running totals once so that any range sum, or product, becomes a single subtraction.

The core idea

Motorways have mile markers. If someone asks how far it is from marker 12 to marker 30, you do not drive the road and count — you subtract: 30 − 12 = 18. The markers did the work once, in advance, so every distance question afterwards costs one subtraction.

A prefix sum is exactly that: an array of mile markers for your numbers. prefix[i] holds the total of everything before index i. Once you have it, the sum of any contiguous stretch — "contiguous" meaning the elements sit next to each other with no gaps — is a single subtraction.

Why it's fast: you pay O(n) once to build the markers, then every range question costs O(1) instead of O(length of the range). Ten thousand questions on a big array go from tens of millions of additions to ten thousand subtractions.

How to recognise it

Prefix sums are worth reaching for when:

  • You are asked the same kind of question many times — "the sum from i to j", asked over and over with different i and j.
  • The answer involves a subarray total: count subarrays summing to k, find a subarray with a given sum, split an array into equal-sum halves.
  • You need "everything before me" or "everything after me" for each position. That works for products and running minimums too, not just sums.
  • A sliding window would fail because the array contains negative numbers, so growing the window does not reliably grow the sum. A sliding window needs that monotonic behaviour; prefix sums do not.
  • You want to apply many range updates — "add 3 to everything between index 2 and 7" — and only read the array at the end.

The naive way first

Say you must answer many "what is the sum of nums[i..j]?" questions. The obvious version walks the range each time: 

def range_sum_slow(nums, i, j):
    total = 0
    for k in range(i, j + 1):
        total += nums[k]
    return total

One call is O(j − i + 1), which is fine. The problem is q calls: that is O(n·q), and for 10,000 queries on a 10,000-element array it is 100 million additions.

Here is the wasted work. Asking for the sum of nums[0..99] and then the sum of nums[0..100] re-adds the same first hundred numbers. Every query redoes almost all of the previous query's arithmetic. Nothing is remembered between calls.

The pattern

Build the markers once. Note the deliberate off-by-one: prefix has n + 1 entries and prefix[0] = 0, the sum of no elements at all. That extra leading zero is what makes queries that start at index 0 work without a special case. 

def build_prefix(nums):
    prefix = [0]                       # prefix[0] = the sum of nothing = 0
    for x in nums:
        prefix.append(prefix[-1] + x)  # each entry = the previous one, plus x
    return prefix

def range_sum(prefix, i, j):
    return prefix[j + 1] - prefix[i]   # everything up to j, minus everything before i

The line that matters is prefix[j + 1] - prefix[i]. Read it as two overlapping totals cancelling. prefix[j + 1] is "everything from the start through j"; prefix[i] is "everything from the start through i − 1". Subtract, and the shared front half vanishes, leaving exactly the slice you wanted. The j + 1 is there because prefix[j] stops before j, and you want j included.

A memory aid for the shift: prefix[k] answers "how many elements have I passed, and what did they add up to?" — prefix[3] means three elements consumed. Index into it with a count, not a position.

Notice what happened at step 6. Building the marker for the last element cost one addition, because it reused the marker before it. The whole table is n additions total. And notice the query: we never touched nums at all. The 4, 1 and 5 were added together back at build time, and the subtraction just cancelled out the 3 + 1 that we did not want.

Sanity-check the edges. The sum of nums[0..5] is prefix[6] - prefix[0] = 23 - 0 = 23, the whole array. The sum of nums[3..3] is prefix[4] - prefix[3] = 9 - 8 = 1, the single element. Both fall out without an if.

Variations

Prefix sum plus a hash map: count subarrays summing to k

A subarray sums to k exactly when two prefix sums differ by k. So as you scan, ask "have I seen the running total running - k before?" A hash map of how many times each running total occurred answers that in O(1), turning an O(n²) pair search into one pass. This works with negative numbers, which is why a window cannot replace it. 

def subarray_sum_count(nums, k):
    counts = {0: 1}       # one "empty prefix" with running total 0
    running = 0
    answer = 0
    for x in nums:
        running += x
        answer += counts.get(running - k, 0)   # earlier prefixes that close a k-sum
        counts[running] = counts.get(running, 0) + 1
    return answer

The {0: 1} seed is not decoration. It is what lets a subarray that starts at index 0 be counted, because such a subarray needs "the empty prefix" as its left boundary.

Prefix and suffix together

The same idea runs backwards. For each position, one pass gives you the product of everything to its left and a second pass multiplies in everything to its right — which is Product of Array Except Self, solved without division. 

def product_except_self(nums):
    n = len(nums)
    result = [1] * n
    running = 1
    for i in range(n):                # left pass: product of everything before i
        result[i] = running
        running *= nums[i]
    running = 1
    for i in range(n - 1, -1, -1):    # right pass: multiply in everything after i
        result[i] *= running
        running *= nums[i]
    return result

Best prefix so far: maximum subarray

The largest subarray sum ending at position j is prefix[j + 1] minus the smallest prefix seen before it. Track that smallest as you go and you get Kadane's algorithm in prefix-sum clothing. 

def max_subarray(nums):
    best = nums[0]
    running = 0
    min_prefix = 0            # smallest prefix seen before the current position
    for x in nums:
        running += x
        best = max(best, running - min_prefix)
        min_prefix = min(min_prefix, running)
    return best

Running it in reverse: the difference array

If you have many range updates and only one read at the end, flip the pattern. Record +amount at the start of each range and -amount just past its end, then take a prefix sum of that at the very end. Each update becomes O(1) instead of O(range length). 

def apply_range_adds(n, updates):
    diff = [0] * (n + 1)
    for start, end, amount in updates:
        diff[start] += amount
        diff[end + 1] -= amount       # the +1 slot is why diff has n + 1 entries
    out, running = [], 0
    for i in range(n):
        running += diff[i]
        out.append(running)
    return out

Common mistakes

Skipping the leading zero. If prefix[0] is nums[0] instead of 0, then every query that starts at index 0 needs a special case, and you will forget it. Always size the array at n + 1 and start it with 0.
Getting the +1 on the wrong side. The inclusive range i..j is prefix[j + 1] - prefix[i], never prefix[j] - prefix[i - 1]. Test it on a range of length 1 before you trust it: i == j must give back nums[i].
Forgetting the empty prefix in the hash-map version. Starting with an empty counts = {} silently loses every answer whose subarray begins at index 0. The seed must be {0: 1}.
Rebuilding after every change. Prefix sums assume the array does not move. If the problem interleaves updates with queries, a rebuild costs O(n) per update and you are back where you started — that is what a Fenwick tree or segment tree is for.

Complexity

  • Time: O(n) to build, then O(1) per range query. Answering q queries is O(n + q) instead of O(n·q).
  • Space: O(n) for the extra array. If you only need a running total as you scan — the hash-map and Kadane variants — it drops to O(1) beyond whatever the map holds.
