Dynamic Programming, Explained

Overlapping subproblems, memoisation, and bottom-up tables, from Fibonacci to coin change.

The core idea

Imagine a class of thirty people all working through the same long homework sheet. Question 20 needs the answer to question 12. So does question 17. And question 19. Left alone, everybody re-derives question 12 from scratch every time they need it, over and over, all afternoon.

Then someone walks to the whiteboard and writes: Q12 = 47. Nobody ever computes it again. The afternoon collapses from hours to minutes, and nothing about the maths changed — only that each answer is now written down once and read many times.

Dynamic programming (DP) is that whiteboard. You take a recursive solution, notice that it keeps asking the same smaller questions — those are called overlapping subproblems — and store each answer the first time you work it out. Nothing more mysterious than that. The scary name is from the 1950s and means nothing useful.

Why it's fast: a branching recursion re-solves the same subproblem on every branch that reaches it, so the work grows like 2n. With the answers stored, each distinct subproblem is solved exactly once, so the total work becomes (number of distinct subproblems) × (work per subproblem). For climbing stairs that is n subproblems doing O(1) work each: exponential becomes linear.

DP needs one more thing to be correct, on top of overlap: optimal substructure, meaning the best answer for a big case really is built out of best answers to smaller cases. That holds far more often than not, but it is the assumption to check when a DP gives wrong answers rather than slow ones.

How to recognise it

Look for these, usually two or three at a time:

  • "How many ways…" or "what is the minimum / maximum…" over a sequence of choices. Counting and optimising are the two DP moods.
  • You can write a recursion, and it is too slow. This is the real signal. Write the honest recursive solution first, then ask which arguments repeat.
  • Each step has a small set of choices — take it or leave it, step 1 or step 2, use this coin or the next one — and a choice affects what comes after.
  • The answer for n depends on the answers for smaller n, and you can say how in one sentence. That sentence is called the recurrence, and it is 90% of the work.
  • A greedy rule looks obvious but breaks on a small counterexample. When "always take the biggest" fails, DP is usually the fix.

The naive way first

The running example is climbing stairs: there are n steps and you can climb 1 or 2 at a time. How many different ways are there to reach the top?

Think about the last move. You arrived at step n either from step n - 1 (a 1-step) or from step n - 2 (a 2-step), and those are different routes. So the number of ways to reach n is the number of ways to reach n - 1 plus the number of ways to reach n - 2. Straight into code: 

def climb_slow(n):
    if n <= 2:                       # 1 step: one way. 2 steps: two ways (1+1, or 2).
        return n
    return climb_slow(n - 1) + climb_slow(n - 2)

climb_slow(6)    # 13, correct
climb_slow(30)   # 1346269, correct, after 1,664,079 function calls

This is right, and it is unusable. Draw the calls for climb_slow(5):

climb(5)
 |
 |-- climb(4)
 |     |-- climb(3)
 |     |     |-- climb(2) = 2
 |     |     \-- climb(1) = 1
 |     \-- climb(2) = 2          <- again
 |
 \-- climb(3)                    <- the WHOLE subtree, recomputed
       |-- climb(2) = 2          <- again
       \-- climb(1) = 1

Nine calls to answer a question about five stairs. climb(3) is computed twice and climb(2) three times, and each duplicate drags its own subtree along with it. The waste compounds: climb_slow(6) takes 15 calls, and climb_slow(30) takes 1,664,079. There are only 30 different questions being asked. The other million-odd calls are the same handful of answers, recomputed.

The pattern

There are two ways to write down the answers, and they compute exactly the same thing. Start with top-down, because it is the naive recursion plus three lines: 

def climb_memo(n, memo=None):
    if memo is None:                 # fresh cache per top-level call (see the gotchas)
        memo = {}
    if n <= 2:
        return n
    if n in memo:                    # ALREADY SOLVED: read it off the whiteboard
        return memo[n]
    memo[n] = climb_memo(n - 1, memo) + climb_memo(n - 2, memo)   # solve once, write it down
    return memo[n]

The line that matters is if n in memo: return memo[n]. Read it as: "have I been asked this exact question before? Then I already know." That one check is what prunes the entire duplicate subtree in the diagram above — the second climb(3) returns instantly instead of expanding. Storing answers like this is called memoisation.

Bottom-up throws away the recursion entirely. If you know you will need every answer from 1 up to n, just compute them in order, smallest first, into a list: 

def climb(n):
    if n <= 2:
        return n
    ways = [0] * (n + 1)             # ways[i] = number of ways to reach step i
    ways[1], ways[2] = 1, 2          # base cases
    for i in range(3, n + 1):
        ways[i] = ways[i - 1] + ways[i - 2]     # the recurrence, as a loop
    return ways[n]

Same recurrence, same answers, no call stack. Read the loop body next to the recursive line and confirm they say the identical sentence — ways[i - 1] + ways[i - 2] versus climb(n - 1) + climb(n - 2). Every bottom-up DP is a recursion turned inside out like this.

How to actually write one: (1) say the recurrence in English; (2) write the slow recursion and check it on a tiny input; (3) add a memo; (4) if you want, flip it to a table. Do not try to write the table first. Almost every wrong DP is someone who skipped steps 1 and 2.

Climbing stairs is Fibonacci in a costume, and quite a few DP problems turn out to be something familiar once the table is on the page.

Variations

Rolling the table up to two variables

Look at the loop: ways[i] only ever reads the two cells behind it. The other n − 2 cells are dead weight. Keep two variables instead and the space drops from O(n) to O(1). 

def climb_o1(n):
    if n <= 2:
        return n
    prev, cur = 1, 2                 # ways to reach step 1 and step 2
    for _ in range(3, n + 1):
        prev, cur = cur, prev + cur  # slide the window forward one step
    return cur

Do this after the table version works, never before. It is an optimisation, not a starting point.

Minimising over choices: coin change

Same machinery, different recurrence. To make amount a with the fewest coins, try every coin as the last one you add and take the best result. best[a - c] + 1 reads as: "however few coins make a - c, plus this one." 

def coin_change(coins, amount):
    INF = amount + 1                              # bigger than any real answer
    best = [INF] * (amount + 1)
    best[0] = 0                                   # zero coins make zero
    for a in range(1, amount + 1):
        for c in coins:
            if c <= a:
                best[a] = min(best[a], best[a - c] + 1)
    return best[amount] if best[amount] != INF else -1

coin_change([1, 3, 4], 6)    # 2  (3 + 3)
coin_change([1, 2, 5], 11)   # 3  (5 + 5 + 1)
coin_change([2], 3)          # -1, impossible

The table for [1, 3, 4] and amount 6 fills in as [0, 1, 2, 1, 1, 2, 2]. Notice best[6] = 2 while grabbing the biggest coin first would give you 4 + 1 + 1 = three coins. That gap is exactly why this problem is DP and not greedy.

Running best in one pass: Kadane

Some DPs need no table at all, because the state is a single number. For the largest sum of any contiguous run (contiguous = next to each other, no gaps), the question at each element is only: does the run so far still help me, or should I start fresh here? 

def max_subarray(nums):
    best = cur = nums[0]
    for x in nums[1:]:
        cur = max(x, cur + x)        # start fresh at x, or extend the run
        best = max(best, cur)
    return best

max_subarray([-2, 1, -3, 4, -1, 2, 1, -5, 4])   # 6

Two-dimensional tables

When the state needs two numbers, the table becomes a grid. Counting paths through an rows × cols grid moving only down or right: 

def unique_paths(rows, cols):
    grid = [[1] * cols for _ in range(rows)]   # top row and left column: exactly one path
    for r in range(1, rows):
        for c in range(1, cols):
            grid[r][c] = grid[r - 1][c] + grid[r][c - 1]
    return grid[rows - 1][cols - 1]

unique_paths(3, 7)   # 28

Edit distance, longest common subsequence, and 0/1 knapsack are all this shape: two indices, so a grid, filled in an order that guarantees the cells you read are already written.

Common mistakes

A memo key that leaves out an argument. If your function is f(i, remaining), the key must be (i, remaining) — not just i. Keying coin change on the coin index alone returns a wrong answer for coins [1, 3, 4] and amount 6: the first answer stored under i gets handed back for a completely different remaining. Rule: every argument that changes between calls belongs in the key.
Initialising a minimum table with 0. For a "fewest / smallest" DP, an empty cell must start at something worse than any real answer — float("inf"), or a sentinel like amount + 1 — or min() will happily pick the placeholder and every answer becomes 0. The mirror image applies to maximum problems.
Off-by-one on the table size and the base cases. If ways[n] is the answer, the list needs n + 1 slots, and index 0 usually stands for "nothing at all" rather than "the first item". Write out what one cell means in a comment before filling any of them; most DP bugs are really "I had two different meanings for the same index".
def f(n, memo={}). In Python a default argument is created once, when the function is defined, and then shared by every call for the rest of the program. As a cache it appears to work — it is fast, and for a pure function like this the values stay correct — but it never empties, and the moment the answers depend on anything else (a different coin list, a different input array) it starts returning results computed for a completely different problem. Use memo=None and create the dict inside, or @functools.cache.

Complexity

  • Time: (number of distinct states) × (work done per state). Climbing stairs: n states, O(1) work each, so O(n). Coin change: amount states, each trying every coin, so O(amount × number of coins). Counting states is the fastest way to sanity-check a DP before you run it.
  • Space: the size of the table — O(n) for a 1-D table, O(rows × cols) for a grid — plus O(depth) for the call stack if you went top-down. Rolling the table up to a couple of variables often gets you to O(1). See time & space complexity.
