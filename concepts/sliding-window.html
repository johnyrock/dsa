Sliding Window, Explained

A window that grows on the right and shrinks on the left, for any "longest or shortest contiguous chunk" question.

The core idea

Picture a long shelf of books and a cardboard tube you look through. The tube shows you a few books at a time. You slide it to the right one book at a time: a new book appears on the right edge, and if the tube is getting too full, you let books fall off the left edge. At no point do you pick the whole shelf up and start counting again — you only ever adjust the two edges.

That tube is the window. A sliding window is a pair of indices, left and right, marking off a contiguous chunk of an array or string. "Contiguous" just means the elements are next to each other with no gaps: [3, 4, 1] out of [9, 3, 4, 1, 7] is contiguous, [9, 4, 7] is not. You push right forward to grow the window, and pull left forward to shrink it.

Why it's fast: left and right only ever move forward, never back. Each of them travels the length of the input at most once, so the whole scan costs about 2n steps — O(n) — even though the loop looks nested.

How to recognise it

The problem is probably a sliding window if you see:

  • The word "subarray", "substring", or "consecutive". All three mean contiguous, and contiguous is the window's whole reason to exist.
  • "Longest" or "shortest" or "maximum" or "minimum" attached to that chunk. You are looking for the best window, not the best single element.
  • A rule the chunk must obey: no repeated characters, sum at least k, at most two distinct letters. That rule is what tells the window when to shrink.
  • A fixed size handed to you: "every subarray of length k". That is the easy flavour — the window never changes size, it just slides.

If the chunk is allowed to have gaps, it is not a sliding window. Reach for dynamic programming or a hash map instead.

The naive way first

Take the classic: find the length of the longest substring with no repeated characters. The obvious approach is to try every possible starting point, and from each one walk right until you hit a repeat. 

def longest_unique_slow(s):
    best = 0
    for i in range(len(s)):
        seen = set()
        for j in range(i, len(s)):
            if s[j] in seen:
                break
            seen.add(s[j])
            best = max(best, j - i + 1)
    return best

This is O(n²): roughly n starting points times n characters each. For a string of 10,000 characters that is about 50 million steps.

Look at where the work is thrown away. When the loop starting at i = 0 gets as far as "abc" and then breaks, it forgets everything. The next loop starts at i = 1 and re-reads "bc" from scratch, even though we just looked at those exact characters and already know they are fine. Every restart re-walks ground we have already covered.

The pattern

The fix is to never restart. Keep the previous window and repair it. When the new character on the right breaks the rule, shrink from the left until the rule holds again. 

def longest_unique(s):
    seen = set()          # what is inside the window right now
    left = 0              # the window is s[left] .. s[right]
    best = 0
    for right in range(len(s)):
        while s[right] in seen:      # the new character breaks the rule
            seen.remove(s[left])     # so drop the leftmost one
            left += 1                # and pull the left edge in
        seen.add(s[right])           # now it is safe to add
        best = max(best, right - left + 1)
    return best

The line that matters is while s[right] in seen:. Read it as a repair loop, not a search loop: "the window is currently broken; keep dropping elements off the left until it is legal again." Everything else is bookkeeping. The outer for always moves right forward by one; the inner while moves left forward by as much as it needs to and no more.

Why a nested loop is still O(n): left starts at 0, only increases, and can never pass right. So across the entire run, the inner while body executes at most n times in total — not n times per outer step. Count total pointer movement, not loop nesting.

Notice what happened at right = 3. The incoming b clashed with the b at index 1, so the window had to shrink past that old b — index 2, not index 1. It dropped two characters in one step, and that is fine: the inner while runs as many times as needed. But left did not jump backwards, and it never will.

Then notice right = 4. The character is a, and there is an a in the string at index 0 — but index 0 is no longer inside the window, so seen does not contain it and nothing shrinks. The set only ever describes the current window. That is exactly why the set is kept in sync on both edges.

Variations

Fixed-size window

When the problem hands you the size, the window never grows or shrinks — it just slides. Add the element entering on the right, subtract the one leaving on the left, and you get each window's sum in one operation instead of k. 

def max_sum_of_k(nums, k):
    window = sum(nums[:k])       # the first window, computed the slow way once
    best = window
    for right in range(k, len(nums)):
        window += nums[right] - nums[right - k]   # add one, drop one
        best = max(best, window)
    return best

Shrink-to-smallest

"Longest" problems shrink only when the window is illegal. "Shortest" problems flip it: shrink while the window is legal, recording the size each time, because a smaller valid window is a better answer. This needs non-negative numbers, so that shrinking always lowers the total. 

def min_window_at_least(nums, target):
    left, total, best = 0, 0, float("inf")
    for right in range(len(nums)):
        total += nums[right]
        while total >= target:            # valid, so try to make it smaller
            best = min(best, right - left + 1)
            total -= nums[left]
            left += 1
    return 0 if best == float("inf") else best

Jump the left edge instead of stepping it

Instead of a set plus a while loop, you can store the last index where each character was seen and move left in one hop. It is the same idea, slightly faster, and easier to get wrong — you must ignore a remembered index that has already fallen out of the window. 

def longest_unique_jump(s):
    last = {}                 # character -> the last index it appeared at
    left, best = 0, 0
    for right, ch in enumerate(s):
        if ch in last and last[ch] >= left:   # this guard is the whole trick
            left = last[ch] + 1
        last[ch] = right
        best = max(best, right - left + 1)
    return best

A window of size one: running best-so-far

Some problems are the degenerate case where you only need one number about everything to the left. Best Time to Buy and Sell Stock is really "for each day, what is the cheapest price so far?" — a single variable trailing behind the scan. 

def max_profit(prices):
    cheapest = prices[0]
    best = 0
    for price in prices[1:]:
        best = max(best, price - cheapest)   # sell today, having bought at the low
        cheapest = min(cheapest, price)
    return best

Common mistakes

Forgetting to update the state when the left edge moves. If you do left += 1 but never seen.remove(...) or total -= ..., your bookkeeping describes a window that no longer exists. Every change to left or right needs a matching change to whatever you are tracking.
Off-by-one in the window length. The window covers indices left through right inclusive, so its length is right - left + 1, not right - left. Sanity-check it: when left == right the window holds one element.
Recording the best answer in the wrong place. For "longest", record after the shrink loop, when the window is valid again. For "shortest", record inside the shrink loop, while it is still valid. Getting these backwards produces answers that look almost right.
Moving left backwards. Any line that sets left to something smaller than its current value breaks the O(n) guarantee and usually the correctness too. If you use the jump variant, guard it: left = max(left, last[ch] + 1).

Complexity

  • Time: O(n). Each of left and right advances at most n times over the whole run, and each advance does O(1) work.
  • Space: O(k), where k is how many distinct things the window can hold — the size of the set or counter. For lowercase letters that is at most 26, so effectively O(1); for a plain running sum it really is O(1).
