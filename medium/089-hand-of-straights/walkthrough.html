Medium · Greedy · LeetCode #846

Hand of Straights, narrated

Scroll through the thinking, from repeatedly pulling runs out of a sorted list to a count map swept from the smallest value upward, with the state of the algorithm shown alongside.

Pattern used Greedy the smallest remaining card can only start a group, so open its groups and consume the run

STEP 1

The problem

You hold a hand of integer cards, hand, and want to deal all of them into groups of exactly groupSize cards where every group is a run of consecutive values, like [2,3,4]. A card belongs to exactly one group; none may be left over.

Return whether such a grouping exists. You are not asked to output the groups, only whether the deal is possible.

Running example: hand = [1,2,3,6,2,3,4,7,8], groupSize = 3. The answer is true: [1,2,3], [2,3,4], [6,7,8].

Nine cards and groups of three means exactly three groups. If the total were not divisible by groupSize the answer would be false before looking at a single value, and that check is the first line of the solution.

STEP 2

Brute force: pull runs out of a sorted list

Sort the hand, take the first card, and try to remove card + 1, card + 2, ... from the list one at a time; repeat until the list is empty or a removal fails.

cards = sorted(hand)while cards:    first = cards.pop(0)    for c in range(first + 1, first + group_size):        if c not in cards:            return False        cards.remove(c)return True

On the sorted example [1,2,2,3,3,4,6,7,8] this pulls 1, removes 2 and 3, pulls 2, removes 3 and 4, pulls 6, removes 7 and 8: true. The reasoning is already right; the cost is not. Each in and remove scans the list, so every card costs O(n) to place and the whole thing is O(n²).

What the list is doing badly is answering "how many copies of value c do I have left?" A counter answers that in O(1).

STEP 3

The key insight: the smallest card has no choice

Look at the smallest value still unplaced. It cannot be the second or third card of any group, because that would need a smaller card in front of it, and there is none. So it must start a group, and that group must be card, card + 1, ..., card + groupSize - 1. There is nothing to decide.

In the example the smallest value is 1. Its only possible group is [1,2,3]. After removing that, the smallest value is 2, whose only possible group is [2,3,4]. And so on.

Two refinements make it fast. Keep a Counter instead of a list, and walk the distinct values in ascending order with sorted(count). If a value has need copies left, all need of them must start groups, so consume need copies of each of the next groupSize values in one go. If any of those values has fewer than need copies, some group cannot be finished, and no other arrangement could have rescued it: False.

STEP 4

The approach

  • if len(hand) % group_size: return False: the cards must divide evenly into groups.
  • count = Counter(hand): copies of each value still to place.
  • for card in sorted(count): visit distinct values smallest first.
  • need = count[card]; if it is 0 the value was already consumed as the tail of earlier groups, so skip it.
  • for c in range(card, card + group_size): the run each new group needs.
  • if count[c] < need: return False, otherwise count[c] -= need.
  • return True: every card was placed.

The panel shows the counter as chips, the groups formed so far as rows, and the current card and need.

STEP 5

Trace it: card = 1

9 % 3 == 0, so we continue. The counter is {1: 1, 2: 2, 3: 2, 4: 1, 6: 1, 7: 1, 8: 1} and sorted(count) is [1, 2, 3, 4, 6, 7, 8].

card = 1, need = 1. The run is range(1, 4) = 1, 2, 3. Each has at least 1 copy, so subtract 1 from each: the counter becomes {1: 0, 2: 1, 3: 1, 4: 1, ...}, and the first group [1,2,3] is formed.

STEP 6

Trace it: card = 2

card = 2, need = count[2] = 1: one copy of 2 was not used by the first group, so it starts a group of its own. The run is 2, 3, 4. Counts are 1, 1, 1, all at least need, so each drops to 0. Group [2,3,4] is formed.

The sweep now reaches card = 3 with need = 0, then card = 4 with need = 0. Both were consumed as tails of earlier groups, so if need: skips them. This is why the loop over sorted(count) does not need to know which values have already been swallowed.

STEP 7

Trace it: card = 6, and the answer

card = 6, need = 1. The run 6, 7, 8 has one copy each, so all three go to 0 and group [6,7,8] is formed.

card = 7 and card = 8 have need = 0 and are skipped. The loop finishes and the function returns True. Every value in the counter is 0, which is what "every card placed" looks like.

The list version did the same three pulls but paid a scan for each removal. The counter did each subtraction in O(1), and each card was decremented exactly once.
STEP 8

Where this goes wrong: direction and the size of the bite

Sweeping from the largest card but still building upward. Write sorted(count, reverse=True) and the first card examined is 8, whose "group" would be 8, 9, 10. count[9] is 0, which is less than need = 1, so the function returns false for a hand that clearly works. The argument that a card has no choice only holds for the smallest remaining card when groups extend upward.

Subtracting 1 instead of need. Write count[c] -= 1 and multiple groups opened from the same value are under-counted. On [1,1,2,2,3,3] with groupSize = 3 the two 1s open two groups but only one 2 and one 3 are consumed; a 1, a 2 and a 3 remain unplaced, the sweep reaches card = 2 with need = 1, cannot find a 4 and returns false. The answer is true.

Testing count[c] == 0 instead of count[c] < need. A value with one copy when two groups need it slips through, its count goes negative, and on [1,1,2,3,4,4] with groupSize = 2 the function returns true instead of false.

Smallest first, run upward, consume need copies of every value in the run, and compare against need, not zero.
STEP 9

Time and space

Building the counter is O(n). Sorting the distinct values is O(n log n). The inner loop decrements each card exactly once across the whole run, so the sweep itself is O(n). Total O(n log n) time, O(n) space for the counter.

ApproachTimeSpace
Sorted list with pop / removeO(n²)O(n)
Counter, sweep sorted distinct valuesO(n log n)O(n)
Counter + min-heap of remaining valuesO(n log n)O(n)

The heap variant pops the smallest value instead of pre-sorting; same bound, more code. Sweeping range(min, max + 1) instead of sorted(count) would be a mistake here, since values go up to 10⁹.

STEP 10

The final solution

  • if len(hand) % group_size: return False rejects hands that cannot split evenly.
  • count = Counter(hand) turns the hand into "copies left" per value.
  • for card in sorted(count) visits values smallest first, each once.
  • need = count[card] and if need: open all groups this value must start, or skip a value already used up.
  • for c in range(card, card + group_size) with if count[c] < need: return False and count[c] -= need consumes the run or proves it impossible.
  • return True when every card has been placed.
One-line summary to remember: the smallest unplaced card must start a group, so count the cards, sweep values upward, and consume each run in one bite.
