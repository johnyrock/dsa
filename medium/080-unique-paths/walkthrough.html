Unique Paths, narrated

Scroll through the thinking, from enumerating every right/down sequence to a 2-D table and then a single rolling row, with the state of the algorithm shown alongside.

Pattern used Dynamic Programming paths(r, c) = paths(r−1, c) + paths(r, c−1), one rolling row

STEP 1

The problem

A robot sits in the top-left cell of an m × n grid. It may move right or down, one cell at a time, and wants the bottom-right cell. Count the distinct routes.

Running example: m = 3, n = 7. The answer is 28.

Two routes are different if their move sequences differ. Every route is 2 downs and 6 rights in some order, which is a strong hint that the answer is a combination count — but the table method below is what generalises to obstacles and costs, so it is the one to learn first.

Only a count is asked for. We never list the routes, so the state per cell can be a single number.

STEP 2

First instinct: recurse on the two moves

From any cell, either move right or move down, and add up the routes from each. Reaching the last row or column leaves only one way home.

def paths(r, c):    if r == m - 1 or c == n - 1:        return 1    return paths(r + 1, c) + paths(r, c + 1)

Correct, and exponential: each call branches twice, and the depth is m + n − 2, so roughly O(2^(m+n)). For 100 × 100 it never returns.

The waste is visible on the example: paths(1, 1) is reached by right-then-down and by down-then-right, and both callers recompute the entire sub-grid below it. Deeper cells are recomputed thousands of times.

STEP 3

The key idea: how did the robot get here?

Flip the direction of the question. Instead of "how many routes from this cell to the end", ask "how many routes from the start to this cell". The robot's last move into cell (r, c) was either a down from (r − 1, c) or a right from (r, c − 1). There is no third way in.

paths(r, c) = paths(r − 1, c) + paths(r, c − 1). Every cell in the first row and the first column is 1: the only route there is a straight line.

Fill the table row by row, left to right, and both neighbours are already final when a cell needs them. The bottom-right cell is the answer.

Then notice what each row reads: only the row directly above it, and the cell just to its left in the same row. So one row can be reused. If row[c] still holds the value from the row above when we do row[c] += row[c − 1], the sum is exactly "above plus left".

STEP 4

The approach, line by line

  • row = [1] * n — the first row of the table: one route to every cell.
  • for _ in range(1, m) — build rows 1 through m − 1; the seed already is row 0.
  • for c in range(1, n) — column 0 stays 1, so start at column 1.
  • row[c] += row[c − 1] — old row[c] is "from above", row[c − 1] is already "from the left".
  • return row[n − 1] — the bottom-right cell after the last row.
STEP 5

Trace it: the seed row

row = [1, 1, 1, 1, 1, 1, 1]. This is row 0 of the table: the robot reaches any cell in the top row only by moving right the whole way, so each has exactly one route.

Column 0 of every later row will also stay 1, for the mirror reason — only straight down reaches it — and that is why the inner loop starts at c = 1 and never touches row[0].

STEP 6

Trace it: row 1

First pass of the outer loop. c = 1: row[1] = 1 + row[0] = 1 + 1 = 2. c = 2: row[2] = 1 + row[1] = 1 + 2 = 3. c = 3: 1 + 3 = 4. And so on: each cell takes the 1 it already held (the route from above) and adds the cell to its left.

After the pass, row = [1, 2, 3, 4, 5, 6, 7]. Check one by hand: cell (1, 2) is reached by DRR, RDR, RRD — three routes.

STEP 7

Trace it: row 2, the answer

Second and last pass. c = 1: row[1] = 2 + 1 = 3. c = 2: row[2] = 3 + 3 = 6. c = 3: 4 + 6 = 10. c = 4: 5 + 10 = 15. c = 5: 6 + 15 = 21. c = 6: 7 + 21 = 28.

row = [1, 3, 6, 10, 15, 21, 28], and row[n − 1] = row[6] = 28 is returned. The full 3 × 7 table is shown on the right; the code only ever held one row of it.

The recursion would have made 55 calls to reach 28, and far more on a larger grid. The row did twelve additions.
STEP 8

Where this goes wrong: one row too many, or zeros

Looping range(m) instead of range(1, m). The seed row already is row 0, so the outer loop must run m − 1 times. Run it m times and you compute a fourth row: [1, 4, 10, 20, 35, 56, 84]. The function returns 84 — the answer for a 4 × 7 grid — instead of 28. It is a plausible-looking number, which is what makes it nasty.

Seeding with zeros. row = [0] * n gives the table no starting routes. Every row[c] += row[c − 1] adds zero to zero and the function returns 0.

Starting the inner loop at c = 0. row[0] += row[−1] silently reads the last cell in Python and corrupts column 0, which must stay 1.

Count the outer iterations for m = 1: there must be zero, and the seed row is returned untouched.
STEP 9

Time and space

One addition per cell of the grid: O(m × n) time. One row of length n: O(n) space — or O(min(m, n)) if you roll along the shorter side.

ApproachTimeSpace
Plain recursionO(2^(m+n))O(m + n) stack
2-D tableO(m × n)O(m × n)
Rolling rowO(m × n)O(n)
Binomial C(m+n−2, m−1)O(min(m, n))O(1)

The closed form exists because every route is a fixed multiset of moves. The table is still the interview baseline because it survives obstacles and per-cell costs unchanged in shape.

STEP 10

The final solution

Six lines. Every one of them maps to a step above.

  • row = [1] * n — the top row of the table, one route per cell.
  • for _ in range(1, m) — produce each remaining row from the one before.
  • for c in range(1, n) — leave column 0 at 1.
  • row[c] += row[c - 1] — above plus left, in one in-place update.
  • return row[n - 1] — the bottom-right corner.
One-line summary to remember: routes into a cell are routes into the cell above plus routes into the cell on its left; a single row updated left to right holds the whole table.
