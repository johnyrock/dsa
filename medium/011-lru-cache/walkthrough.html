LRU Cache, narrated

Scroll through the thinking, from a dictionary with timestamps to a hash map pointing into a doubly linked list ordered by recency, with the state of the cache shown alongside.

STEP 1

The problem

Build a cache with a fixed capacity. get(key) returns the stored value or −1. put(key, value) stores or updates. When a put would exceed the capacity, throw out the entry that has gone longest without being touched.

Both a get hit and a put count as touching the key. And both operations must be O(1). That last requirement is the whole problem.

Running example, capacity 2: put(1,1), put(2,2), get(1) → 1, put(3,3) evicts 2, get(2) → −1, put(4,4) evicts 1, get(1) → −1, get(3) → 3, get(4) → 4.
STEP 2

First instinct: a dictionary plus timestamps

Keep key → (value, last_used) in a dictionary and a counter that ticks on every operation. get and put update the timestamp. On eviction, scan every entry for the smallest timestamp.

def put(self, key, value):    if key not in self.d and len(self.d) == self.cap:        oldest = min(self.d, key=lambda k: self.d[k][1])        del self.d[oldest]    self.d[key] = (value, self.tick()); ...

get is O(1), but that min scan makes eviction O(n). With 200,000 operations on a full cache of 3,000 entries that is hundreds of millions of comparisons. The requirement says O(1) for both.

STEP 3

Reframe: keep the entries in recency order

The scan exists because the dictionary has no order. Suppose instead the entries sit in a sequence sorted by last use: most recent at the front, least recent at the back. Then the eviction victim is always the last element, no search needed.

Maintaining that order costs one operation per touch: move the touched entry to the front. So we need a sequence that supports, in O(1):

  • remove an element from the middle,
  • insert at the front,
  • remove from the back.

A Python list fails the first one: removing from the middle is O(n). A doubly linked list does all three in O(1), provided you already hold a reference to the node.

STEP 4

The key idea: the dictionary points at nodes

Pair the two structures. The dictionary maps key → node, so a lookup lands directly on the node's position in the recency list. Unlink it (its prev and next are right there), push it to the front, done. The list gives order; the dictionary gives the "where is it" the list cannot.

  • Two sentinel nodes, head and tail, never removed. The most recent real node is head.next, the least recent is tail.prev, and no insert or unlink ever has to check for None.
  • Each node stores its key as well as its value, so when tail.prev is evicted we can also del nodes[key].
  • Two helpers, _unlink and _push_front, and every operation is a short composition of them.
STEP 5

Trace it: fill the cache, then a hit

put(1,1): new key, size 0 < 2, create node, index it, push front. List: 1. put(2,2): same. List: 2 → 1, with 1 now at the back.

get(1): dictionary hit. Unlink node 1 from the back, push it to the front. List: 1 → 2. Return 1. The read reordered the list, which is exactly the point: 1 is now safe, 2 is the next victim.

STEP 6

Trace it: eviction

put(3,3): new key, and the size is already 2. tail.prev is node 2. Unlink it and delete key 2 from the dictionary, using the key stored on the node. Then create node 3 and push it front. List: 3 → 1.

get(2) misses: −1. put(4,4) evicts 1 the same way. List: 4 → 3. get(1) → −1, get(3) → 3 (list becomes 3 → 4), get(4) → 4 (list becomes 4 → 3).

Every operation touched a constant number of pointers and one dictionary entry. Nothing was scanned.
STEP 7

The pitfall: updating an existing key

put on a key that is already present must update in place: change the node's value, move it to the front, and return. It must not create a second node, and it must not run the eviction check, because the size does not change.

Check key in nodes before the capacity check. Evict first and you can throw out a live entry to make room for an update that needed no room. Insert a fresh node and the dictionary points at the new one while the old one lingers in the list, so the size count is wrong forever.

Two more: a get hit that forgets to move the node to the front lets hot keys get evicted, and a node without a stored key cannot be removed from the dictionary when it falls off the tail.

STEP 8

Time and space

get: one dictionary lookup, one unlink (four pointer writes), one push-front (four pointer writes). put: the same plus at most one eviction, which is another unlink and a dictionary delete. O(1) for both.

One node and one dictionary entry per cached key: O(capacity) space.

Python's OrderedDict is this exact structure under the hood, with move_to_end and popitem(last=False). Mention it, then show you can build it.

STEP 9

The final solution

About forty lines, but only four ideas.

  • Node holds key, val, prev, next; the key is there for eviction.
  • head and tail sentinels remove every empty-list special case.
  • _unlink and _push_front are the only pointer surgery; get and put compose them.
  • put checks "already present" first, then "full", then inserts.
One-line summary to remember: the map finds the node, the list remembers the order, and the victim is always the node before the tail.
