Non-overlapping Intervals, narrated

Scroll through the thinking, from trying every subset of intervals to sorting by end time and keeping whichever one finishes first, with the intervals drawn on a timeline alongside.

Pattern used Intervals sort by end; keep an interval if it starts at or after the last kept end, otherwise count it removed

STEP 1

The problem

You are given intervals as [start, end] pairs. Remove as few of them as possible so that none of the survivors overlap, and return how many you removed. Two intervals that merely touch, like [1, 2] and [2, 3], are not overlapping.

Running example: intervals = [[1, 2], [2, 3], [3, 4], [1, 3]]. Remove [1, 3] and the other three sit back to back. Answer 1.

Note that the output is a count, not a list. That frees the algorithm from tracking which intervals survive; it only has to decide, for each one, whether it stays or goes.

Also note the equivalence that drives the solution: removing the fewest intervals is the same as keeping the most non-overlapping intervals. Every scheduling problem of the form "pick the most compatible activities" is this problem in disguise.

STEP 2

First instinct: try every subset of survivors

Enumerate every subset of the intervals, test whether it is pairwise non-overlapping, and remember the largest one that is:

best = 0for mask in range(1 << n):    chosen = [iv for i, iv in enumerate(intervals) if mask >> i & 1]    chosen.sort()    if all(chosen[k][0] >= chosen[k - 1][1] for k in range(1, len(chosen))):        best = max(best, len(chosen))return n - best

For four intervals that is 16 subsets. The constraint allows 10^5 intervals, and 2^100000 subsets will not finish. This is O(2ⁿ · n log n), and it ignores structure that is sitting in plain sight: intervals live on a line, and the ones that end early leave room for the ones that come after.

STEP 3

The key insight: the interval that ends earliest is always safe to keep

Among all intervals, consider the one with the smallest end. Any optimal set of survivors either contains it or contains some other interval that overlaps it. In the second case, swap that other interval out and the earliest-ending one in: the new set is the same size, and because its new member ends no later than the one it replaced, it cannot collide with anything the old member did not already collide with.

So there is always an optimal answer that keeps the earliest-ending interval. Keep it, discard everything that overlaps it, and repeat on what is left. That is a sort by end followed by a single sweep.

In the panel the intervals are now in end order: [1, 2], [2, 3], [1, 3], [3, 4]. Line 3, intervals.sort(key=lambda interval: interval[1]), is that reordering. Notice that [1, 3] has moved after [2, 3]; they share an end, and the stable sort keeps their input order, which does not matter for the count.

STEP 4

The approach: sweep in end order with prev_end

  • intervals.sort(key=lambda interval: interval[1]) puts the earliest-ending interval first.
  • prev_end = intervals[0][1]: the first interval is always kept; its end is the boundary the next kept one must clear.
  • for start, end in intervals[1:]: walk the rest in end order.
  • if start >= prev_end: prev_end = end: no conflict with what is kept, so keep it and advance the boundary.
  • else: removed += 1: it starts before the last kept interval ends, so it overlaps and must go.
  • return removed.

The dashed green line in the panel is prev_end. A bar that starts at or to the right of it is kept (green); one that starts to the left is removed (amber).

STEP 5

Trace it: keep [1, 2], then keep [2, 3]

After the sort, intervals[0] = [1, 2], so prev_end = 2. It is kept without a comparison; nothing ends before it, so nothing can be a better first choice.

Next is [2, 3]: start = 2, and 2 >= 2 is true. The intervals touch at 2, which is allowed, so keep it and set prev_end = 3. removed is still 0.

The boundary moved from 2 to 3. Everything kept so far ends at or before 3, and any future survivor must start at or after it.

STEP 6

Trace it: [1, 3] starts before the boundary, remove it

Next is [1, 3]: start = 1, and 1 >= 3 is false. It overlaps the kept [2, 3] (and [1, 2] too), so removed = 1. prev_end stays at 3.

Why is removing this one right, rather than removing [2, 3] to make room for it? Because they end at the same time, and [2, 3] was reached first, so keeping it already leaves at least as much room to the right. In general the interval we are looking at ends no earlier than the last kept one, so dropping it never costs anything the alternative would have gained.

The removed bar is amber. The boundary does not move on a removal; only kept intervals push it.
STEP 7

Trace it: keep [3, 4] and finish

Last is [3, 4]: start = 3, and 3 >= 3 is true. Touching again, so keep it and set prev_end = 4.

The loop ends and the function returns removed = 1. Three intervals survived, [1, 2], [2, 3], [3, 4], which is the most that can fit in [1, 4] when each has length one, so no better answer exists.

Four intervals, one sort, three comparisons.

STEP 8

Where this goes wrong: sorting by start

Sorting by start and keeping whichever comes first. Take [[1, 100], [2, 3], [4, 5]], which the panel now shows. In start order [1, 100] comes first and is kept, prev_end = 100, and both [2, 3] and [4, 5] start before 100, so the code reports 2 removals. The answer is 1: drop the long interval and the two short ones coexist. In end order, [2, 3] and [4, 5] come first, are kept, and [1, 100] is the one removed. A start-sorted sweep can be rescued by keeping the interval with the smaller end on each conflict, but sorting by end makes that the default.

Using > instead of >=. Then 2 > 2 is false at [2, 3], and touching intervals are treated as overlapping. The running example returns 2 instead of 1, and [[1, 2], [2, 3]] returns 1 instead of 0.

Seeding prev_end = 0 and looping over every interval. With negative coordinates such as [[-5, -1], [-2, 0]], neither start clears 0, both are counted removed, and the function returns 2 for an input whose answer is 1. Seed from intervals[0][1] instead.

Sort by end. The earliest finisher leaves the most room, and "starts first" says nothing about how much room it leaves.
STEP 9

Time and space

The sort is O(n log n). The sweep does one comparison and at most one assignment per interval, O(n), so the sort dominates. The sort is in place and the sweep keeps two integers: O(1) extra space.

ApproachTimeSpace
Try every subsetO(2ⁿ · n log n)O(n)
Sort by end, greedy sweepO(n log n)O(1) extra

The exchange argument in step 3 is what lets a single pass replace an exponential search: at every step there is a choice that is provably never worse.

STEP 10

The final solution

Ten lines. Every one of them maps to a step above.

  • intervals.sort(key=lambda interval: interval[1]) orders by end so the earliest finisher is always next.
  • prev_end = intervals[0][1] keeps the first interval and records its end as the boundary.
  • for start, end in intervals[1:] sweeps the rest.
  • if start >= prev_end: prev_end = end keeps a compatible interval; touching counts as compatible.
  • else: removed += 1 drops an overlapping one without moving the boundary.
  • return removed.
One-line summary to remember: sort by end, keep whatever starts at or after the last kept end, and count everything else as removed.
