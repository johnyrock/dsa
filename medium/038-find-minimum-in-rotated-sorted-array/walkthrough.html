Find Minimum in Rotated Sorted Array, narrated

Scroll through the thinking, from a linear scan to a binary search that decides which half holds the rotation point, with the state of the algorithm shown alongside.

Pattern used Binary Search compare nums[mid] with nums[hi] to pick the half that contains the drop

STEP 1

The problem

Someone took a sorted array of distinct integers and rotated it: they cut it at some point and moved the front piece to the back. [0, 1, 2, 4, 5, 6, 7] rotated four times becomes [4, 5, 6, 7, 0, 1, 2]. You get the rotated array and must return its smallest value, in O(log n) time.

Running example: nums = [4, 5, 6, 7, 0, 1, 2]. The answer is 0, at index 4. It is the only place where a value is smaller than the one before it.

The shape to hold in mind: a rotated sorted array is two ascending runs, [4, 5, 6, 7] and [0, 1, 2], with every value in the left run larger than every value in the right run. The minimum is the first element of the right run. If the rotation was a full turn, the "right run" is the whole array and the minimum is nums[0].

STEP 2

First instinct: scan for the drop

Walk the array once and return the first element that is smaller than its predecessor. If there is no such element, the array is not rotated and the answer is nums[0]:

for i in range(1, len(nums)):    if nums[i] < nums[i - 1]:        return nums[i]return nums[0]

Or simply min(nums). Both are O(n), and both are correct — the problem does not forbid them, it just asks for better. With n up to 5000 a scan is fast in practice, but the whole point of the exercise is to use the fact that the array is almost sorted and pay only O(log n).

On the running example the scan checks 5 > 4, 6 > 5, 7 > 6, then finds 0 < 7 and returns 0 after four comparisons. Binary search will do it in three probes and would do a million-element array in twenty.

STEP 3

The key idea: compare the middle with the right end

Binary search needs a yes/no question that is no on one side of the answer and yes on the other. Here it is: "is nums[i] <= nums[hi]?" Every element of the left run is bigger than nums[hi] (it is bigger than everything in the right run), so the question is no there. Every element of the right run is at most nums[hi], so the question is yes there. Over the running example that reads [no, no, no, no, yes, yes, yes], and the minimum is the first yes.

The comparison is if nums[mid] > nums[hi]. When it holds, mid is in the left run and the drop is strictly to its right: lo = mid + 1. Otherwise mid is in the right run, and the drop is at mid or to its left: hi = mid.

Why the right end and not the left? Comparing with nums[lo] is ambiguous: nums[mid] > nums[lo] is true when mid is in the left run, but it is also true when the array is not rotated at all, and those two cases need opposite moves. nums[hi] has no such ambiguity — the right end is always the end of the right run.

STEP 4

The approach, line by line

  • lo, hi = 0, len(nums) - 1 — the whole array, with hi inclusive because nums[hi] is the anchor.
  • while lo < hi — narrow until one index is left. No <=: we are finding a boundary, not matching a target.
  • mid = (lo + hi) // 2 — rounds down, so mid < hi whenever the loop runs, and lo = mid + 1 always makes progress.
  • if nums[mid] > nums[hi]: lo = mid + 1 — mid is in the big left run, so it and everything left of it are out.
  • else: hi = mid — mid through hi is sorted, so its smallest value is nums[mid]; keep mid, drop everything right of it.
  • return nums[lo] — lo == hi now, and that index is the minimum.

The invariant: the minimum's index is always inside [lo, hi]. The first branch removes only elements proven larger than nums[hi]; the second removes only elements to the right of a smaller nums[mid]. Neither can remove the minimum.

STEP 5

Trace it: mid = 3, value 7

Start with lo = 0, hi = 6. Then mid = (0 + 6) // 2 = 3, and nums[3] = 7. Compare with the right anchor: 7 > nums[6] = 2, so mid is in the left run.

That means indices 0 through 3 — the values 4, 5, 6, 7 — are all part of the run that sits above the drop. None of them can be the minimum. lo = mid + 1 = 4.

One probe has thrown away four of the seven candidates. The surviving range is [4, 6], the values [0, 1, 2].

STEP 6

Trace it: mid = 5, value 1

Now lo = 4, hi = 6, so mid = (4 + 6) // 2 = 5, and nums[5] = 1. Compare: 1 > nums[6] = 2 is false, so we are in the else branch. Indices 5 through 6 form a sorted run [1, 2], and its smallest value is at mid. The minimum is at index 5 or somewhere to its left.

hi = mid = 5. Notice that 5 stays inside the range: the value 1 could have been the minimum, so we must not discard it. Only the first branch skips mid.

Two candidates remain: indices 4 and 5, values 0 and 1.

STEP 7

Trace it: mid = 4, value 0, the answer

lo = 4, hi = 5, so mid = (4 + 5) // 2 = 4, and nums[4] = 0. Compare: 0 > nums[5] = 1 is false, so hi = mid = 4.

Now lo == hi == 4. The loop condition lo < hi fails, and we return nums[4], which is 0.

Three probes, three comparisons. Each one used the right anchor to decide which run mid was in, and each halved what was left.
STEP 8

Where this goes wrong: the wrong anchor and the wrong shrink

Comparing with the left end. Write if nums[mid] > nums[lo]: lo = mid + 1. On the running example the first probe still works (7 > 4, so lo = 4). But the second probe compares nums[5] = 1 with nums[lo] = nums[4] = 0: 1 > 0, so the code decides mid is "in the left run" and moves lo = 6. The loop ends and returns nums[6], which is 2, not 0. The left anchor cannot tell "left run" apart from "already sorted".

Discarding mid in the else branch. Write hi = mid - 1 the way an exact-match search would. On [3, 1, 2] the first probe is mid = 1, value 1, which is the minimum; 1 > nums[2] = 2 is false, so hi = 0, and the function returns nums[0] = 3. The else branch only knows the minimum is at mid or to its left, so mid has to stay.

Using while lo <= hi. Once lo == hi, mid == hi and hi = mid changes nothing, so the loop spins forever.

Anchor on nums[hi], keep mid when it might be the answer (hi = mid), skip it when it cannot be (lo = mid + 1), and stop at lo == hi.
STEP 9

Time and space

Every iteration does one comparison and removes at least half of the remaining range, so there are at most log₂ n iterations: O(log n) time. Three integer indices are the only extra state: O(1) space.

ApproachTimeSpace
min(nums) or scan for the dropO(n)O(1)
Sort and take the first elementO(n log n)O(n)
Binary search on the rotation pointO(log n)O(1)

Sorting is the one approach that is strictly worse than the scan: it throws away the structure the input already has and pays to rebuild it.

STEP 10

The final solution

Eight lines. Every one of them maps to a step above.

  • lo, hi = 0, len(nums) - 1 brackets the whole array with an inclusive right anchor.
  • while lo < hi runs until exactly one index survives.
  • mid = (lo + hi) // 2 picks the probe, rounding down so the first branch always advances.
  • if nums[mid] > nums[hi]: lo = mid + 1 — the left run, skip mid and everything before it.
  • else: hi = mid — the right run, keep mid and drop everything after it.
  • return nums[lo] is the value at the rotation point.
One-line summary to remember: a rotated sorted array is two ascending runs; compare the middle with the right end to learn which run it is in, and squeeze toward the boundary.
