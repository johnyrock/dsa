Medium · Binary Search · LeetCode #875

Koko Eating Bananas, narrated

I will test candidate eating speeds one by one first, then I use the fact that a speed being feasible stays feasible as it increases.

Pattern used Binary Search on the answer: feasibility is monotonic in the speed, so search the speed range

STEP 1

The problem

Koko has a row of banana piles, piles[i] bananas each, and h hours before the guards return. She chooses one eating speed k and sticks with it. Each hour she picks a pile and eats k bananas from it; if fewer than k remain, she finishes the pile and the rest of that hour is wasted. She cannot start a second pile in the same hour.

Return the smallest integer k that still gets every pile eaten within h hours.

Running example: piles = [3, 6, 7, 11], h = 8. The answer is 4: at speed 4 the piles take 1 + 2 + 2 + 3 = 8 hours, exactly the budget. At speed 3 they take 1 + 2 + 3 + 4 = 10, one too many.

Two things to notice. Because each hour is spent on exactly one pile, a pile of size p costs ceil(p / k) hours, no matter what the other piles look like. And because h >= len(piles) is guaranteed, some speed always works — at worst k = max(piles), which clears every pile in one hour each.

STEP 2

First instinct: try every speed from 1 upward

I can test every integer speed from 1 through the largest pile and return the first speed that finishes within h hours.

def minEatingSpeed(piles, h):    for k in range(1, max(piles) + 1):        hours = sum((pile + k - 1) // k for pile in piles)        if hours <= h:            return k

This is correct. It can test max(piles) speeds and scan every pile for each one, so the time complexity is O(n · max(piles)). It uses O(1) extra space.

A passing speed makes every larger speed feasible too. That monotonic result lets me binary search the answer instead of checking every possible speed.

STEP 3

The key idea: feasibility is monotonic, so binary search the speed

I look at what the brute force actually discovered: speeds 1, 2, 3 fail, then 4 passes — and every speed above 4 passes too, because eating faster can only reduce the hours. Laid out over the range, feasibility looks like [fail, fail, fail, pass, pass, …, pass].

A sorted-looking boolean array is exactly what binary search wants. The trick is that I am not searching for a value in an array; I am searching the answer space — the candidate speeds from lo = 1 to hi = max(piles) — for the first candidate that passes a test.

The feasibility test is hours = sum((pile + mid - 1) // mid for pile in piles), then hours <= h. The expression (pile + mid - 1) // mid is ceiling division in integers: for pile 7 and speed 4 it gives (7 + 3) // 4 = 2, not 7 // 4 = 1.

Because the test is monotonic, one probe rules out half the remaining speeds at once. Instead of up to a billion probes I need about log₂(10⁹) ≈ 30.

STEP 4

The approach, line by line

  • lo, hi = 1, max(piles) — the slowest legal speed and a speed that is guaranteed to work. Nothing above hi can beat it, so the answer is inside.
  • while lo < hi — keep going while more than one candidate is left. This is the "find the first passing value" shape, not the "find an exact match" shape, so there is no <=.
  • mid = (lo + hi) // 2 — probe the middle speed.
  • hours = sum((pile + mid - 1) // mid for pile in piles) — how many hours speed mid needs.
  • if hours <= h: hi = mid — feasible, so the answer is mid or slower. I keep mid; it might be the answer.
  • else: lo = mid + 1 — infeasible, so mid and everything slower are out.
  • return lo — when the loop stops, lo == hi and it is the smallest speed never rejected.

The invariant to hold in my head: hi always works, and everything below lo never does. Every branch preserves it, and the loop ends when the two meet.

STEP 5

Trace it: probe 6, then probe 3

I start with lo = 1, hi = 11. The first probe is mid = (1 + 11) // 2 = 6. Hours at speed 6: pile 3 takes 1, pile 6 takes 1, pile 7 takes 2, pile 11 takes 2 — 1 + 1 + 2 + 2 = 6, which is within the budget of 8. So hi = 6: the answer is 6 or something slower.

Second probe: mid = (1 + 6) // 2 = 3. Hours at speed 3: 1 + 2 + 3 + 4 = 10, more than 8. Speed 3 fails, and so does everything slower, so lo = 4.

Two probes have narrowed eleven candidates down to three: 4, 5, or 6. The panel shows the second probe, with the surviving range highlighted and the per-pile hour counts under each pile.

STEP 6

Trace it: probe 5

Now lo = 4, hi = 6, so mid = (4 + 6) // 2 = 5. Hours at speed 5: pile 3 takes (3 + 4) // 5 = 1, pile 6 takes (6 + 4) // 5 = 2, pile 7 takes (7 + 4) // 5 = 2, pile 11 takes (11 + 4) // 5 = 3. Total 1 + 2 + 2 + 3 = 8, and 8 <= 8 passes.

So hi = 5. Note that 5 stays inside the range — it passed, so it could still be the answer. Only failing speeds get thrown away with the mid + 1 step.

Two candidates remain: 4 and 5.

STEP 7

Trace it: probe 4, the answer

lo = 4, hi = 5, so mid = (4 + 5) // 2 = 4. Hours at speed 4: 1 + 2 + 2 + 3 = 8 again — pile 11 needs (11 + 3) // 4 = 3 hours, since 4 + 4 + 3 is three hours of eating. That passes, so hi = 4.

Now lo == hi == 4, the loop condition lo < hi is false, and I return lo, which is 4.

The brute force needed four probes for this tiny input and could need a billion for a big one. The binary search needed four probes here and never needs more than about thirty.
STEP 8

Where this goes wrong: floor division and the shrinking rule

Rounding the hours down. I write the check as hours = sum(pile // mid for pile in piles) and every partial pile is under-counted. On the running example speed 3 now appears to take 1 + 2 + 2 + 3 = 8 hours, so the search accepts it and moves down: it probes 2 (12 hours, fails) and returns 3. But at speed 3 the pile of 7 really takes 3 hours and the pile of 11 takes 4, for 10 hours total. Koko gets caught. The ceiling is the whole point of the "one pile per hour" rule.

Discarding a passing speed. I write hi = mid - 1 on the feasible branch, as I would in an exact-match search. Now the loop can end on a speed that was never tested: with lo = 4, hi = 5, probing 4 passes and sets hi = 3, the loop exits with lo = 4 — right answer here, by luck. On piles = [2, 2], h = 4 it probes 1 (passes, hi = 0) and then returns lo = 1, also by luck; but pair the same off-by-one with while lo <= hi and I return lo after it has walked past the answer. The safe pairing is lo < hi with hi = mid.

Starting at lo = 0. Speed 0 is not a legal speed, and the moment mid lands on 0 the check divides by zero.

Two rules: the feasibility test uses ceiling division, and a passing mid stays in the range (hi = mid) while a failing one leaves it (lo = mid + 1).
STEP 9

Time and space

Each probe scans all n piles once, and the number of probes is the number of halvings of the range [1, max(piles)]. With m = max(piles) that is O(n log m) time; the biggest input allows roughly 10⁴ × 30 = 3 × 10⁵ operations. The search keeps three integers and a running sum, so O(1) extra space.

ApproachTimeSpace
Try every speed 1 … max(piles)O(n · m)O(1)
Binary search on [1, sum(piles)]O(n log(n · m))O(1)
Binary search on [1, max(piles)]O(n log m)O(1)

The middle row is a common first draft: searching up to sum(piles) is correct because any speed that large works, but it wastes a few probes. Noticing that no speed above max(piles) ever helps tightens the range for free.

STEP 10

The final solution

Nine lines. Every one of them maps to a step above.

  • lo, hi = 1, max(piles) brackets the answer: lo is the slowest legal speed, hi is a speed known to work.
  • while lo < hi runs until exactly one candidate is left.
  • mid = (lo + hi) // 2 picks the probe.
  • hours = sum((pile + mid - 1) // mid for pile in piles) is the feasibility test, with ceiling division done in integers.
  • if hours <= h: hi = mid keeps a passing speed in play and drops everything faster.
  • else: lo = mid + 1 drops a failing speed and everything slower.
  • return lo is the first speed that passes.
One-line summary to remember: when "does k work?" is yes for every k past some threshold, binary search k itself and return the threshold.
