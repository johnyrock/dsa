Jump Game II, narrated

Scroll through the thinking, from a table of minimum jumps per index to a single sweep that advances a window one jump at a time, with the state of the algorithm shown alongside.

Pattern used Greedy BFS by levels without a queue: each window is everything reachable with one more jump

STEP 1

The problem

Same board as Jump Game: you start on index 0 of nums, and from index i you may jump forward to any index in i + 1 .. i + nums[i]. This time the last index is guaranteed to be reachable, and the question is how few jumps it takes.

Running example: nums = [2,3,1,1,4]. The answer is 2: jump 1 step to index 1, then 3 steps to index 4.

There are other routes. 0 → 2 → 3 → 4 is legal and takes three jumps, and so does 0 → 1 → 2 → 4. Notice the trap: the longest jump from index 0 lands on index 2, and that route is worse. Jumping far is not the same as jumping well.

The answer is a count, so as with the yes/no version we are free to reason about sets of positions rather than one chosen path.

STEP 2

Brute force: minimum jumps per index

The obvious table is dp[j] = fewest jumps to land on index j. Index 0 costs 0. For every other j, look at every earlier i that can reach it and take the cheapest:

dp = [0] + [inf] * (len(nums) - 1)for j in range(1, len(nums)):    for i in range(j):        if i + nums[i] >= j:            dp[j] = min(dp[j], dp[i] + 1)return dp[-1]

On the example the table comes out [0, 1, 1, 2, 2], and dp[4] = 2 is the answer. It is correct, but the double loop is O(n²), and at n = 10⁴ that is fifty million checks for a question whose answer is a small integer.

Look at the table again: it is non-decreasing, and equal values sit in contiguous runs. Level 0 is {0}, level 1 is {1, 2}, level 2 is {3, 4}. That structure is the whole shortcut.

STEP 3

The key insight: each jump count is a contiguous window

Indices reachable with at most k jumps form a prefix (any jump can be shortened), so indices whose minimum is exactly k form one contiguous window. Call its right edge end.

While sweeping through the window for k jumps, record farthest = max(i + nums[i]). The window for k + 1 jumps is exactly end + 1 .. farthest.

So we never need a queue or a table. Walk i left to right, keep farthest up to date, and the moment i == end the current window is exhausted: one more jump is unavoidable to go any further, so jumps += 1 and the next window runs to farthest.

This is breadth-first search where each level is an interval. The greedy choice is not "which index to jump to" but "when to commit to another jump", and that is forced.

STEP 4

The approach

  • jumps = 0, end = 0, farthest = 0: zero jumps reach only index 0.
  • for i in range(len(nums) - 1): sweep every index except the last; standing on the last index needs no further jump.
  • farthest = max(farthest, i + nums[i]): the best landing spot any index in the current window offers.
  • if i == end: the window is used up, so jumps += 1 and end = farthest opens the next one.
  • return jumps: the last index lies inside the final window.

In the panel the blue cell is i and the green cells are the window the next jump can land in.

STEP 5

Trace it: i = 0

farthest = max(0, 0 + 2) = 2. Then i == end is 0 == 0, true: the zero-jump window (just index 0) is exhausted. Commit one jump: jumps = 1, end = 2.

Indices 1 and 2 are now the window for one jump. We do not decide which of them to use; the sweep will visit both and ask each how far it can see.

STEP 6

Trace it: i = 1

farthest = max(2, 1 + 3) = 4. Index 1 can see all the way to the end. But i == end is 1 == 2, false, so no jump is committed yet: we are still inside the one-jump window and index 2 has not had its say.

This is the moment the greedy is being careful. It records that some index in this window reaches 4, without yet paying for the jump that gets there.

STEP 7

Trace it: i = 2, then i = 3

i = 2: farthest = max(4, 2 + 1) = 4, no improvement. Now i == end is 2 == 2, true: the one-jump window is exhausted. Commit: jumps = 2, end = 4. The two-jump window is indices 3 and 4, and 4 is the goal.

i = 3: farthest = max(4, 3 + 1) = 4, and 3 == 4 is false. The loop stops here because range(len(nums) - 1) is range(4), so i = 4 is never visited.

Return jumps = 2. The table said dp[4] = 2; the sweep found the same number with three integers and no inner loop.
STEP 8

Where this goes wrong: visiting the last index

Looping over range(len(nums)). Let the sweep reach i = 4. Since end was just set to 4, the test i == end is true one more time and a phantom third jump is counted: the function returns 3 instead of 2. Standing on the last index does not require jumping off it. The same bug makes [0] return 1 instead of 0.

Closing the window from the wrong index. Write end = i + nums[i] instead of end = farthest when the window closes. On the example the one-jump window closes at i = 2, which only reaches 3, so the two-jump window is {3} and a third jump is needed to reach 4: again 3. The whole point of farthest is to remember the best launch point, which was index 1, not the last one.

Sweep to len(nums) - 1, exclusive, and always open the next window at farthest, never at the current index.
STEP 9

Time and space

One pass with a max and one comparison per index: O(n) time. Three integers: O(1) space.

ApproachTimeSpace
dp[j] over all earlier iO(n²)O(n)
BFS with an explicit queueO(n)O(n) queue + visited
Window sweep (greedy)O(n)O(1)

BFS already gets the linear time, since each index is enqueued once. The sweep notices that every BFS level is an interval and replaces the queue with two integers, end and farthest.

STEP 10

The final solution

  • jumps = 0, end = 0, farthest = 0 describe the zero-jump level: only index 0.
  • for i in range(len(nums) - 1) visits every launch index; the last index is a destination, not a launch point.
  • farthest = max(farthest, i + nums[i]) is the best landing spot seen from the current level.
  • if i == end means the level is exhausted; jumps += 1 and end = farthest open the next level.
  • return jumps is the level on which the last index was discovered.
One-line summary to remember: each jump count is a contiguous window; sweep it, remember the farthest index it can see, and pay for one jump when the window runs out.
