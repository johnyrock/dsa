Multiply Strings, narrated

I’ll start with ordinary partial products, then place every digit pair directly into its result cells.

Pattern used Math digit i of num1 times digit j of num2 lands at result[i + j + 1], carry into result[i + j]

STEP 1

The problem

Two non-negative integers arrive as strings of digits, num1 and num2. Return their product as a string. The catch is the rule attached: no converting the whole string with int(), no big-integer library. You have to multiply the way you were taught in school, one digit at a time.

Running example: num1 = "123", num2 = "456". The answer is "56088".

The inputs can be 200 digits long, so the product can be 400 digits. That is far beyond a 64-bit integer, which is the practical reason the problem exists: in most languages you genuinely cannot take the shortcut.

Note the two input guarantees: no leading zeros except for the number "0" itself, and only digit characters. That means "0" is the only way a factor can be zero.

STEP 2

First instinct: cheat, or build partial products as strings

My first thought in Python is the one-line shortcut, but it is disallowed. The complete baseline is the paper method below: I build each partial product and add it to a running string total.

return str(int(num1) * int(num2))

The int() shortcut is disallowed and can overflow in fixed-width languages. My baseline instead follows the paper method: for each digit of num2, I build a padded partial product and add it to the running total.

total = "0"for j in range(len(num2) - 1, -1, -1):    partial = multiply_by_digit(num1, num2[j]) + "0" * (len(num2) - 1 - j)    total = add_strings(total, partial)

This takes O(m · n + n · (m + n)) time and O(m + n) space for partial strings. It works, but I build each partial product only to dissolve it into the sum.

By adding every digit pair directly into its final two result cells, I never build partial-product strings.

STEP 3

Key insight: every digit pair has a fixed address

Index the digits from the left, so num1[i] and num2[j]. Digit i of an m-digit number is worth 10^(m - 1 - i), and digit j of an n-digit number is worth 10^(n - 1 - j). Their product is worth 10^(m + n - 2 - i - j).

If the result array has m + n cells with the most significant on the left, then the cell for power 10^k is at index m + n - 1 - k. Substitute: the ones digit of num1[i] * num2[j] belongs at index i + j + 1, and its tens digit one cell to the left, at i + j.

On the example: i = 2, j = 2 is 3 × 6 = 18. It lands at cells 5 and 4 of the six-cell result: the 8 goes to result[5], the 1 to result[4].

So there is no need for partial-product strings. Allocate [0] * (m + n) once, and add every digit product straight into its two cells. The addition of partial products happens implicitly, because cells accumulate.

STEP 4

The approach, line by line

  • if num1 == "0" or num2 == "0": return "0" — a zero factor is the only case where the whole array stays 0, and I return "0", not a run of zeros.
  • result = [0] * (len(num1) + len(num2)) — one cell per possible output digit.
  • Two nested loops, both range(len(...) - 1, -1, -1), walking right to left so that carries move into cells that have not been finalised yet.
  • total = int(num1[i]) * int(num2[j]) + result[i + j + 1] — the digit product plus whatever earlier pairs already left in the ones cell.
  • result[i + j + 1] = total % 10 keeps the ones digit; result[i + j] += total // 10 pushes the carry left.
  • After the loops, I skip leading zeros with while start < len(result) - 1 and result[start] == 0, then join.

The panel starts with all six cells at 0 and the two pointers on the rightmost digits, i = 2 and j = 2.

STEP 5

Trace it: i = 2, j = 2

The first pair is the two rightmost digits: num1[2] = 3 and num2[2] = 6. Their product is 18, and result[5] is still 0, so total = 18 + 0 = 18.

Split it: 18 % 10 = 8 goes into result[5], and 18 // 10 = 1 is added into result[4]. The array is now [0, 0, 0, 0, 1, 8].

I can see this matches paper arithmetic exactly. Multiplying 123 by the 6 of 456, I write 8 in the ones column and carry 1.

STEP 6

Trace it: i = 2, j = 1, the first accumulation

Still on num1[2] = 3, now with num2[1] = 5. The product is 15, and the ones cell for this pair is result[2 + 1 + 1] = result[4], which already holds the carry 1 from the previous pair. So total = 15 + 1 = 16.

16 % 10 = 6 replaces the 1 in result[4]; 16 // 10 = 1 is added into result[3]. The array becomes [0, 0, 0, 1, 6, 8].

This is the moment the + result[i + j + 1] term earns its keep: without it, the carry from 3 × 6 would have been overwritten by the 5 from 3 × 5.

The loop then does i = 2, j = 0 (3 × 4 = 12, giving [0, 0, 1, 3, 6, 8]) and moves i to the middle digit.

STEP 7

Trace it: i = 1, j = 1, a carry into an unfinished cell

After i = 1, j = 2 (2 × 6 = 12, plus the 6 in result[4], making 18, so the array is [0, 0, 1, 4, 8, 8]), the pair num1[1] = 2, num2[1] = 5 gives 10. Its ones cell is result[3] = 4, so total = 10 + 4 = 14.

result[3] becomes 4 and result[2] goes from 1 to 2. The array reads [0, 0, 2, 4, 8, 8].

The remaining four pairs run the same way and finish at [0, 5, 6, 0, 8, 8]. Only the leftmost cell is a leading zero, so the strip loop stops at start = 1 and the join returns "56088".

Cells to the left of the current pair are never read until a later pair addresses them as i + j + 1. Walking right to left is what guarantees each cell is normalised to a single digit before it is finalised.
STEP 8

Where this goes wrong: dropping the cell, or the wrong cell

Overwriting instead of accumulating. If I write total = int(num1[i]) * int(num2[j]) without the + result[i + j + 1], every carry from an earlier pair is stomped on by the next pair's ones digit. On the running example the array finishes as [0, 4, 5, 6, 2, 8] and the function returns "45628" instead of "56088".

Off-by-one on the address. Using result[i + j] for the ones digit and result[i + j - 1] for the carry shifts everything one place left, and at i = j = 0 the carry index is -1, which Python quietly treats as the last cell. The example comes out as "560880": an extra trailing digit with the leading 5 wrapped around to the end.

Forgetting the zero guard. "0" × "12345" leaves six zero cells. The strip loop is deliberately bounded by len(result) - 1 so it keeps one cell and returns "0"; without that bound it returns the empty string.

The ones cell is i + j + 1, the carry cell is i + j, and I read the ones cell before writing it. For i = j = 0, its carry must land at index 0, not index −1.
STEP 9

Time and space

The nested loops visit every pair of digits once, so with m = len(num1) and n = len(num2) that is O(m · n) multiplications. The strip and join are O(m + n) on top. The result array is the only extra storage, O(m + n).

ApproachTimeSpace
Partial-product strings, added one by oneO(m · n + n · (m + n))O(m + n) per string, n strings built
Cell array with i + j + 1O(m · n)O(m + n)
Karatsuba (out of scope)O(n^1.585)O(n) recursion

For the 200-digit constraint that is 40,000 digit products, trivially fast. The cell approach wins on simplicity as much as on time: no helper functions, one array.

STEP 10

The final solution

  • if num1 == "0" or num2 == "0": return "0" — the zero factor, handled before any cells exist.
  • result = [0] * (len(num1) + len(num2)) — one cell per possible digit of the product.
  • Two range(len(...) - 1, -1, -1) loops — least significant digits first.
  • total = int(num1[i]) * int(num2[j]) + result[i + j + 1] — the product plus what is already in the ones cell.
  • result[i + j + 1] = total % 10 and result[i + j] += total // 10 — keep the ones digit, carry the rest.
  • The while strip and "".join(...) — drop leading zeros but keep at least one digit.
One-line summary to remember: digit i times digit j lives at result[i + j + 1], with its carry at result[i + j]; I walk right to left and the cells add themselves up.
