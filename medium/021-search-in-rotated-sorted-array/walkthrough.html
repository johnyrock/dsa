Search in Rotated Sorted Array, narrated

Scroll through identifying which half of the array is a normal sorted run at each step, and discarding the other.

Pattern used Binary Search at every mid, one half is a contiguous sorted run — check it, discard the other if the target can't be in it

STEP 1

The problem

Find a target's index in an ascending array that's been rotated at an unknown pivot, in O(log n) time.

Running example: [4,5,6,7,0,1,2], target = 0. Answer: index 4.
STEP 2

The key idea: one half is always properly sorted

Even after rotation, comparing nums[left] to nums[mid] reveals which half — left-to-mid, or mid-to-right — is a normal ascending run with no rotation inside it. Check whether the target falls in that sorted half's range; if so, search there, otherwise search the other half.

STEP 3

Trace it: first mid

left=0, right=6, mid=3 (value 7). nums[0]=4 <= nums[3]=7 — left half is sorted. Is target 0 in [4, 7)? No. Search the other half: left = mid+1 = 4.

STEP 4

Trace it: second mid

left=4, right=6, mid=5 (value 1). nums[4]=0 <= nums[5]=1 — left half [4,5] sorted. Is 0 in [0, 1)? Yes. Search there: right = mid-1 = 4.

STEP 5

Trace it: found

left=4, right=4, mid=4 (value 0). nums[4] == target — return 4.

STEP 6

Where this goes wrong

Using < instead of <= in nums[left] <= nums[mid] breaks the 2-element window case, where left == mid must still count as "sorted". Getting the two branches backwards — treating the mid-to-right half as sorted when it's actually the left half — silently searches the wrong side.

STEP 7

Time and space

O(log n) time — still standard binary search, just with an extra branch each step. O(1) space.

STEP 8

The final solution

  • Standard binary-search loop with left <= right.
  • Check nums[mid] == target first.
  • Determine which half is sorted via nums[left] <= nums[mid].
  • Check whether target falls in that sorted half's range to decide which side to keep.
