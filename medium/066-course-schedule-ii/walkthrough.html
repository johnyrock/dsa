Medium · Topological Sort · LeetCode #210

Course Schedule II, narrated

I will first test every possible course order, then repeatedly take a course whose prerequisites are already satisfied.

Pattern used Topological Sort Kahn's algorithm: BFS from zero-indegree courses, the pop order is the answer

STEP 1

The problem

There are numCourses courses numbered from 0. Each pair [a, b] says course b must be taken before course a. Return an order in which to take all the courses so that every prerequisite comes before the course that needs it. If no such order exists because the prerequisites loop back on themselves, return [].

This is Course Schedule with one extra demand: not just whether an order is possible, but one valid order itself. Any valid order is accepted, so there is no single right answer to match, only a constraint to satisfy.

Running example: numCourses = 4, prerequisites = [[1,0],[2,0],[3,1],[3,2]]. Course 0 unlocks 1 and 2; both of those unlock 3. The graph is a diamond. [0, 1, 2, 3] is a valid answer, and so is [0, 2, 1, 3].

Read each pair carefully: [1, 0] means "1 needs 0", so 0 comes first. Getting that direction backwards is the most common bug in this problem, and it produces an answer that looks plausible and is completely wrong.

STEP 2

First instinct: try every order

I can generate each course order and return the first one that places every prerequisite before its dependent course.

from itertools import permutationsdef findOrder(numCourses, prerequisites):    for order in permutations(range(numCourses)):        pos = {course: i for i, course in enumerate(order)}        if all(pos[before] < pos[after] for after, before in prerequisites): return list(order)    return []

This is correct. There are n! orders and checking one takes O(E) time, so the time complexity is O(n! · E). The generated order and position map use O(n) space.

Using the prerequisite counts directly tells me which course is safe to place now, and removing it may expose the next safe course.

STEP 3

The key idea: a course is ready when nothing is left to wait for

Instead of guessing an order and checking it, I build the order one course at a time, placing only a course that is legal right now. Those courses already have every prerequisite in the order. At the start, that means courses with no prerequisites.

I count each course's outstanding prerequisites as its indegree in the graph where each pair [a, b] is an edge b → a. When I place a course, I reduce the indegree of every course it unlocks. A course becomes legal when that count reaches 0.

I keep a queue of ready courses. I pop one, append it to order, decrement its neighbours, and enqueue any that reach 0. The order in which courses are popped is a valid answer. This is Kahn's algorithm.

And it detects cycles for free. A course inside a cycle has a prerequisite inside the same cycle, which has a prerequisite inside the cycle, and so on. None of them can ever reach indegree 0, so none is ever popped, and order ends up shorter than num_courses.

STEP 4

The approach, line by line

  • graph = [[] for _ in range(num_courses)] and indegree = [0] * num_courses: an adjacency list and a counter per course.
  • for course, pre in prerequisites: graph[pre].append(course); indegree[course] += 1: the edge runs from the prerequisite to the course it unlocks.
  • queue = deque(c for c in range(num_courses) if indegree[c] == 0): everything with no prerequisites is ready immediately. Iterating range(num_courses), not the pairs, catches courses that appear in no pair at all.
  • while queue: I pop a course, add it to order, reduce each nxt in graph[course], and enqueue nxt only when its count becomes exactly 0.
  • return order if len(order) == num_courses else []: a short order means a cycle swallowed the rest.

For the running example the build step produces graph = [[1, 2], [3], [3], []] and indegree = [0, 1, 1, 2]. Course 3 has indegree 2 because it waits on both 1 and 2.

STEP 5

Trace it: seed the queue and take course 0

I scan indegree = [0, 1, 1, 2]. Only course 0 is at 0, so queue = [0] and order = [].

I pop 0, giving order = [0]. Its neighbours are graph[0] = [1, 2]. I reduce course 1 from 1 - 1 = 0 and enqueue it, then do the same for course 2. Now indegree = [0, 0, 0, 2] and queue = [1, 2].

Course 3 has not moved: it is still waiting on two things. That is the whole mechanism in one step — placing 0 made exactly the courses that depended only on 0 ready, and nothing else.

STEP 6

Trace it: take 1, then 2

I pop 1 first because the queue is FIFO. This gives order = [0, 1]; its only neighbour, 3, drops from 2 - 1 = 1, so it is not ready yet. The queue is [2].

I then pop 2, giving order = [0, 1, 2]. Course 3 drops from 1 - 1 = 0, so I enqueue it. The result is queue = [3] and indegree = [0, 0, 0, 0].

Course 3 was decremented twice but enqueued once, on the decrement that took it to exactly 0. That == 0 test is what stops a course from appearing in the order twice.
STEP 7

Trace it: take 3, then check the length

I pop 3 and get order = [0, 1, 2, 3]. Because graph[3] is empty, the queue empties and the loop ends.

len(order) == 4 == num_courses, so I return [0, 1, 2, 3]. I can verify the pairs directly: 0 precedes 1 and 2, while 1 and 2 both precede 3.

For contrast, I use numCourses = 3 and [[1,0],[2,1],[1,2]]. Here indegree = [0, 2, 1]. I pop 0, reduce course 1 to 2 - 1 = 1, and the queue empties. order = [0] has length 1 rather than 3, so I return [].

STEP 8

Where this goes wrong: edge direction and the length check

Two specific bugs live here, and both produce output that looks like an answer.

Building the edge backwards. Writing graph[course].append(pre) and indegree[pre] += 1 turns every arrow around. On the running example that gives indegree = [2, 1, 1, 0], so course 3 is popped first, and the algorithm returns [3, 1, 2, 0]: course 3 before either of its prerequisites, and course 0 last. The pair [a, b] means b first, so the edge is b → a.

Returning order without the length check. With a cycle the queue just runs dry early. On [[1,0],[2,1],[1,2]] the wrong version returns [0], a partial schedule, instead of []. Kahn's algorithm never raises an error on a cycle; I identify it from the short order.

Edge from prerequisite to course, and always compare len(order) to num_courses before returning.
STEP 9

Time and space

Building the graph is one pass over the E pairs. The loop pops each of the V courses at most once, and across all pops each edge is examined once. That is O(V + E) time.

The adjacency list holds E entries, and indegree, the queue and order are each at most V long: O(V + E) space.

ApproachTimeSpace
Try every permutationO(n! × E)O(n)
DFS post-order, reversed, with cycle colouringO(V + E)O(V + E) + recursion depth
Kahn's algorithm (this solution)O(V + E)O(V + E)

The DFS version is equally fast but has to detect cycles explicitly with a "currently on the stack" colour and can hit the recursion limit at 2000 courses in a chain. Kahn's is iterative and the cycle check is a single length comparison.

STEP 10

The final solution

Every line maps to a step above.

  • graph[pre].append(course) and indegree[course] += 1 build the dependency graph with edges from prerequisite to course.
  • queue = deque(c for c in range(num_courses) if indegree[c] == 0) seeds with every course that is ready immediately.
  • course = queue.popleft() then order.append(course): the pop sequence is the answer.
  • indegree[nxt] -= 1 and if indegree[nxt] == 0: queue.append(nxt) release a course exactly once, when its last prerequisite is placed.
  • return order if len(order) == num_courses else [] turns a cycle into an empty answer.
My rule is: I repeatedly take any course with zero unmet prerequisites and record it; a short order means there was a cycle.
