Medium · Hash Map · LeetCode #49

Group Anagrams, narrated

Scroll through the thinking, from comparing every pair of words to a single pass that buckets each word under a canonical key, with the state of the algorithm shown alongside.

Pattern used Hash Map letter-count tuple -> bucket of words

STEP 1

The problem

You get a list of words. Put the anagrams together: two words belong in the same group when one can be rearranged into the other, which means they have exactly the same letters with the same counts.

Group order and the order inside a group do not matter. All the grader checks is that the right words ended up together.

Running example: ["eat", "tea", "tan", "ate", "nat", "bat"]. The answer is three groups: [eat, tea, ate], [tan, nat], [bat].

The awkward part is that "is an anagram of" is a relation between two words, but the output wants whole groups. Turning a pairwise relation into groups is what the rest of this page is about.

STEP 2

First instinct: compare every pair

The direct idea: for each word, look through the groups formed so far and ask a representative of each group "are you my anagram?" using the Valid Anagram check. If yes, join that group; if no group says yes, start a new one.

groups = []for word in strs:    for g in groups:        if is_anagram(word, g[0]):            g.append(word); break    else:        groups.append([word])

It is correct. But every word may be checked against every existing group, and each check costs O(k) for words of length k. In the worst case, with no anagrams at all, that is O(n² · k). At n = 10,000 the inner loop runs about fifty million anagram checks.

The waste is that we re-derive "same letters?" from scratch for every pair, when that fact depends on each word alone.

STEP 3

Reframe: give each word a name that anagrams share

Anagrams are words that look different but are the same multiset of letters. So compute something from each word that depends only on that multiset. Anagrams will get identical results; non-anagrams will not.

The simplest such thing is the word with its letters sorted. eat, tea and ate all sort to aet. tan and nat both sort to ant. bat sorts to abt and nothing else does.

Call this the word's key. Two words are anagrams if and only if their keys are equal. That is an exact test, not a heuristic.

Once every word has a key, grouping is no longer a pairwise question. It is "put things with the same key in the same bucket", which is exactly what a dictionary does.

STEP 4

The key idea: a dictionary from key to bucket

Walk the list once. For each word, compute its key, then append the word to groups[key], creating the bucket the first time the key appears. At the end, the buckets are the answer.

  • The dictionary lookup is O(1) on average, so grouping costs nothing beyond computing the key.
  • No word is ever compared to another word. The key does all the matching.

For the key itself there is a choice. Sorting the letters costs O(k log k). Because the alphabet is only lowercase a–z, we can instead count letters into a 26-slot list in O(k), and freeze that list into a tuple so it can be a dictionary key. The final code uses the tally; the sorted string is a perfectly acceptable answer too.

STEP 5

Trace it: the first three words

eat: the tally has a 1 in the a, e and t slots. Nothing has that key yet, so open a new bucket and drop eat in.

tea: same three letters, so the very same tally. The key is already in the dictionary. Append tea to the existing bucket. No comparison against eat happened; the equal key did the work.

tan: a, n, t. A different tally, so a second bucket opens.

STEP 6

Trace it: the rest of the list

ate lands with eat and tea. nat lands with tan. bat is a, b, t, which nobody has produced, so a third bucket opens.

Six words, six dictionary operations, three buckets. list(groups.values()) hands them back.

The panel shows keys as the sorted letters because they are easier to read than 26-number tuples. In the code the key is the tuple; the meaning is identical.
STEP 7

The pitfall: a key that is not exact

It is tempting to shortcut the key: add up the character codes, or multiply primes assigned to letters. Sums are not safe. "bdddddddddd" and "bbbbbbbbbbc" have the same total but are not anagrams, so a sum-based key would wrongly merge them.

The key must be a lossless description of the letter multiset. The sorted string and the 26-count tally both are. Anything that compresses further can collide.

Two smaller traps: a Python list cannot be a dictionary key, so the tally has to become a tuple; and the empty string is a legal word whose key is 26 zeros, which works fine as long as you do not special-case it away.

STEP 8

Time and space

Each of the n words is visited once, and building its tally touches each of its k letters once, so the total is O(n · k) time. With the sorted-string key it would be O(n · k log k).

The dictionary holds every word once plus one key per group, so O(n · k) space.

ApproachTimeSpace
Compare against every groupO(n² · k)O(n · k)
Sorted-string keyO(n · k log k)O(n · k)
Letter-count keyO(n · k)O(n · k)

The output itself is O(n · k), so no solution can use less space than that.

STEP 9

The final solution

Ten lines. Every one of them maps to a step above.

  • groups = {} is the key-to-bucket dictionary.
  • counts = [0] * 26 and the inner loop build the O(k) tally.
  • key = tuple(counts) freezes it so it can be hashed.
  • if key not in groups opens a bucket the first time a key appears.
  • groups[key].append(word) is the whole grouping step.
  • return list(groups.values()) hands back the buckets.
One-line summary to remember: anagrams share a canonical key, so bucket by key instead of comparing pairs.
