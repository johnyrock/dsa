Two Sum II - Input Array Is Sorted, narrated

I’ll start by checking every pair, then I use the sorted order to move two pointers inward without extra memory.

Pattern used Two Pointers one pointer at each end; the sum decides which one moves inward

STEP 1

The problem

You are handed an array numbers that is already sorted in non-decreasing order, plus a target. Exactly one pair of elements adds up to target, and you must return their 1-based positions, smaller index first.

Two rules matter. You cannot use the same element twice, and the follow-up asks for constant extra space, which rules out the hash map that solves the unsorted version.

Running example: numbers = [2, 7, 11, 15], target = 9. The answer is [1, 2], because 2 + 7 = 9 and those values sit at positions 1 and 2 when counting from 1.

The word "sorted" is doing all the work in this problem. The unsorted version needs memory to remember what it has seen; the sorted version can reason about where the answer must be.

STEP 2

First instinct: try every pair

My first instinct is to pick every i, then every j > i, and check their sum.

for i in range(len(numbers)):    for j in range(i + 1, len(numbers)):        if numbers[i] + numbers[j] == target:            return [i + 1, j + 1]return []

It checks O(n²) pairs, so it takes O(n²) time and uses O(1) extra space.

The sorted endpoints tell me which pointer is safe to move. Comparing the two outer values tells me which pointer can move without losing a possible answer.

STEP 3

Reframe: a sorted pair tells you which way to move

I put one pointer on the smallest value and one on the largest. I look at their sum. Because the array is sorted, that single comparison eliminates a whole element, not just a pair.

If numbers[left] + numbers[right] is too small, then numbers[left] paired with anything is too small, because numbers[right] is already the largest partner available. So left can never be part of the answer and I move it up.

If the sum is too big, the mirror argument holds: numbers[right] is too big for every partner, because numbers[left] is the smallest one on offer. I move right down.

Every comparison throws away one element for good. That is why a single pass suffices, and why no memory is needed to record what was tried.
STEP 4

The approach

  • left, right = 0, len(numbers) - 1: I start at the two ends.
  • while left < right: I keep going while the two pointers still name different elements.
  • total = numbers[left] + numbers[right]: the only pair examined this round.
  • if total == target: done, I return [left + 1, right + 1] to convert to 1-based positions.
  • if total < target: left += 1, otherwise right -= 1.

The panel shows left in blue and right in green, with the cells the pointers have already discarded dimmed out. Watch the sum shrink toward 9.

STEP 5

Trace it: 2 + 15 is too big

I start with left = 0 and right = 3. The sum is numbers[0] + numbers[3] = 2 + 15 = 17, which is larger than 9.

Apply the reframe: 15 is the largest number in the array and even with the smallest partner it overshoots. So 15 is out of the running for every pair, and right moves down to 2. Nothing about left changes.

STEP 6

Trace it: 2 + 11 is still too big

Now left = 0 and right = 2. The sum is 2 + 11 = 13. Still larger than 9, so the same reasoning applies to 11: it cannot pair with anything at or above 2, and 2 is the smallest value I have.

right moves down again, to 1. Two elements have been eliminated with two additions, and no pair was ever revisited.

STEP 7

Trace it: 2 + 7 hits the target

With left = 0 and right = 1, the sum is 2 + 7 = 9, exactly the target. The loop returns [left + 1, right + 1] = [1, 2].

The + 1 on each index is the only concession to the problem's 1-based convention; the algorithm itself thinks in ordinary 0-based indices.

Three additions instead of six pair checks. On a 30,000-element array the gap is 30,000 versus 450 million.
STEP 8

Where this goes wrong: the loop bound and the index base

Letting the pointers meet. I write while left <= right instead of while left < right and the two pointers can land on the same element. I take the running array with target = 4: the sums go 17, 13, 9, and then with left = right = 0 the loop computes 2 + 2 = 4 and returns [1, 1]. That uses element 1 twice, which the problem forbids. With the strict bound the loop simply ends.

Forgetting the 1-based shift. Returning [left, right] gives [0, 1] for the running example, which reads as a plausible answer and fails every test. The conversion belongs in the return statement and nowhere else.

Moving the wrong pointer. If total > target moves left up, the sum only grows: 17, then 22, then 26, and the loop walks off the end without ever finding 9.

Two different indices, so left < right. Too small moves left up, too big moves right down, and the answer is shifted by one only when returning.
STEP 9

Time and space

Each iteration moves exactly one pointer one step inward, and they start n - 1 apart, so there are at most n - 1 iterations: O(n) time. The state is two indices and a sum: O(1) space.

ApproachTimeSpace
Check every pairO(n²)O(1)
Hash map (Two Sum I)O(n)O(n)
Two pointers on sorted inputO(n)O(1)

The hash map wins on unsorted input, where there is no way to know which direction to move. Sorting first and then using two pointers costs O(n log n), which is why the two-pointer walk is only the right answer when the input already arrives sorted.

STEP 10

The final solution

Ten lines, and each one is a step above.

  • left, right = 0, len(numbers) - 1 puts a pointer at each end.
  • while left < right stops before the pointers name the same element.
  • total = numbers[left] + numbers[right] is the one pair examined per round.
  • return [left + 1, right + 1] converts to the 1-based answer the moment the sum matches.
  • left += 1 when too small, right -= 1 when too big: each branch discards an element that can never be in the answer.
  • return [] is never reached because a solution is guaranteed, but keeps the function total.
One-line summary to remember: on a sorted array, a too-small sum means the left value is useless and a too-big sum means the right value is useless, so I walk inward.
