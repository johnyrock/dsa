Time Based Key-Value Store, narrated

I will keep each key's history in order and scan it at first, then I use binary search to find the latest allowed timestamp.

Pattern used Binary Search rightmost timestamp ≤ t in a list that is sorted because writes arrive in order

STEP 1

The problem

Build a key-value store with a memory. set(key, value, timestamp) records that key took on value at that moment. get(key, timestamp) asks what the key's value was at that moment: the value from the most recent write at or before timestamp. If nothing that old exists, or the key was never set, return "".

The guarantee that makes this tractable: for any one key, the timestamps passed to set are strictly increasing. History is written in order.

Running example: set("foo", "bar", 1), set("foo", "bar2", 4), set("foo", "bar3", 7). Then get("foo", 4) is "bar2" (exact hit), get("foo", 5) is "bar2" (nothing written at 5, so fall back to 4), get("foo", 0) is "" (everything is newer), and get("foo", 9) is "bar3".

Two things the wording hides. A read at an exact timestamp must return that write, so "at or before" is a <=, not a <. And a read older than the first write is not an error — it is the empty string.

STEP 2

First instinct: keep every write and scan on read

I can append each value and timestamp to its key's history. On a read, I scan the history and remember the latest timestamp that does not exceed the request.

class TimeMap:    def __init__(self): self.store = {}    def set(self, key, value, timestamp):        self.store.setdefault(key, []).append((timestamp, value))    def get(self, key, timestamp):        best = ""        for t, value in self.store.get(key, []):            if t <= timestamp: best = value        return best

This is correct because timestamps for a key arrive in order, so the last fitting value is the answer. set takes O(1) time, while get takes O(k) time for a key with k writes. Stored histories use O(n) space across all operations.

The repeated read scan disappears because each key's timestamps are already sorted. Binary search can locate the rightmost timestamp at or before the requested time.

STEP 3

The key idea: the history is already sorted, so binary search it

The scan looks at every timestamp to find the last one <= timestamp. But the list is sorted — the problem promised increasing timestamps, and I only ever append — so the predicate "times[i] <= timestamp" reads [yes, yes, …, yes, no, no, …, no] across the list. I want the position of the last yes. That is a boundary, and binary search finds boundaries in O(log k).

I keep two parallel lists per key: self.times[key] and self.values[key]. set appends to both. get binary searches times for the insertion point of timestamp — the index just past every timestamp <= timestamp — and returns values[lo - 1].

This is exactly what bisect.bisect_right(times, timestamp) computes. Writing the loop by hand is worth doing once, because the two decisions inside it — <= versus <, and lo - 1 versus lo — are where every bug in this problem lives.

STEP 4

The approach, line by line

  • self.times = {}, self.values = {} — a dict from key to its sorted timestamps, and a parallel dict of values.
  • set: self.times.setdefault(key, []).append(timestamp) and the same for the value. O(1); the order guarantee means no sorting.
  • get: if key not in self.times: return "" — unknown key, no history.
  • lo, hi = 0, len(times) — hi is exclusive so that lo can end at len(times) when every write qualifies.
  • while lo < hi: mid = (lo + hi) // 2 — the standard boundary loop.
  • if times[mid] <= timestamp: lo = mid + 1 — this write is old enough, and so is everything before it; the boundary is to the right.
  • else: hi = mid — this write is too new; the boundary is at mid or to the left.
  • if lo == 0: return "" — no write is old enough.
  • return self.values[key][lo - 1] — the last write that qualified.

The invariant: everything before lo is <= timestamp, everything from hi on is > timestamp. When they meet, lo is the count of qualifying writes.

STEP 5

Trace it: three sets, then get("foo", 4)

After the three writes, times["foo"] is [1, 4, 7] and values["foo"] is ["bar", "bar2", "bar3"]. Each set was a pair of appends; nothing was searched or shifted.

Now get("foo", 4). I start with lo = 0, hi = 3. First probe: mid = (0 + 3) // 2 = 1, times[1] = 4, and 4 <= 4 is true — the exact hit counts as old enough, so lo = 2. Second probe: mid = (2 + 3) // 2 = 2, times[2] = 7, and 7 <= 4 is false, so hi = 2.

Now lo == hi == 2: two timestamps are <= 4. The answer is values[2 - 1] = values[1], which is "bar2".

STEP 6

Trace it: get("foo", 5), a timestamp nobody wrote

get("foo", 5) runs the identical probes. mid = 1: times[1] = 4 <= 5, so lo = 2. mid = 2: times[2] = 7 <= 5 is false, so hi = 2. Again lo = 2 and the answer is values[1] = "bar2".

This is the case the problem is really about: no write happened at 5, so the reader wants whatever was true at 5, which is the value set at 4 and not yet replaced by the one set at 7. The search does not care whether the timestamp is an exact hit — it only asks "how many writes are at or before this moment?" and takes the last of them.

STEP 7

Trace it: get("foo", 0) and get("foo", 9), the two edges

get("foo", 0): mid = 1, times[1] = 4 <= 0 is false, so hi = 1. mid = 0, times[0] = 1 <= 0 is false, so hi = 0. The loop ends with lo = 0: zero writes qualify. The guard if lo == 0: return "" fires and the answer is "". Without that guard the code would compute values[-1], which Python happily resolves to the newest value.

get("foo", 9): mid = 1, 4 <= 9, lo = 2. mid = 2, 7 <= 9, lo = 3. Now lo == hi == 3 — all three writes qualify — and the answer is values[3 - 1] = values[2], which is "bar3". This is why hi starts at len(times) rather than len(times) - 1: lo has to be able to reach 3.

Every get did two probes on a three-element history. A history of a hundred thousand writes needs seventeen.
STEP 8

Where this goes wrong: the comparison and the offset

Strict less-than. I write if times[mid] < timestamp and the search computes the left insertion point instead of the right one: an exact hit is treated as "too new". On get("foo", 4), mid = 1 gives 4 < 4 false, so hi = 1; then mid = 0, 1 < 4, lo = 1. The result is values[0] = "bar", the value from before the write at 4. The problem says "at or before", so the comparison must be <=.

Returning values[lo]. lo is the insertion point, one past the last qualifying write. get("foo", 5) ends with lo = 2 and would return values[2] = "bar3", a value from the future; get("foo", 9) ends with lo = 3 and raises IndexError.

Dropping the lo == 0 guard. values[0 - 1] is values[-1], so get("foo", 0) returns "bar3" instead of "". Python's negative indexing turns an off-by-one into a silently wrong answer rather than a crash.

Search with <=, I treat lo as a count, and answer with values[lo - 1] — after checking that the count is not zero.
STEP 9

Time and space

set is two list appends: O(1) amortized. get is a dict lookup plus a binary search over that key's k writes: O(log k). The store keeps every write, so space is O(n) in the total number of set calls — which is unavoidable, since any of them might be asked about later.

ApproachsetgetSpace
Per-key list, scan on readO(1)O(k)O(n)
Per-key dict timestamp → value, walk back from tO(1)O(t) worst caseO(n)
Per-key sorted list, binary searchO(1)O(log k)O(n)

The middle row is a tempting wrong turn: a plain dict answers exact-timestamp reads in O(1), but a read at a timestamp nobody wrote has to count downward until it finds one, and timestamps go up to 10⁷.

STEP 10

The final solution

The whole class. Every line maps to a step above.

  • self.times and self.values — parallel per-key lists, so the search reads plain integers.
  • setdefault(key, []).append(...) — set is an append; the order guarantee keeps the list sorted.
  • if key not in self.times: return "" — unknown key.
  • lo, hi = 0, len(times) — exclusive hi so lo can reach the end.
  • if times[mid] <= timestamp: lo = mid + 1 — an exact hit counts as old enough.
  • else: hi = mid — too new, I keep mid as a possible boundary.
  • if lo == 0: return "" — nothing is old enough.
  • return self.values[key][lo - 1] — the last qualifying write.
One-line summary to remember: writes arrive in order, so I append them and answer reads with a rightmost-<= binary search (bisect_right minus one).
