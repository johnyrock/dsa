Word Container, narrated

Scroll through the thinking, from comparing every pair of words to a single shared trie walked from every starting index, with the state of the search shown alongside.

Pattern used Trie insert every word once, then walk from each index looking for a completed word

STEP 1

The problem

A WordList holds a collection of words. A Solver looks at that list and returns every word that has some other word from the same list sitting inside it as a substring.

Running example: ["apple", "app", "banana", "nana"]. The answer is ["apple", "banana"] — "apple" contains "app", "banana" contains "nana".

"app" and "nana" are not in the answer: nothing else in the list is a substring of either of them.

STEP 2

First instinct: compare every pair

For each word, check it against every other word with the in operator:

result = []for word in words:    for other in words:        if other is not word and other in word:            result.append(word)            break

Correct, and fine for small lists. But this is O(n² · L) — for each of n words, scan up to n others, each substring check costing up to O(L). With 10,000 words that is 100 million substring scans.

STEP 3

Reframe: stop comparing pairs, index once

The n² cost comes from re-scanning the whole word list for every single word. But the word list itself never changes while we search — so build one shared structure over it, and query that structure instead of the raw list.

A trie stores every word as a path from the root, one character per edge, with the end of each word marked. Checking "does any word in the list equal this substring?" becomes a walk of that substring's length, regardless of how many words are stored.
STEP 4

The key idea: walk from every starting index

Insert every word into one trie. Then, for a given word W of length n, try each starting index 0..n-1: follow the trie one character at a time from that index, and stop the moment either the trie has no such branch, or a completed word is found.

  • If a completed word is found and it isn't W matching itself in full — that's a hit.
  • If the branch dead-ends, abandon only that starting index and try the next one.
The self-match exclusion matters: start == 0 and end == n - 1 is W checking against itself, which the trie cannot distinguish from a real match without that explicit check.
STEP 5

Trace it: checking "apple"

Trie holds: apple, app, banana, nana. Start at index 0 of "apple": a → p → p is already a completed word ("app"), and this is not a full self-match (end=2, n-1=4) — hit.

"apple" contains "app". No need to try the other starting indices — one hit is enough.
STEP 6

Trace it: checking "app"

Start at index 0: a → p → p reaches the end of "app" itself — but start=0, end=2=n-1, so this is excluded as a self-match. No other starting index (1: "pp", 2: "p") completes a word in the trie.

"app" is correctly left out of the answer.
STEP 7

Trace it: checking "banana"

Try starting indices in turn. At index 2 ("nana"): n → a → n → a reaches the end of "nana", and this is not W itself (start=2, not a full-length match) — hit.

"banana" contains "nana", found from a starting index other than 0 — this is exactly why every starting index has to be tried.
STEP 8

Where this goes wrong

Only trying index 0. "banana" contains "nana" starting at index 2 — checking only prefixes would miss it entirely.

Not excluding the self-match. Without the start == 0 and end == n - 1 guard, every word would trivially "contain itself" and the whole list would come back as the answer.

Breaking the outer loop on a dead branch. When the trie has no edge for the next character, only that starting index is a dead end — other starting positions can still succeed.

Duplicate identical words ("same", "same") do not count as containing each other either — the trie only records whether a word exists, not how many times, so the same self-match guard covers this case too.
STEP 9

Time and space

ApproachTimeSpace
Compare every pairO(n² · L)O(n · L) to store the words
Shared trie, walk from every indexO(n · L²) worst caseO(n · L) for the trie

Building the trie is O(n · L). Checking one word costs up to L starting positions, each walking up to L trie steps — O(L²) per word, O(n · L²) total. That drops the dependence on n from quadratic to linear.

A further step — not needed here, but worth naming — is Aho-Corasick, which builds failure links so the whole list can be scanned against every word in roughly O(total characters), independent of L².
STEP 10

The final solution

WordList builds the trie once. Solver runs the from-every-index walk against it for each word.

  • _insert — one pass per word, building/reusing shared trie nodes.
  • has_other_word_inside — nested loop over starting index and walk length, bounded by the trie.
  • The self-match guard is the one line that keeps "contains itself" from being a false positive.
One-line summary to remember: insert every word into one trie, then for each word try every starting index and stop at the first completed word that isn't the word matching itself in full.
